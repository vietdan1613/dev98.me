# Next.js

## 1. What is Next.js?

**Keywords:** `React framework` · `Routing` · `SSR/SSG` · `RSC` · `metadata` · `route handlers` · `deploy`

**Expectations:** Define Next.js as a React framework that structures your app around React. Name its built-in features: file-based routing, SSR/SSG, React Server Components, data fetching, metadata, route handlers, image and font optimization, and deployment-friendly defaults.

---

## 2. What is the App Router?

**Keywords:** `app/` · `page`/`layout` · `RSC`/`client` · `loading`/`error` · `handlers` · `metadata` · `cache`

**Expectations:** Explain that the App Router lives under `app/` with folder segments, `page.tsx` and `layout.tsx`, Server and Client Components, loading and error UI, route handlers, metadata, and caching. Default to App Router answers, and mention the Pages Router only when comparing `getStaticProps` and `getServerSideProps`.

---

## 3. How does file-system routing work?

**Keywords:** `Folders = segments` · `page.tsx` · `public route`

**Expectations:** Explain that each folder is a URL segment and `page.tsx` defines a public route. Give examples: `app/page` → `/`, `app/products/page` → `/products`, and `app/products/[id]/page` → `/products/:id`.

---

## 4. What is the difference between page.tsx and layout.tsx?

**Keywords:** `page` · `layout` · `shared shell`

**Expectations:** Contrast `page.tsx`, the UI for that route segment, with `layout.tsx`, which wraps child routes in a shared shell such as nav, sidebar, and providers.

---

## 5. What are dynamic routes?

**Keywords:** `[id]` · `[slug]` · `[...slug]` · `[[...slug]]` · `params` · `notFound()`

**Expectations:** Explain that dynamic segments use bracket syntax and that route handlers receive `params` (often async). Mention calling `notFound()` when the resource does not exist.

---

## 6. What are Server Components?

**Keywords:** `Server render` · `no client JS` · `Data/DB/secrets/SEO` · `smaller bundle`

**Expectations:** Explain that Server Components render on the server and do not ship their code to the browser, making them ideal for data, secrets, and SEO. Point out that they cannot use browser APIs, event handlers, or `useState`.

---

## 7. What are Client Components?

**Keywords:** `"use client"` · `browser` · `interactivity`

**Expectations:** Explain that Client Components are marked with `"use client"` and run in the browser, and name what they are for: clicks, local state, effects, browser APIs, and interactive widgets.

---

## 8. When should you use "use client"?

**Keywords:** `Interactive subtree` · `client boundary`

**Expectations:** Explain that `"use client"` belongs only on the subtree that needs interactivity. Point out the common mistake of marking an entire page as client for a single `onClick`.

---

## 9. Can Server Components render Client Components?

**Keywords:** `Serializable props` · `islands` · `children from server`

**Expectations:** Say yes, and explain passing serializable props into Client Components as interactive islands. Point out that Client Components cannot import Server Components, so server UI is passed as `children` from a server parent instead.

---

## 10. What is hydration?

**Keywords:** `SSR HTML` · `client JS` · `mismatch`

**Expectations:** Define hydration as attaching client JavaScript to server-rendered HTML so it becomes interactive. Name common mismatch causes: `Date.now()`, `Math.random()`, locale differences, or reading `localStorage` on the first render.

---

# Routing, metadata, and error handling

## 11. How do you handle a 404 in the App Router?

**Keywords:** `notFound()` · `not-found.tsx` · `route state`

**Expectations:** Explain calling `notFound()` when a resource is missing and providing `not-found.tsx` for the UI. Point out that a missing resource is route state, not merely an empty screen.

---

## 12. How do redirects work?

**Keywords:** `redirect()` · `server` · `no flash`

**Expectations:** Explain using `redirect()` on the server for auth or setup flows, and point out that this keeps protected content from flashing before the redirect completes.

---

## 13. How do you add metadata?

**Keywords:** `metadata` · `generateMetadata()` · `title` · `OG`

**Expectations:** Explain exporting static `metadata` or implementing `generateMetadata()` for dynamic routes. Mention the fields it sets from server data: title, description, canonical URL, and Open Graph tags.

---

## 14. What is loading.tsx?

**Keywords:** `Loading UI` · `Suspense` · `stable layout`

**Expectations:** Explain that `loading.tsx` defines route-level loading UI integrated with Suspense, giving a stable loading layout instead of a blank screen.

---

## 15. What is error.tsx?

**Keywords:** `Error boundary` · `Client Component` · `recoverable`

**Expectations:** Explain that `error.tsx` is a route error boundary and must be a Client Component. Point out that it is for recoverable errors, not for expected empty or not-found states.

---

# Rendering and caching questions

## 16. Static generation versus request-time rendering: how do you choose?

**Keywords:** `Static` · `request-time` · `mixed` · `Suspense`

**Expectations:** Explain choosing static when content can be stale until revalidate, and request-time for user-specific data, cookies, headers, or permissions. Mention mixed patterns that cache a shell and revalidate price or inventory, using Suspense for uncached segments.

---

## 17. What is generateStaticParams()?

**Keywords:** `Build-time` · `dynamic routes` · `known slugs`

**Expectations:** Explain that `generateStaticParams()` returns params at build time for dynamic routes, and give typical uses: known catalog slugs, docs, or marketing pages.

---

## 18. How does caching work with fetch()?

**Keywords:** `Explicit freshness` · `revalidate` · `per-request` · `secrets`

**Expectations:** State caching and freshness explicitly rather than relying on memorized defaults. Explain caching public slow-changing data with revalidate and keeping user-specific fetches per-request or private. Point out that cached responses must never be shared across users when secrets are involved.

---

## 19. What is revalidation?

**Keywords:** `Time-based` · `on-demand` · `CMS`

**Expectations:** Define revalidation as refreshing cached content on a schedule or on demand (for example after a CMS or admin publish). Name the freshness requirement first, then pick the mechanism.

---

## 20. How do you avoid stale search results?

**Keywords:** `Query-driven` · `server render` · `client fetch`

**Expectations:** Point out that search is query-driven and should not be treated as fully static. Name the options: server-render per query, fetch on the client, or use a cached shell with client-side refinement.

---

# Data, mutations, and APIs

## 21. What are Route Handlers?

**Keywords:** `route.ts` · `APIs` · `webhooks` · `server-only`

**Expectations:** Explain that Route Handlers in `route.ts` expose HTTP endpoints for APIs and webhooks on the server, keeping secrets and backend logic off the client.

---

## 22. Where should secrets live?

**Keywords:** `Server only` · `never Client` · `NEXT_PUBLIC_*`

**Expectations:** Explain that secrets belong on the server only, and point out they must never go in Client Components or in `NEXT_PUBLIC_*` environment variables, which are exposed to the browser.

---

## 23. What are Server Functions?

**Keywords:** `Server mutations` · `validate` · `authorize` · `trusted writes`

**Expectations:** Explain that Server Functions run mutations and server-side work you trust. Walk through what they do: validate input, authorize the caller, use secrets safely, and perform writes on the server.

---

## 24. How do you validate user input?

**Keywords:** `Client = UX` · `Server = trust` · `pending` · `a11y`

**Expectations:** Contrast client validation, which improves UX, with server validation, which enforces trust. Mention handling pending state, preventing double-submit, surfacing errors clearly, and keeping messages accessible.

---

## 25. How do you handle authentication?

**Keywords:** `Server cookies/headers` · `redirect` · `Proxy (Middleware)` · `authorize at data layer`

**Expectations:** Explain reading auth from server cookies or headers and redirecting before rendering protected UI. Point out that Proxy (Middleware) can gate early, but you must still authorize at the data and mutation layer.

---

# Performance and deployment questions

## 26. How do you reduce client JavaScript?

**Keywords:** `Prefer RSC` · `small "use client"` · `bundle size`

**Expectations:** Explain preferring Server Components, keeping `"use client"` boundaries small, and avoiding heavy shared imports in client trees. Mention measuring bundle impact.

---

## 27. How do images work in Next.js?

**Keywords:** `next/image` · `sized` · `reserve space` · `LCP`

**Expectations:** Explain using `next/image` for responsive sizing, reserved layout space to avoid CLS, and better LCP performance.

---

## 28. How do fonts work?

**Keywords:** `next/font` · `CLS` · `perceived perf`

**Expectations:** Explain that `next/font` self-hosts and optimizes fonts to reduce layout shift and improve perceived performance.

---

## 29. How do you debug a slow route?

**Keywords:** `Fetch` · `blocking data` · `JS size` · `hydration` · `LCP` · `cache`

**Expectations:** Walk through checking whether slow fetch, blocking data, client JS size, hydration cost, images/LCP, or disabled caching is the bottleneck. Mention measuring with build output, DevTools, server logs, and Web Vitals.

---

## 30. What changes between local development and production?

**Keywords:** `Dev = feedback` · `Prod = optimized` · `env` · `caching`

**Expectations:** Contrast development, which optimizes for fast feedback, with production, which serves real users with optimized builds. Point out that environment variables, build output, runtime behavior, and caching differ between the two.

---

# Senior Next.js questions

## 31. How would you design a product detail route?

**Keywords:** `Server page` · `SEO metadata` · `notFound` · `freshness`

**Expectations:** Describe a server-rendered page with SEO metadata, `notFound()` for missing products, and small client widgets for interactivity. Mention an explicit freshness policy for price and inventory.

---

## 32. How would you design an authenticated dashboard?

**Keywords:** `Auth gate` · `private server fetch` · `Suspense` · `URL filters`

**Expectations:** Explain gating auth before UI and fetching private per-user server data (no shared cache). Mention Suspense for heavy widgets and driving filters from the URL where it helps sharing and back navigation.

---

## 33. How would you migrate from Pages Router to App Router?

**Keywords:** `Route-by-route` · `layouts` · `client boundaries` · `coexist`

**Expectations:** Explain migrating incrementally: replace data APIs, adopt layouts and client boundaries, and watch for old mental models around RSC and cache. Point out that routes can coexist, use `"use client"` and Route Handlers as needed, and mention testing redirects, metadata, and 404 behavior.

---

## 34. How do you prevent hydration mismatches?

**Keywords:** `Match first render to SSR` · `effects` · `cookies on server`

**Expectations:** Explain keeping the first client render aligned with server HTML. Name the techniques: defer browser-only reads to effects, resolve cookies on the server, or isolate unknown state behind a client boundary.

---

## 35. How do you choose between server and client fetching?

**Keywords:** `Server: SEO/secrets/auth` · `Client: interactive/live` · `loading/error UI`

**Expectations:** Contrast server fetching, suited to SEO, secrets, auth, and avoiding waterfalls, with client fetching, suited to interactivity, browser-only APIs, and live updates after mount. Point out that either path always needs defined loading and error UI.

---

## 36. How do you handle partial failures?

**Keywords:** `Route error` · `widget error` · `degrade` · `fatal vs degradable`

**Expectations:** Explain separating route-level failures from local widget errors and degrading optional sections when possible. Point out the distinction between fatal errors and recoverable or degradable ones.

---

## 37. How do you keep a route maintainable?

**Keywords:** `Split concerns` · `page.tsx`

**Expectations:** Explain splitting data loading, metadata, UI composition, client widgets, mutations, and error handling instead of dumping everything into `page.tsx`.

---

## 38. How do you test a Next.js app?

**Keywords:** `Unit` · `RTL` · `E2E` · `route/integration`

**Expectations:** Walk through the layers: unit tests for utilities, React Testing Library for components, E2E for critical flows, and route or integration tests for redirects, Route Handlers, and server boundaries.

---

## 39. How do you review a Next.js PR?

**Keywords:** `Secrets` · `client size` · `route states` · `explicit cache`

**Expectations:** Name what you review for: leaked secrets, oversized client boundaries, loading/error/404 and metadata coverage, and explicit caching choices rather than accidental defaults.

---

## 40. What is a good final interview answer pattern?

**Keywords:** `Boundary` · `freshness` · `server/client` · `Next API` · `failure mode`

**Expectations:** Walk through the structure of a strong answer: name the boundary, state freshness needs, pick server vs client, cite a concrete Next.js API, and mention one failure mode you would handle.
