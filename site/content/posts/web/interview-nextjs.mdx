# Next.js

## 1. What is Next.js?

**Keywords:** `React framework` · `Routing` · `SSR/SSG` · `RSC` · `metadata` · `route handlers` · `deploy`

Next.js is a React framework that structures your app around React with built-in file-based routing, SSR/SSG, React Server Components, data fetching, metadata, route handlers, image and font optimization, and deployment-friendly defaults.

---

## 2. What is the App Router?

**Keywords:** `app/` · `page`/`layout` · `RSC`/`client` · `loading`/`error` · `handlers` · `metadata` · `cache`

The App Router lives under `app/` with folder segments, `page.tsx` and `layout.tsx`, Server and Client Components, loading and error UI, route handlers, metadata, and caching. Prefer App Router answers in interviews; mention Pages Router only when comparing `getStaticProps` and `getServerSideProps`.

---

## 3. How does file-system routing work?

**Keywords:** `Folders = segments` · `page.tsx` · `public route`

Each folder is a URL segment and `page.tsx` defines a public route—for example `app/page` → `/`, `app/products/page` → `/products`, and `app/products/[id]/page` → `/products/:id`.

---

## 4. What is the difference between page.tsx and layout.tsx?

**Keywords:** `page` · `layout` · `shared shell`

`page.tsx` is the UI for that route segment; `layout.tsx` wraps child routes with shared shell such as nav, sidebar, and providers.

---

## 5. What are dynamic routes?

**Keywords:** `[id]` · `[slug]` · `[...slug]` · `[[...slug]]` · `params` · `notFound()`

Dynamic segments use bracket syntax; route handlers receive `params` (often async). Call `notFound()` when the resource does not exist.

---

## 6. What are Server Components?

**Keywords:** `Server render` · `no client JS` · `Data/DB/secrets/SEO` · `smaller bundle`

Server Components render on the server and do not ship that component code to the browser—ideal for data, secrets, and SEO. They cannot use browser APIs, event handlers, or `useState`.

---

## 7. What are Client Components?

**Keywords:** `"use client"` · `browser` · `interactivity`

Client Components are marked with `"use client"` and run in the browser for clicks, local state, effects, browser APIs, and interactive widgets.

---

## 8. When should you use "use client"?

**Keywords:** `Interactive subtree` · `client boundary`

Use `"use client"` only on the subtree that needs interactivity. A common mistake is marking an entire page client for a single `onClick`.

---

## 9. Can Server Components render Client Components?

**Keywords:** `Serializable props` · `islands` · `children from server`

Yes—pass serializable props into Client Components as interactive islands. Client Components cannot import Server Components; pass server UI as `children` from a server parent instead.

---

## 10. What is hydration?

**Keywords:** `SSR HTML` · `client JS` · `mismatch`

Hydration attaches client JavaScript to server-rendered HTML so it becomes interactive. Mismatches often come from `Date.now()`, `Math.random()`, locale differences, or reading `localStorage` on the first render.

---

# Routing, metadata, and error handling

## 11. How do you handle a 404 in the App Router?

**Keywords:** `notFound()` · `not-found.tsx` · `route state`

Call `notFound()` when a resource is missing and provide `not-found.tsx` for the UI. A missing resource is route state, not merely an empty screen.

---

## 12. How do redirects work?

**Keywords:** `redirect()` · `server` · `no flash`

Use `redirect()` on the server for auth or setup flows so protected content does not flash before the redirect completes.

---

## 13. How do you add metadata?

**Keywords:** `metadata` · `generateMetadata()` · `title` · `OG`

Export static `metadata` or implement `generateMetadata()` for dynamic routes—title, description, canonical URL, and Open Graph tags from server data.

---

## 14. What is loading.tsx?

**Keywords:** `Loading UI` · `Suspense` · `stable layout`

`loading.tsx` defines route-level loading UI integrated with Suspense, giving a stable loading layout instead of a blank screen.

---

## 15. What is error.tsx?

**Keywords:** `Error boundary` · `Client Component` · `recoverable`

`error.tsx` is a route error boundary and must be a Client Component. Use it for recoverable errors, not for expected empty or not-found states.

---

# Rendering and caching questions

## 16. Static generation versus request-time rendering: how do you choose?

**Keywords:** `Static` · `request-time` · `mixed` · `Suspense`

Choose static when content can be stale until revalidate; choose request-time for user-specific data, cookies, headers, or permissions. Mixed patterns cache a shell and revalidate price or inventory; use Suspense for uncached segments.

---

## 17. What is generateStaticParams()?

**Keywords:** `Build-time` · `dynamic routes` · `known slugs`

`generateStaticParams()` returns params at build time for dynamic routes—typical for known catalog slugs, docs, or marketing pages.

---

## 18. How does caching work with fetch()?

**Keywords:** `Explicit freshness` · `revalidate` · `per-request` · `secrets`

State caching and freshness explicitly rather than relying on memorized defaults. Cache public slow-changing data with revalidate; keep user-specific fetches per-request or private; never share cached responses across users when secrets are involved.

---

## 19. What is revalidation?

**Keywords:** `Time-based` · `on-demand` · `CMS`

Revalidation refreshes cached content on a schedule or on demand (for example after a CMS or admin publish). Name the freshness requirement first, then pick the mechanism.

---

## 20. How do you avoid stale search results?

**Keywords:** `Query-driven` · `server render` · `client fetch`

Search is query-driven and should not be treated as fully static. Server-render per query, fetch on the client, or use a cached shell with client-side refinement.

---

# Data, mutations, and APIs

## 21. What are Route Handlers?

**Keywords:** `route.ts` · `APIs` · `webhooks` · `server-only`

Route Handlers in `route.ts` expose HTTP endpoints for APIs and webhooks on the server, keeping secrets and backend logic off the client.

---

## 22. Where should secrets live?

**Keywords:** `Server only` · `never Client` · `NEXT_PUBLIC_*`

Secrets belong on the server only—never in Client Components or in `NEXT_PUBLIC_*` environment variables exposed to the browser.

---

## 23. What are Server Functions?

**Keywords:** `Server mutations` · `validate` · `authorize` · `trusted writes`

Server Functions run mutation and server-side work you trust: validate input, authorize the caller, use secrets safely, and perform writes on the server.

---

## 24. How do you validate user input?

**Keywords:** `Client = UX` · `Server = trust` · `pending` · `a11y`

Client validation improves UX; server validation enforces trust. Handle pending state, prevent double-submit, surface errors clearly, and keep messages accessible.

---

## 25. How do you handle authentication?

**Keywords:** `Server cookies/headers` · `redirect` · `Proxy (Middleware)` · `authorize at data layer`

Read auth from server cookies or headers and redirect before rendering protected UI. Proxy (Middleware) can gate early, but still authorize at the data and mutation layer.

---

# Performance and deployment questions

## 26. How do you reduce client JavaScript?

**Keywords:** `Prefer RSC` · `small "use client"` · `bundle size`

Prefer Server Components, keep `"use client"` boundaries small, avoid heavy shared imports in client trees, and measure bundle impact.

---

## 27. How do images work in Next.js?

**Keywords:** `next/image` · `sized` · `reserve space` · `LCP`

Use `next/image` for responsive sizing, reserved layout space to avoid CLS, and better LCP performance.

---

## 28. How do fonts work?

**Keywords:** `next/font` · `CLS` · `perceived perf`

`next/font` self-hosts and optimizes fonts to reduce layout shift and improve perceived performance.

---

## 29. How do you debug a slow route?

**Keywords:** `Fetch` · `blocking data` · `JS size` · `hydration` · `LCP` · `cache`

Check whether slow fetch, blocking data, client JS size, hydration cost, images/LCP, or disabled caching is the bottleneck. Measure with build output, DevTools, server logs, and Web Vitals.

---

## 30. What changes between local development and production?

**Keywords:** `Dev = feedback` · `Prod = optimized` · `env` · `caching`

Development optimizes for fast feedback; production serves real users with optimized builds. Environment variables, build output, runtime behavior, and caching differ between the two.

---

# Senior Next.js questions

## 31. How would you design a product detail route?

**Keywords:** `Server page` · `SEO metadata` · `notFound` · `freshness`

A server-rendered page with SEO metadata, `notFound()` for missing products, small client widgets for interactivity, and explicit freshness policy for price and inventory.

---

## 32. How would you design an authenticated dashboard?

**Keywords:** `Auth gate` · `private server fetch` · `Suspense` · `URL filters`

Gate auth before UI, fetch with private per-user server data (no shared cache), use Suspense for heavy widgets, and drive filters from the URL where it helps sharing and back navigation.

---

## 33. How would you migrate from Pages Router to App Router?

**Keywords:** `Route-by-route` · `layouts` · `client boundaries` · `coexist`

Migrate incrementally: replace data APIs, adopt layouts and client boundaries, and watch for old mental models around RSC and cache. Routes can coexist; use `"use client"` and Route Handlers as needed, and test redirects, metadata, and 404 behavior.

---

## 34. How do you prevent hydration mismatches?

**Keywords:** `Match first render to SSR` · `effects` · `cookies on server`

Keep the first client render aligned with server HTML—defer browser-only reads to effects, resolve cookies on the server, or isolate unknown state behind a client boundary.

---

## 35. How do you choose between server and client fetching?

**Keywords:** `Server: SEO/secrets/auth` · `Client: interactive/live` · `loading/error UI`

Server fetching suits SEO, secrets, auth, and avoiding waterfalls. Client fetching suits interactivity, browser-only APIs, and live updates after mount. Always define loading and error UI for either path.

---

## 36. How do you handle partial failures?

**Keywords:** `Route error` · `widget error` · `degrade` · `fatal vs degradable`

Separate route-level failures from local widget errors—degrade optional sections when possible and distinguish fatal errors from recoverable or degradable ones.

---

## 37. How do you keep a route maintainable?

**Keywords:** `Split concerns` · `page.tsx`

Split data loading, metadata, UI composition, client widgets, mutations, and error handling instead of dumping everything into `page.tsx`.

---

## 38. How do you test a Next.js app?

**Keywords:** `Unit` · `RTL` · `E2E` · `route/integration`

Unit-test utilities, use React Testing Library for components, E2E for critical flows, and route or integration tests for redirects, Route Handlers, and server boundaries.

---

## 39. How do you review a Next.js PR?

**Keywords:** `Secrets` · `client size` · `route states` · `explicit cache`

Review for leaked secrets, oversized client boundaries, loading/error/404 and metadata coverage, and explicit caching choices rather than accidental defaults.

---

## 40. What is a good final interview answer pattern?

**Keywords:** `Boundary` · `freshness` · `server/client` · `Next API` · `failure mode`

Structure strong answers: name the boundary, state freshness needs, pick server vs client, cite a concrete Next.js API, and mention one failure mode you would handle.
