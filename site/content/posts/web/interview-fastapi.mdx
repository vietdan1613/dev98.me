# Beginner FastAPI

## 1. What is FastAPI?

**Keywords:** `Python` · `API Framework` · `Type Hints` · `Pydantic` · `Starlette`

**Expectations:** Define FastAPI as a modern Python framework for building APIs that uses Python type hints for validation, serialization, and automatic documentation. Mention that it is built on **Starlette** and **Pydantic**.

---

## 2. Why is FastAPI popular?

**Keywords:** `Fast` · `Type Hints` · `Async` · `Auto Docs`

**Expectations:** Explain that FastAPI is popular for its high performance, native async support, automatic validation, and automatic API documentation, all with relatively little boilerplate.

---

## 3. FastAPI vs Flask

**Keywords:** `Minimal` · `Validation` · `Async` · `OpenAPI`

**Expectations:** Contrast Flask as minimal and flexible with FastAPI's built-in validation, serialization, OpenAPI documentation, and native async support. Sum it up simply: Flask gives you more control, FastAPI gives you more features out of the box.

---

## 4. FastAPI vs Django

**Keywords:** `API-first` · `Full-stack` · `ORM` · `Admin`

**Expectations:** Contrast Django, a full-stack framework with ORM, authentication, admin, and templating, with FastAPI, which is API-focused and lets you choose your own database and other components. Say when to pick each: FastAPI for APIs, microservices, and ML services; Django for full web applications.

---

## 5. How do you define a route?

**Keywords:** `Decorator` · `HTTP Method` · `Path`

**Expectations:** Explain that you define a route with a FastAPI decorator, and point out that the decorator defines both the HTTP method and the URL path.

```python
@app.get("/items")
def read_items():
    return {"items": []}
```

---

## 6. What are path parameters?

**Keywords:** `URL Path` · `{id}` · `Validation`

**Expectations:** Define path parameters as values embedded directly in the URL, and mention that FastAPI validates their type automatically.

```python
@app.get("/items/{item_id}")
def read_item(item_id: int):
    return {"item_id": item_id}
```

---

## 7. What are query parameters?

**Keywords:** `?` · `Key/Value` · `Optional` · `Default`

**Expectations:** Explain that query parameters appear after `?` in the URL, and give their common uses: filtering, pagination, sorting, and searching.

```text
/items?skip=20&limit=10
```

---

## 8. What is automatic API documentation?

**Keywords:** `OpenAPI` · `/docs` · `/redoc` · `Swagger`

**Expectations:** Explain that FastAPI automatically generates API documentation from type hints, routes, and Pydantic models. Name the endpoints: `/docs` for Swagger UI, `/redoc` for ReDoc, and `/openapi.json` for the OpenAPI schema.

---

## 9. What role does Pydantic play?

**Keywords:** `Validation` · `Serialization` · `Models`

**Expectations:** Explain that Pydantic defines the structure of request and response data, and that FastAPI uses the model to validate incoming data and serialize responses.

```python
class Item(BaseModel):
    name: str
    price: float
```

---

# 🟡 Intermediate FastAPI

## 10. How does request validation work?

**Keywords:** `Type Hints` · `Pydantic` · `422`

**Expectations:** Explain that FastAPI automatically validates path, query, body, and header parameters using type hints and Pydantic models. Mention that when validation fails, FastAPI returns a **422** response with error details.

---

## 11. What are response models?

**Keywords:** `Security` · `Schema` · `Contract`

**Expectations:** Define a response model as the declaration of exactly what the API is allowed to return. Name its benefits: it prevents sensitive fields from leaking, documents the response, and keeps the API contract stable.

```python
@app.get("/users/{id}", response_model=UserPublic)
```

---

## 12. How does Dependency Injection work?

**Keywords:** `Depends()` · `Reusable` · `DB` · `Auth`

**Expectations:** Explain that FastAPI uses `Depends()` to inject reusable logic into endpoints, and give common dependencies: database sessions, authentication, permissions, and configuration.

```python
def read_items(db = Depends(get_db)):
    ...
```

---

## 13. What is Middleware?

**Keywords:** `Global` · `Request` · `Response` · `Cross-cutting`

**Expectations:** Explain that middleware runs for every request and response, and give common use cases: logging, CORS, headers, and request timing. Contrast it with dependencies: use **middleware** for global behavior and **dependencies** for endpoint-specific behavior.

---

## 14. How do you handle exceptions?

**Keywords:** `HTTPException` · `Exception Handler` · `Error Response`

**Expectations:** Explain that you raise `HTTPException` for errors inside an endpoint, and use custom exception handlers when the same error needs consistent handling across the application.

```python
raise HTTPException(
    status_code=404,
    detail="Item not found"
)
```

---

## 15. What are Background Tasks?

**Keywords:** `After Response` · `Short Task` · `BackgroundTasks`

**Expectations:** Explain that background tasks run after the response is sent and are good for sending emails, small notifications, and lightweight cleanup. Point out that important or long-running jobs requiring retries and persistence should use a real task queue such as Celery or RQ.

---

## 16. How do you handle file uploads?

**Keywords:** `UploadFile` · `Streaming` · `Memory`

**Expectations:** Explain that you use `UploadFile` for file uploads, and point out that it is preferred because it can stream large files instead of loading the entire file into memory.

```python
async def upload_file(file: UploadFile = File(...)):
    ...
```

---

## 17. What are the basics of authentication?

**Keywords:** `OAuth2` · `Bearer Token` · `JWT` · `Depends`

**Expectations:** Name FastAPI's security utilities (OAuth2, API keys, HTTP Basic, and Bearer authentication), then walk through a common flow: extract the token from the request, validate the JWT, get the current user, and reach the protected endpoint.

```text
Request
   ↓
Extract Token
   ↓
Validate JWT
   ↓
Get Current User
   ↓
Protected Endpoint
```

# 🔴 Advanced FastAPI

## 18. How does Dependency Injection work internally?

**Keywords:** `Dependency Tree` · `Resolve` · `Cache` · `yield`

**Expectations:** Explain that FastAPI inspects function signatures to build a dependency tree, resolves dependencies before the endpoint runs, and caches the same dependency within a request. Give an example: `get_db` can be shared by multiple dependencies without creating multiple sessions.

---

## 19. What are Lifespan Events?

**Keywords:** `Startup` · `Shutdown` · `Resources` · `ML Model`

**Expectations:** Explain that lifespan events run code when the application starts and shuts down, with typical uses like database connections, loading ML models, and initializing and cleaning up resources. Point out that lifespan runs **per worker process**.

```text
Startup
   ↓
Application Running
   ↓
Shutdown
```

---

## 20. How do you write custom middleware?

**Keywords:** `HTTP Middleware` · `ASGI` · `Request/Response`

**Expectations:** Walk through the simple approach using the `@app.middleware("http")` decorator with `call_next`, and mention that for advanced use cases you can implement Starlette or raw ASGI middleware.

```python
@app.middleware("http")
async def log_requests(request, call_next):
    response = await call_next(request)
    return response
```

---

## 21. How do you optimize FastAPI performance?

**Keywords:** `Async I/O` · `Lean Models` · `Caching` · `Profiling`

**Expectations:** Name the main strategies: use async for I/O-bound operations, keep response models efficient, cache expensive operations, and profile before optimizing. Mention tools such as `py-spy` for identifying real bottlenecks.

---

## 22. How do you handle API versioning?

**Keywords:** `URL Versioning` · `Header` · `Router`

**Expectations:** Describe URL versioning as a common approach that is simple and easy to understand, and explain that FastAPI can serve each version through a separate router.

```text
/v1/users
/v2/users
```

```python
v1_router = APIRouter(prefix="/v1")
v2_router = APIRouter(prefix="/v2")
```

---

## 23. How do you scale a FastAPI application?

**Keywords:** `Workers` · `Uvicorn` · `Gunicorn` · `Load Balancer`

**Expectations:** Explain that a single Uvicorn process uses one event loop, so production should run multiple workers. For larger systems, mention running multiple containers behind a load balancer and moving shared state to Redis or a database.

```bash
gunicorn app.main:app \
  -w 4 \
  -k uvicorn.workers.UvicornWorker
```

---

## 24. What caching strategies work with FastAPI?

**Keywords:** `In-process` · `Redis` · `HTTP Cache`

**Expectations:** Name the three common levels: in-process (`lru_cache`, `cachetools`), distributed (Redis, Memcached), and HTTP (`Cache-Control`, CDN). Point out that the main tradeoff is **cache invalidation and stale data**.

---

## 25. How do you manage database sessions?

**Keywords:** `Dependency` · `yield` · `Close` · `One Request`

**Expectations:** Explain that a database session is usually created and closed through a dependency, so each request gets its own session.

```python
def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()
```

# 🔵 Async Programming

## 26. Async vs Sync Endpoints

**Keywords:** `def` · `async def` · `Threadpool` · `Event Loop`

**Expectations:** Explain that a normal `def` endpoint runs in a threadpool, while an `async def` endpoint runs directly on the event loop. Point out that async is not automatically faster and is useful mainly for **I/O-bound work**.

---

## 27. What is `asyncio`?

**Keywords:** `Event Loop` · `Coroutine` · `Task` · `gather`

**Expectations:** Define `asyncio` as Python's library for asynchronous programming, name useful APIs such as `gather()`, `create_task()`, and `sleep()`, and mention that FastAPI uses asyncio through Starlette and Uvicorn.

```python
asyncio.gather()
asyncio.create_task()
asyncio.sleep()
```

---

## 28. What does `await` actually do?

**Keywords:** `Pause` · `Event Loop` · `Resume` · `Non-blocking`

**Expectations:** Explain that `await` pauses the current coroutine while the operation is waiting, letting the event loop run other coroutines until the I/O completes and the coroutine resumes. Point out that `await` only helps when the awaited operation is actually asynchronous.

```text
Coroutine
   ↓
await I/O
   ↓
Pause
   ↓
Other tasks run
   ↓
I/O completes
   ↓
Resume
```

---

## 29. What is the Event Loop?

**Keywords:** `Single Thread` · `Coroutines` · `Scheduler` · `I/O`

**Expectations:** Explain that the event loop runs coroutines and switches between them whenever one is waiting, and describe it as a **single worker handling many I/O tasks by switching between them**.

---

## 30. Concurrency vs Parallelism

**Keywords:** `Concurrency` · `Parallelism` · `I/O` · `CPU`

**Expectations:** Define **concurrency** as dealing with multiple tasks by switching between them and **parallelism** as executing multiple tasks at the same time on multiple CPU cores. Map them to FastAPI: async gives concurrency for I/O, while workers/processes give parallelism for CPU.

```text
Async → Concurrency → I/O
Workers/Processes → Parallelism → CPU
```

---

## 31. When does Async improve performance?

**Keywords:** `I/O-bound` · `Database` · `HTTP` · `Waiting`

**Expectations:** Explain that async improves performance when the application spends most of its time waiting, with examples like async database queries, external API calls, file I/O, and message queues. Point out that it does not help CPU-heavy work such as image processing or ML inference.

---

## 32. What happens with blocking operations in async code?

**Keywords:** `Blocking` · `Event Loop` · `time.sleep` · `to_thread`

**Expectations:** Explain that blocking code freezes the event loop, contrast calling `time.sleep()` inside an async endpoint (bad) with `await asyncio.sleep()` (better), and mention moving blocking work to a thread with `asyncio.to_thread()`.

```python
async def endpoint():
    time.sleep(5)
```

```python
await asyncio.sleep(5)
```

**Keywords:** `Resources` · `HTTP Methods` · `Stateless` · `Status Codes`

**Expectations:** Name the principles of good REST API design: resource-based URLs, correct use of HTTP methods, stateless requests, and consistent status codes. Give an example of the standard routes for a `users` resource.

GET    /users/{id}

## 34. Which HTTP Status Codes should you use?

| Code  | Meaning               |

| `201` | Created               |
| `204` | No Content            |
| `400` | Bad Request           |

## 35. How should you handle request validation?

**Keywords:** `Validate Early` · `Pydantic` · `Business Rules`

**Expectations:** Explain that data should be validated as close to the API boundary as possible, using Pydantic for input structure and validation before business logic and the database. Point out that business rules that depend on database state should remain in the business/service layer.

```text
Request
 ↓
Pydantic Validation
 ↓
Business Logic
 ↓
Database
```

---

## 36. How should response validation shape your API?

**Keywords:** `Response Model` · `Security` · `Contract`

**Expectations:** Explain that every public endpoint should ideally have a response model, name what it provides (field filtering, API documentation, and response validation), and point out that it prevents internal database fields from accidentally being exposed.

---

## 37. How do you handle pagination?

**Keywords:** `Offset` · `Cursor` · `Large Dataset`

**Expectations:** Contrast offset pagination, which is simple but becomes slower for deep pages, with cursor pagination, which is more efficient and stable for large datasets and infinite scrolling. Give the rule of thumb: offset for small/admin use cases, cursor for large datasets or infinite scroll.

```text
?page=2&limit=20
```

```text
?cursor=abc123&limit=20
```

```text
Small/Admin → Offset
Large/Infinite Scroll → Cursor
```

## 38. How do you handle filtering?

**Keywords:** `Query Params` · `Pydantic` · `Depends`

**Expectations:** Explain that simple filtering can use query parameters, while many filters are better handled with a Pydantic model as a dependency, which keeps the endpoint clean and makes validation easier.

```text
/orders?status=paid&customer_id=10
```

---

## 39. How does FastAPI generate OpenAPI schemas?

**Keywords:** `Routes` · `Type Hints` · `Pydantic` · `OpenAPI`

**Expectations:** Explain that FastAPI inspects routes, path/query parameters, Pydantic models, response models, and dependencies, and then generates an OpenAPI JSON schema.

```text

# 🗄️ Database

**Keywords:** `ORM` · `Engine` · `Session` · `Depends`

**Expectations:** Walk through the typical architecture: create a session factory and inject a SQLAlchemy session into each request via `Depends(get_db)`, which the endpoint then uses to talk to the database.

FastAPI Endpoint
      ↓
Depends(get_db)

```

## 41. What is SQLModel?

**Keywords:** `SQLAlchemy` · `Pydantic` · `Less Duplication`

**Expectations:** Explain that SQLModel combines ideas from SQLAlchemy and Pydantic, so a single model can represent both database data and validation schemas. Mention the advantage (less duplicated code) and the tradeoff (SQLAlchemy is more mature and flexible for complex schemas).

---

## 42. How do you access the database asynchronously?

**Keywords:** `Async Driver` · `Async Engine` · `AsyncSession`

**Expectations:** Walk through a common PostgreSQL setup, where FastAPI uses an `AsyncSession` backed by SQLAlchemy async and the `asyncpg` driver, and mention that database operations use `await`.

```text
FastAPI
 ↓
AsyncSession
 ↓
SQLAlchemy Async
 ↓
asyncpg
 ↓
PostgreSQL
```

---

## 43. How do you handle database transactions?

**Keywords:** `Commit` · `Rollback` · `Atomic`

**Expectations:** Explain that a transaction groups multiple database operations into one unit that is committed together, and that if something fails you roll back instead of leaving the database partially updated. Point out that you shouldn't commit after every operation in a multi-step transaction.

```text
Operation 1
   ↓
Operation 2
   ↓
Operation 3
   ↓
Commit
```

---

## 44. How do you manage database sessions?

**Keywords:** `One Session/Request` · `Close` · `Dependency`

**Expectations:** Cover the main rules: one session per request, close sessions after the request, and don't keep sessions open longer than necessary. Point out that request sessions shouldn't be shared with background tasks, which should create their own database session.

---

## 45. How do you handle database migrations?

**Keywords:** `Alembic` · `Revision` · `Upgrade` · `Review`

**Expectations:** Mention that Alembic is commonly used with SQLAlchemy, and walk through the typical workflow of autogenerating a revision and upgrading to head. Point out that you should always review generated migrations and never modify an already-applied migration; create a new migration instead.

```bash
alembic revision --autogenerate -m "add users"
alembic upgrade head
```

---

## 46. How do you configure connection pooling?

**Keywords:** `pool_size` · `max_overflow` · `timeout` · `pre_ping`

**Expectations:** Explain that SQLAlchemy manages a connection pool and name the important settings: `pool_size` for normal connections, `max_overflow` for extra connections during spikes, `pool_timeout` for the wait time for a connection, and `pool_pre_ping` to check whether a connection is still alive. Point out that total connections across all workers must always stay below the database connection limit.

```python
create_engine(
    DATABASE_URL,
    pool_size=10,
    max_overflow=20,
    pool_timeout=30,
    pool_pre_ping=True,
)
```
