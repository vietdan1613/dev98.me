# 🟢 Beginner FastAPI

## 1. What is FastAPI?

**Keywords:** `Python` · `API Framework` · `Type Hints` · `Pydantic` · `Starlette`

FastAPI is a modern Python framework for building APIs. It uses Python type hints for validation, serialization, and automatic documentation. It is built on **Starlette** and **Pydantic**.

---

## 2. Why is FastAPI popular?

**Keywords:** `Fast` · `Type Hints` · `Async` · `Auto Docs`

FastAPI is popular because it provides high performance, native async support, automatic validation, and automatic API documentation with relatively little boilerplate.

---

## 3. FastAPI vs Flask

**Keywords:** `Minimal` · `Validation` · `Async` · `OpenAPI`

Flask is minimal and flexible, while FastAPI provides built-in validation, serialization, OpenAPI documentation, and native async support.

**Simple answer:** Flask gives you more control; FastAPI gives you more features out of the box.

---

## 4. FastAPI vs Django

**Keywords:** `API-first` · `Full-stack` · `ORM` · `Admin`

Django is a full-stack framework with ORM, authentication, admin, and templating.

FastAPI is API-focused and lets you choose your own database and other components.

**Use FastAPI:** APIs, microservices, ML services.
**Use Django:** full web applications.

---

## 5. How do you define a route?

**Keywords:** `Decorator` · `HTTP Method` · `Path`

Use a FastAPI decorator:

```python
@app.get("/items")
def read_items():
    return {"items": []}
```

The decorator defines the HTTP method and URL path.

---

## 6. What are path parameters?

**Keywords:** `URL Path` · `{id}` · `Validation`

Path parameters are values embedded directly in the URL.

```python
@app.get("/items/{item_id}")
def read_item(item_id: int):
    return {"item_id": item_id}
```

FastAPI validates the type automatically.

---

## 7. What are query parameters?

**Keywords:** `?` · `Key/Value` · `Optional` · `Default`

Query parameters appear after `?` in the URL.

```text
/items?skip=20&limit=10
```

They are commonly used for filtering, pagination, sorting, and searching.

---

## 8. What is automatic API documentation?

**Keywords:** `OpenAPI` · `/docs` · `/redoc` · `Swagger`

FastAPI automatically generates API documentation from type hints, routes, and Pydantic models.

* `/docs` → Swagger UI
* `/redoc` → ReDoc
* `/openapi.json` → OpenAPI schema

---

## 9. What role does Pydantic play?

**Keywords:** `Validation` · `Serialization` · `Models`

Pydantic defines the structure of request and response data.

```python
class Item(BaseModel):
    name: str
    price: float
```

FastAPI uses the model to validate incoming data and serialize responses.

---

# 🟡 Intermediate FastAPI

## 10. How does request validation work?

**Keywords:** `Type Hints` · `Pydantic` · `422`

FastAPI automatically validates path, query, body, and header parameters using type hints and Pydantic models.

If validation fails, FastAPI returns a **422** response with error details.

---

## 11. What are response models?

**Keywords:** `Security` · `Schema` · `Contract`

A response model defines exactly what the API is allowed to return.

```python
@app.get("/users/{id}", response_model=UserPublic)
```

Benefits:

* Prevent sensitive fields from leaking.
* Document the response.
* Keep the API contract stable.

---

## 12. How does Dependency Injection work?

**Keywords:** `Depends()` · `Reusable` · `DB` · `Auth`

FastAPI uses `Depends()` to inject reusable logic into endpoints.

```python
def read_items(db = Depends(get_db)):
    ...
```

Common dependencies include database sessions, authentication, permissions, and configuration.

---

## 13. What is Middleware?

**Keywords:** `Global` · `Request` · `Response` · `Cross-cutting`

Middleware runs for every request and response.

Common use cases:

* Logging
* CORS
* Headers
* Request timing

Use **middleware** for global behavior and **dependencies** for endpoint-specific behavior.

---

## 14. How do you handle exceptions?

**Keywords:** `HTTPException` · `Exception Handler` · `Error Response`

Use `HTTPException` for errors inside an endpoint:

```python
raise HTTPException(
    status_code=404,
    detail="Item not found"
)
```

Use custom exception handlers when the same error needs consistent handling across the application.

---

## 15. What are Background Tasks?

**Keywords:** `After Response` · `Short Task` · `BackgroundTasks`

Background tasks run after the response is sent.

Good for:

* Sending emails
* Small notifications
* Lightweight cleanup

For important or long-running jobs requiring retries and persistence, use a real task queue such as Celery or RQ.

---

## 16. How do you handle file uploads?

**Keywords:** `UploadFile` · `Streaming` · `Memory`

Use `UploadFile` for file uploads.

```python
async def upload_file(file: UploadFile = File(...)):
    ...
```

`UploadFile` is preferred because it can stream large files instead of loading the entire file into memory.

---

## 17. What are the basics of authentication?

**Keywords:** `OAuth2` · `Bearer Token` · `JWT` · `Depends`

FastAPI provides security utilities such as OAuth2, API keys, HTTP Basic, and Bearer authentication.

A common flow is:

```text
Request
   ↓
Extract Token
   ↓
Validate JWT
   ↓
Get Current User
   ↓
Protected Endpoint
```

# 🔴 Advanced FastAPI

## 18. How does Dependency Injection work internally?

**Keywords:** `Dependency Tree` · `Resolve` · `Cache` · `yield`

FastAPI inspects function signatures and builds a dependency tree.

It resolves dependencies before the endpoint runs and caches the same dependency within a request.

For example, `get_db` can be shared by multiple dependencies without creating multiple sessions.

---

## 19. What are Lifespan Events?

**Keywords:** `Startup` · `Shutdown` · `Resources` · `ML Model`

Lifespan events run code when the application starts and shuts down.

Typical use cases:

* Database connections
* Loading ML models
* Initializing resources
* Cleaning up resources

```text
Startup
   ↓
Application Running
   ↓
Shutdown
```

One important point: lifespan runs **per worker process**.

---

## 20. How do you write custom middleware?

**Keywords:** `HTTP Middleware` · `ASGI` · `Request/Response`

The simple approach is:

```python
@app.middleware("http")
async def log_requests(request, call_next):
    response = await call_next(request)
    return response
```

For advanced use cases, you can implement Starlette or raw ASGI middleware.

---

## 21. How do you optimize FastAPI performance?

**Keywords:** `Async I/O` · `Lean Models` · `Caching` · `Profiling`

Main strategies:

1. Use async for I/O-bound operations.
2. Keep response models efficient.
3. Cache expensive operations.
4. Profile before optimizing.

Tools such as `py-spy` can help identify real bottlenecks.

---

## 22. How do you handle API versioning?

**Keywords:** `URL Versioning` · `Header` · `Router`

Common approaches:

```text
/v1/users
/v2/users
```

URL versioning is simple and easy to understand.

FastAPI can use separate routers:

```python
v1_router = APIRouter(prefix="/v1")
v2_router = APIRouter(prefix="/v2")
```

---

## 23. How do you scale a FastAPI application?

**Keywords:** `Workers` · `Uvicorn` · `Gunicorn` · `Load Balancer`

A single Uvicorn process uses one event loop.

For production, run multiple workers:

```bash
gunicorn app.main:app \
  -w 4 \
  -k uvicorn.workers.UvicornWorker
```

For larger systems, run multiple containers behind a load balancer.

Shared state should move to Redis or a database.

---

## 24. What caching strategies work with FastAPI?

**Keywords:** `In-process` · `Redis` · `HTTP Cache`

Three common levels:

* **In-process** → `lru_cache`, `cachetools`
* **Distributed** → Redis, Memcached
* **HTTP** → `Cache-Control`, CDN

The main tradeoff is **cache invalidation and stale data**.

---

## 25. How do you manage database sessions?

**Keywords:** `Dependency` · `yield` · `Close` · `One Request`

A database session is usually created and closed through a dependency.

```python
def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()
```

Each request gets its own session.

# 🔵 Async Programming

## 26. Async vs Sync Endpoints

**Keywords:** `def` · `async def` · `Threadpool` · `Event Loop`

A normal `def` endpoint runs in a threadpool.

An `async def` endpoint runs directly on the event loop.

**Important:** async is not automatically faster.

Async is useful mainly for **I/O-bound work**.

---

## 27. What is `asyncio`?

**Keywords:** `Event Loop` · `Coroutine` · `Task` · `gather`

`asyncio` is Python's library for asynchronous programming.

Useful APIs include:

```python
asyncio.gather()
asyncio.create_task()
asyncio.sleep()
```

FastAPI uses asyncio through Starlette and Uvicorn.

---

## 28. What does `await` actually do?

**Keywords:** `Pause` · `Event Loop` · `Resume` · `Non-blocking`

`await` pauses the current coroutine while the operation is waiting.

The event loop can execute other coroutines during that time.

```text
Coroutine
   ↓
await I/O
   ↓
Pause
   ↓
Other tasks run
   ↓
I/O completes
   ↓
Resume
```

`await` only helps when the awaited operation is actually asynchronous.

---

## 29. What is the Event Loop?

**Keywords:** `Single Thread` · `Coroutines` · `Scheduler` · `I/O`

The event loop runs coroutines and switches between them whenever one is waiting.

Think of it as a **single worker handling many I/O tasks by switching between them**.

---

## 30. Concurrency vs Parallelism

**Keywords:** `Concurrency` · `Parallelism` · `I/O` · `CPU`

**Concurrency:** dealing with multiple tasks by switching between them.

**Parallelism:** executing multiple tasks at the same time on multiple CPU cores.

In FastAPI:

```text
Async → Concurrency → I/O
Workers/Processes → Parallelism → CPU
```

---

## 31. When does Async improve performance?

**Keywords:** `I/O-bound` · `Database` · `HTTP` · `Waiting`

Async improves performance when the application spends most of its time waiting.

Good examples:

* Async database queries
* External API calls
* File I/O
* Message queues

It does not help CPU-heavy work such as image processing or ML inference.

---

## 32. What happens with blocking operations in async code?

**Keywords:** `Blocking` · `Event Loop` · `time.sleep` · `to_thread`

Blocking code freezes the event loop.

Bad:

```python
async def endpoint():
    time.sleep(5)
```

Better:

```python
await asyncio.sleep(5)
```

Or move blocking work to a thread with `asyncio.to_thread()`.

# 🟣 API Design

## 33. What REST principles does FastAPI encourage?

**Keywords:** `Resources` · `HTTP Methods` · `Stateless` · `Status Codes`

Good REST API design uses:

* Resource-based URLs
* HTTP methods correctly
* Stateless requests
* Consistent status codes

Example:

```text
GET    /users
POST   /users
GET    /users/{id}
PATCH  /users/{id}
DELETE /users/{id}
```

---

## 34. Which HTTP Status Codes should you use?

**Keywords:** `2xx` · `4xx` · `5xx`

Important codes:

| Code  | Meaning               |
| ----- | --------------------- |
| `200` | OK                    |
| `201` | Created               |
| `204` | No Content            |
| `400` | Bad Request           |
| `401` | Unauthorized          |
| `403` | Forbidden             |
| `404` | Not Found             |
| `409` | Conflict              |
| `422` | Validation Error      |
| `500` | Internal Server Error |

Easy distinction:

**401 → not authenticated**
**403 → authenticated but not allowed**

---

## 35. How should you handle request validation?

**Keywords:** `Validate Early` · `Pydantic` · `Business Rules`

Validate data as close to the API boundary as possible.

Use Pydantic for input structure and validation.

For example:

```text
Request
 ↓
Pydantic Validation
 ↓
Business Logic
 ↓
Database
```

Business rules that depend on database state should remain in the business/service layer.

---

## 36. How should response validation shape your API?

**Keywords:** `Response Model` · `Security` · `Contract`

Every public endpoint should ideally have a response model.

It provides:

1. Field filtering.
2. API documentation.
3. Response validation.

It prevents internal database fields from accidentally being exposed.

---

## 37. How do you handle pagination?

**Keywords:** `Offset` · `Cursor` · `Large Dataset`

Two common approaches:

### Offset Pagination

```text
?page=2&limit=20
```

Simple but becomes slower for deep pages.

### Cursor Pagination

```text
?cursor=abc123&limit=20
```

More efficient and stable for large datasets and infinite scrolling.

**Rule of thumb:**

```text
Small/Admin → Offset
Large/Infinite Scroll → Cursor
```

---

## 38. How do you handle filtering?

**Keywords:** `Query Params` · `Pydantic` · `Depends`

Simple filtering can use query parameters:

```text
/orders?status=paid&customer_id=10
```

For many filters, use a Pydantic model as a dependency.

This keeps the endpoint clean and makes validation easier.

---

## 39. How does FastAPI generate OpenAPI schemas?

**Keywords:** `Routes` · `Type Hints` · `Pydantic` · `OpenAPI`

FastAPI inspects:

* Routes
* Path/query parameters
* Pydantic models
* Response models
* Dependencies

Then it generates an OpenAPI JSON schema.

```text
/openapi.json
/docs
/redoc
```

# 🗄️ Database

## 40. How do you use SQLAlchemy with FastAPI?

**Keywords:** `ORM` · `Engine` · `Session` · `Depends`

Typical architecture:

```text
FastAPI Endpoint
      ↓
Depends(get_db)
      ↓
SQLAlchemy Session
      ↓
Database
```

Create a session factory and inject a session into each request.

---

## 41. What is SQLModel?

**Keywords:** `SQLAlchemy` · `Pydantic` · `Less Duplication`

SQLModel combines ideas from SQLAlchemy and Pydantic.

A single model can represent both database data and validation schemas.

**Advantage:** less duplicated code.

**Tradeoff:** SQLAlchemy is more mature and flexible for complex schemas.

---

## 42. How do you access the database asynchronously?

**Keywords:** `Async Driver` · `Async Engine` · `AsyncSession`

For PostgreSQL, a common setup is:

```text
FastAPI
 ↓
AsyncSession
 ↓
SQLAlchemy Async
 ↓
asyncpg
 ↓
PostgreSQL
```

Database operations use `await`.

---

## 43. How do you handle database transactions?

**Keywords:** `Commit` · `Rollback` · `Atomic`

A transaction groups multiple database operations into one unit.

```text
Operation 1
   ↓
Operation 2
   ↓
Operation 3
   ↓
Commit
```

If something fails, rollback instead of leaving the database partially updated.

**Important:** don't commit after every operation in a multi-step transaction.

---

## 44. How do you manage database sessions?

**Keywords:** `One Session/Request` · `Close` · `Dependency`

Main rules:

* One session per request.
* Close sessions after the request.
* Don't share request sessions with background tasks.
* Don't keep sessions open longer than necessary.

Background tasks should create their own database session.

---

## 45. How do you handle database migrations?

**Keywords:** `Alembic` · `Revision` · `Upgrade` · `Review`

Alembic is commonly used with SQLAlchemy.

Typical workflow:

```bash
alembic revision --autogenerate -m "add users"
alembic upgrade head
```

Always review generated migrations.

**Important:** never modify an already-applied migration. Create a new migration instead.

---

## 46. How do you configure connection pooling?

**Keywords:** `pool_size` · `max_overflow` · `timeout` · `pre_ping`

SQLAlchemy manages a connection pool.

Important settings:

```python
create_engine(
    DATABASE_URL,
    pool_size=10,
    max_overflow=20,
    pool_timeout=30,
    pool_pre_ping=True,
)
```

* `pool_size` → normal connections
* `max_overflow` → extra connections during spikes
* `pool_timeout` → wait time for a connection
* `pool_pre_ping` → checks whether a connection is still alive

Always make sure total connections across all workers stay below the database connection limit.
