# React Technical

## 1. What causes a component to re-render?

![React Hook Flow](/hook-flow-diagram.png)

**Keywords:** `State` · `Props` · `Parent Re-render` · `Hooks`

**Expectations:** Name the three triggers: a state change, a props change, or a parent re-render (which can pass new props or simply re-run the child). Mention that in function components hooks replace class lifecycle methods, and use the diagram above to walk through typical hook flow relative to render and effects.

---

## 2. What is controlled vs uncontrolled components?

**Keywords:** `Controlled` · `Uncontrolled` · `State` · `Refs`

**Expectations:** Define controlled components as those whose value or behavior is driven by React state or props (for example, an input whose `value` comes from state). Contrast them with uncontrolled components, which keep state in the DOM and are read or updated via refs rather than React state.

---

## 3. What is a Pure Component?

**Keywords:** `Same Props/State` · `Same Output` · `Shallow Compare`

**Expectations:** Define a pure component as one that renders the same output for the same props and state. Mention that `React.memo` wraps function components with a shallow prop comparison to skip re-renders when props are unchanged.

---

## 4. What is a Higher Order Component (HOC)?

**Keywords:** `Wrapper` · `Reuse Logic` · `Props`

**Expectations:** Define a HOC as a function that takes a component and returns a new component with added behavior or data, usually by injecting props. Explain that it is a pattern for sharing cross-cutting logic without duplicating it in every component.

---

## 5. What is reconciliation in React?

**Keywords:** `Virtual DOM` · `Diff` · `Fiber`

**Expectations:** Explain reconciliation as React’s process of comparing the new element tree with the previous one and applying the minimal set of updates to the real DOM. Mention that the Fiber architecture enables incremental work and priorities such as concurrent rendering.

---

## 6. What is the difference between `useEffect()` and `useLayoutEffect()`?

**Keywords:** `After Paint` · `Before Paint` · `DOM`

**Expectations:** Contrast the timing: `useEffect` runs after the browser paints and does not block painting, while `useLayoutEffect` runs after DOM updates but before paint. Point out that this is why `useLayoutEffect` keeps the user from seeing intermediate layout when you measure or mutate the DOM synchronously.

---

## 7. Why is `useLayoutEffect` considered dangerous if misused?

**Keywords:** `Blocking` · `Paint` · `Performance`

**Expectations:** Explain that because it runs synchronously before paint, heavy work inside `useLayoutEffect` blocks visual updates and can cause jank. Say you prefer `useEffect` unless you must read or change layout before the user sees it.

---

## 8. Give a real-world use case for `useLayoutEffect`

**Keywords:** `Measure DOM` · `Animation` · `Tooltip Position`

**Expectations:** Give the example of measuring element size or position before paint, such as positioning a tooltip, synchronizing scroll, or avoiding a flash of wrong layout when animations depend on dimensions.

---

## 9. How does Concurrent Rendering affect lifecycle behavior?

**Keywords:** `Interruptible` · `Priorities` · `Effects`

**Expectations:** Explain that concurrent rendering lets React pause, resume, or discard work on lower-priority updates. Point out that effect timing and what the user sees can differ from strictly synchronous renders, but the goal is smoother UI under load.

---

## 10. What is your error-handling strategy in production apps?

**Keywords:** `Error Boundaries` · `Async` · `try/catch`

**Expectations:** Describe wrapping UI subtrees in Error Boundaries to catch render errors and show fallback UI. For async logic (fetch, event handlers), mention `try/catch`, centralized logging, and user-visible error states rather than uncaught promise rejections.

---

## 11. How do you render a list in React?

**Keywords:** `map()` · `key` · `Elements`

**Expectations:** Explain mapping over the data array and returning a React element per item. Point out that each root element in the list needs a `key` prop so React can match items across updates.

---

## 12. Why are keys important in React lists?

**Keywords:** `Identity` · `Reconciliation` · `Reuse`

**Expectations:** Explain that keys tell React which list items correspond between renders. Point out that stable keys help preserve component state and avoid incorrect DOM reuse when items are inserted, removed, or reordered.

---

## 13. What makes a good key?

**Keywords:** `Unique` · `Stable` · `Id`

**Expectations:** Say a good key is unique among siblings and stable across renders, such as database ids, slugs, or other durable ids. Point out that random values created on each render are not good keys.

---

## 14. Can you use array index as a key?

**Keywords:** `Static List` · `Reorder` · `Anti-pattern`

**Expectations:** Explain that index keys are acceptable only when the list is static (no reorder, insert, or delete in the middle). Point out that if order or membership changes, index keys cause subtle bugs and lost local state.

---

## 15. What happens if you don’t provide keys?

**Keywords:** `Index Fallback` · `Warning`

**Expectations:** Explain that React falls back to array indices and may log a development warning. Point out that updates still work for simple cases but can be wrong when the list changes structurally.

---

## 16. How do you optimize large lists?

**Keywords:** `Virtualization` · `Windowing` · `Pagination`

**Expectations:** Name virtualization (for example `react-window` or `@tanstack/react-virtual`) so only visible rows mount and render. Mention combining it with memoized row components and stable keys.

---

## 17. How does `useId()` differ from `key`?

**Keywords:** `Accessibility` · `Stable ID` · `List Identity`

**Expectations:** Explain that `useId()` generates stable unique ids across renders for accessibility attributes (`htmlFor`, `aria-*`), while `key` identifies list items during reconciliation. Point out that `key` is not a substitute for DOM ids and must be unique per sibling in a list.

---

## 18. What is the Context API?

**Keywords:** `Global State` · `Prop Drilling` · `Provider`

**Expectations:** Define Context as a way to pass data through the tree without threading props through every level. Name the basic API: `createContext`, a `Provider`, and `useContext` (or `Consumer`).

---

## 19. When should you use Context?

**Keywords:** `Theme` · `Auth` · `Locale` · `Settings`

**Expectations:** Say to use it for low-churn global data that many components need: theme, authentication session, locale, or feature flags. Point out that you should avoid putting fast-changing or highly granular state in a single large context.

---

## 20. How does Context work?

**Keywords:** `createContext` · `Provider` · `useContext`

**Expectations:** Walk through the flow: `React.createContext(defaultValue)` creates a context object, a parent wraps children with `<Provider value={...}>`, and descendants call `useContext(MyContext)` to read the nearest provider value.

---

## 21. What are performance considerations for Context?

**Keywords:** `Re-render Consumers` · `Split Context` · `Memoize Value`

**Expectations:** Explain that when the provider `value` changes, all consuming components re-render. Mention splitting contexts by concern, memoizing the value object with `useMemo`, and colocating state so unrelated updates do not broadcast globally.

---

## 22. What causes performance issues in React apps?

**Keywords:** `Re-renders` · `Large Trees` · `Heavy Render`

**Expectations:** Name the common causes: unnecessary re-renders, huge component trees, expensive work during render, and global context updates. Mention that profiling usually shows whether the bottleneck is render count or render cost.

---

## 23. How do you optimize React performance?

**Keywords:** `memo` · `useMemo` · `useCallback` · `Split State`

**Expectations:** Mention memoizing expensive components and values (`React.memo`, `useMemo`, `useCallback`), splitting state and context, virtualizing long lists, and moving heavy work out of render (workers, deferred updates).

---

## 24. How do you detect unnecessary re-renders?

**Keywords:** `Profiler` · `DevTools` · `why-did-you-render`

**Expectations:** Name the React DevTools Profiler for recording commits and flame charts. Mention that during development, strategic logging or tools like “why did you render” help trace prop or context changes.

---

## 25. What is the difference between `React.memo()`, `useMemo()`, and `useCallback()`?

**Keywords:** `Component` · `Value` · `Function`

**Expectations:** Contrast the three: `React.memo` memoizes a component based on props, `useMemo` memoizes a computed value, and `useCallback` memoizes a function reference so child memo components see stable props.

---

## 26. When should you use `React.memo()` and when should you avoid it?

**Keywords:** `Expensive Render` · `Stable Props` · `Cheap Render`

**Expectations:** Say to use it when a component is expensive and props are often unchanged. Point out that you avoid it when renders are cheap or props change every time, because memo comparison overhead can cost more than re-rendering.

---

## 27. How would you optimize rendering a list with thousands of items?

**Keywords:** `react-window` · `Memoized Row` · `Stable Keys`

**Expectations:** Explain virtualizing the list so only visible items render. Mention extracting a memoized row component and passing stable keys and narrow props to limit re-renders while scrolling.

---

## 28. When would you use `useDeferredValue()` or `useTransition()`?

**Keywords:** `Non-urgent Updates` · `Concurrent` · `UX`

**Expectations:** Explain that both mark work as lower priority under concurrent features. Contrast `useDeferredValue`, which defers updating a derived value (for example, filtering a large list while typing), with `useTransition`, which wraps state updates (for example, switching tabs while loading heavy content) so the UI stays responsive.

---

## 29. What is React Testing Library (RTL)?

**Keywords:** `User-centric` · `DOM` · `Jest/Vitest`

**Expectations:** Explain that RTL encourages tests that query and interact with the DOM the way users do (roles, labels, and text) rather than testing component internals.

---

## 30. How do you find elements in RTL?

**Keywords:** `getByRole` · `getByLabelText` · `getByText`

**Expectations:** Name the queries in recommended order: `getByRole`, `getByLabelText`, `getByPlaceholderText`, `getByText`, then test ids as a last resort.

---

## 31. Why is `getByRole` preferred?

**Keywords:** `Accessibility` · `Real Usage` · `Resilience`

**Expectations:** Explain that roles mirror how assistive tech and users perceive the page. Point out that tests tied to roles tend to survive refactors better than tests tied to class names or component structure.

---

## 32. What’s the difference between `getBy`, `queryBy`, and `findBy`?

**Keywords:** `Sync` · `Async` · `Throw vs Null`

**Expectations:** Contrast the three: `getBy*` throws if the element is missing (sync), `queryBy*` returns `null` if missing (sync), and `findBy*` returns a promise and waits for the element (async). Mention that `findBy*` suits post-fetch or animated UI.

---

## 33. Why prefer `userEvent` over `fireEvent`?

**Keywords:** `Realistic` · `Pointer` · `Keyboard`

**Expectations:** Explain that `@testing-library/user-event` simulates full interaction sequences (focus, keydown, input) that are closer to real browser behavior than low-level `fireEvent` calls.

---

## 34. Why do we avoid testing implementation details?

**Keywords:** `Behavior` · `Refactor-safe` · `Public API`

**Expectations:** Explain that tests should assert observable behavior (what users see and do), not internal state, private methods, or child component structure. Point out that this keeps refactors from breaking tests unnecessarily.

---

## 35. When should you mock and when not?

**Keywords:** `Network` · `Timers` · `Real DOM`

**Expectations:** Say to mock external systems (APIs, modules you do not own, fake timers) and prefer real DOM behavior from RTL. Point out that you only mock browser APIs when JSDOM lacks them and you cannot run tests in a real browser.

---

## 36. Why use MSW instead of mocking `fetch`?

**Keywords:** `Network Layer` · `Realistic` · `Reuse`

**Expectations:** Explain that Mock Service Worker intercepts requests at the network level, so components use real `fetch`. Mention that handlers stay reusable across unit and integration tests.

---

## 37. What’s the biggest mistake people make with RTL?

**Keywords:** `Implementation Details` · `Enzyme-style` · `Queries`

**Expectations:** Name the common mistakes: testing internals, overusing test ids, or manually mounting with legacy patterns instead of rendering and querying as a user. Mention asserting on component instance state as another form of the same mistake.

---

## 38. What is JSDOM?

**Keywords:** `Node` · `DOM Implementation` · `No Browser`

**Expectations:** Define JSDOM as an implementation of DOM and HTML APIs in Node so tests run without a full browser. Mention that it is the default environment for many Jest/Vitest React setups.

---

## 39. Which browser APIs are missing or incomplete in JSDOM?

**Keywords:** `ResizeObserver` · `matchMedia` · `Clipboard`

**Expectations:** Name common gaps such as `ResizeObserver`, `matchMedia`, and `Clipboard`. Mention that tests depending on them may need polyfills, mocks, or browser runners (Playwright/Cypress).

---

## 40. Why is mocking browser APIs called “poking a hole in reality”?

**Keywords:** `Integration` · `E2E` · `Fidelity`

**Expectations:** Explain that heavy mocking drifts from production behavior. Point out that integration and E2E tests should use real environments where possible so layout, events, and APIs match what users experience.

---

## 41. When testing forms, what user behaviors should you simulate?

**Keywords:** `Type` · `Click` · `Submit` · `Validation`

**Expectations:** Mention simulating typing, tabbing, clicking buttons, submitting, and reading validation messages. Point out that you should not call `setState` directly or reach into form libraries’ internals.

---

## 42. Which matchers do you use?

**Keywords:** `jest-dom` · `Presence` · `Visibility`

**Expectations:** Name common `@testing-library/jest-dom` matchers: `toBeInTheDocument()`, `toHaveTextContent()`, `toHaveAttribute()`, `toBeVisible()`, and role/name assertions via `toHaveAccessibleName()`.

---

## 43. What patterns do you apply in your React project?

**Keywords:** `Composition` · `Compound Components` · `Prop Getters`

**Expectations:** Name the typical patterns: composition instead of deep props, latest ref for async callbacks, compound components for flexible APIs, and prop getters for controlled customization.

---

## 44. Why use Component Composition instead of inheritance?

**Keywords:** `children` · `Flexibility` · `Reuse`

**Expectations:** Explain that composition passes UI and behavior via `children` and slots instead of class hierarchies. Give examples such as tabs, layouts, and dropdowns, where consumers arrange pieces without fragile base classes.

---

## 45. Why store the latest value in `useRef` instead of state for async logic?

**Keywords:** `No Re-render` · `Stale Closure` · `Timers`

**Expectations:** Explain that refs update without re-rendering and always expose the current value in async callbacks. Mention intervals, debounced handlers, and subscriptions as cases where state closures would be stale.

---

## 46. What are Compound Components in React?

**Keywords:** `Shared Context` · `Implicit State` · `Flexible API`

**Expectations:** Define compound components as related components (for example `<Tabs>`, `<TabList>`, `<Tab>`) that share state through context. Point out that consumers can compose markup freely without prop drilling every callback.

---

## 47. How does the state reducer pattern customize behavior?

**Keywords:** `useReducer` · `Override Transitions` · `Inversion`

**Expectations:** Explain that consumers pass a reducer or dispatch rules to intercept state transitions (open/close, next step). Point out that this customizes behavior without forking the internal component implementation.

---

## 48. What is the advantage of a Prop Getter over prop collection?

**Keywords:** `Merge Props` · `Required Behavior` · `Override-safe`

**Expectations:** Explain that prop getters return props objects that merge required handlers and aria attributes while letting callers spread their own props. Mention accessible inputs, dropdowns, and modals as common uses.

---

# System Design

**Keywords:** `Component Architecture` · `State` · `Caching` · `Performance` · `A11y`

**Expectations:** Cover, in order: a modular route and feature structure, a clear split between server state (React Query) and UI state, data fetching with caching and pagination, code splitting, virtualization for large tables/charts, and responsive accessible layouts.

## 2. How would you design a real-time chat application for the web?

**Keywords:** `WebSockets` · `Message State` · `Virtualization` · `Offline`

**Expectations:** Cover, in order: UI layers (conversation list, thread, composer), WebSocket or SSE transport with reconnect, optimistic sends and ordering, virtualized message lists, presence/typing indicators, and error or offline handling.

---

## 3. How would you design a reusable, accessible, scalable modal component?

**Keywords:** `Portal` · `Focus Trap` · `ARIA` · `Controlled API` · `Stacking`

**Expectations:** Cover, in order: props for open/onClose, controlled vs uncontrolled usage, `createPortal`, focus trap and return focus, `role="dialog"` and `aria-modal`, escape and overlay click policy, theming, and stacking multiple modals without z-index chaos.

# State Management

## 1. How do you decide whether state belongs in Redux, React Query, or local component state?

**Keywords:** `UI State` · `Server State` · `Global` · `Auth`

**Expectations:** Explain the split: local state for UI that does not need sharing, Redux (or similar) for global client state many features update, and React Query for server data (fetch, cache, sync). Mention that auth often combines Context with secure storage and a minimal global footprint.

---

## 2. What is Redux Toolkit?

**Keywords:** `Boilerplate` · `Immer` · `Slices` · `Store`

**Expectations:** Explain that RTK is the recommended way to write Redux, with `configureStore`, `createSlice`, and built-in Immer reducing boilerplate. Point out that it keeps predictable unidirectional flow: UI → action → middleware → reducer → store → UI.

---

## 3. What does `createSlice` do?

**Keywords:** `Reducers` · `Actions` · `Initial State`

**Expectations:** Explain that `createSlice` defines initial state, reducers, and auto-generated action creators in one module, keeping related logic colocated.

---

## 4. How can RTK allow “mutating” state?

**Keywords:** `Immer` · `Draft` · `Immutable Update`

**Expectations:** Explain that reducers written with “mutation” syntax run inside Immer, which produces immutable state updates safely from draft changes.

---

## 5. What is `configureStore`?

**Keywords:** `DevTools` · `Middleware` · `Defaults`

**Expectations:** Explain that `configureStore` sets up the Redux store with sensible defaults: combined reducers, Redux DevTools integration, and default middleware (including checks in development).

---

## 6. How do you use middleware in RTK?

**Keywords:** `getDefaultMiddleware` · `concat` · `redux-logger`

**Expectations:** Walk through extending middleware via `configureStore({ middleware: (getDefaultMiddleware) => getDefaultMiddleware().concat(logger) })` for logging, analytics, or custom side effects. Point out that this keeps reducers pure.

---

## 7. What is `createAsyncThunk`?

**Keywords:** `Pending` · `Fulfilled` · `Rejected` · `API`

**Expectations:** Explain that `createAsyncThunk` creates an async action that dispatches lifecycle actions for API calls or other promises. Mention wiring the results into slices via `extraReducers` without manual boilerplate.

---

## 8. Can one slice respond to actions from another slice?

**Keywords:** `extraReducers` · `Cross-slice` · `Builder`

**Expectations:** Answer yes, and explain using `extraReducers` with `builder.addCase(otherSliceAction, ...)` to update state when external actions fire.

---

## 9. `extraReducers` vs `reducers`?

**Keywords:** `Own Actions` · `External Actions` · `Slice`

**Expectations:** Contrast them: `reducers` handle actions defined in the same slice, while `extraReducers` handle actions from other slices, thunks, or shared action creators.

---

## 10. What is Redux Saga?

**Keywords:** `Middleware` · `Side Effects` · `Generators`

**Expectations:** Define Redux Saga as middleware for complex async flows such as debouncing, polling, and cancellation. Point out that it uses declarative effects instead of putting async logic in components or reducers.

---

## 11. Why does Redux-Saga use generator functions?

**Keywords:** `pause` · `resume` · `Declarative`

**Expectations:** Explain that generators (`function*`) can yield effects and resume when async work completes. Point out that this makes sequential and parallel flows readable and testable.

---

## 12. What is a saga?

**Keywords:** `Watcher` · `Worker` · `Effect`

**Expectations:** Define a saga as typically a generator that watches for actions and runs workers that yield effects (`call`, `put`, `fork`, etc.) to perform side effects.

---

## 13. What is the difference between `call`, `put`, and `fork`?

**Keywords:** `Invoke` · `Dispatch` · `Non-blocking`

**Expectations:** Contrast the three: `put` dispatches an action, `call` invokes a function and waits for its result, and `fork` starts a non-blocking task in the background for concurrent work.

---

## 14. What does `takeLatest` do?

**Keywords:** `Cancel Previous` · `Debounce Pattern` · `Search`

**Expectations:** Explain that for a given action type, `takeLatest` cancels any in-flight worker from a prior dispatch and runs only the newest. Mention search or rapid clicks as ideal use cases.

---

## 15. What is the difference between `takeEvery`, `takeLatest`, and `takeLeading`?

**Keywords:** `Every` · `Latest` · `Leading`

**Expectations:** Contrast them: `takeEvery` runs a worker for every action, `takeLatest` keeps only the latest, and `takeLeading` ignores new actions until the current worker finishes.

---

## 16. How do you run multiple API calls in parallel in Redux-Saga?

**Keywords:** `all` · `Concurrent` · `Effects`

**Expectations:** Explain using `yield all([call(api1), call(api2), ...])` to run independent requests concurrently and collect results together.

---

## 17. How do you handle errors in Redux-Saga?

**Keywords:** `try/catch` · `onError` · `Failure Action`

**Expectations:** Explain wrapping `yield call(...)` in try/catch and dispatching failure actions. Mention optionally using `spawn` with error boundaries for detached tasks.

---

## 18. How do you cancel a running saga?

**Keywords:** `takeLatest` · `cancel` · `fork`

**Expectations:** Point out that `takeLatest` auto-cancels prior tasks. Mention manually using `cancel(forkedTask)` or race patterns when a route changes or a component unmounts.

---

## 19. What is `race` and when would you use it?

**Keywords:** `First Wins` · `Timeout` · `Cancellation`

**Expectations:** Explain that `race` runs multiple effects and completes when the first finishes. Give examples such as timeouts, “click cancel vs wait for response”, or competing events.

---

## 20. Why should reducers remain pure when using Redux-Saga?

**Keywords:** `Predictable` · `Time-travel` · `Testability`

**Expectations:** Explain that side effects belong in sagas while reducers stay synchronous and pure. Point out that this keeps state updates deterministic, easy to test, and compatible with DevTools.

---

## 21. What is React Query?

**Keywords:** `Server State` · `Cache` · `Sync` · `TanStack Query`

**Expectations:** Explain that React Query (TanStack Query) manages server state: fetching, caching, background refetch, and keeping UI in sync with the backend. Point out that it avoids duplicating loading/error logic everywhere.

---

## 22. What is a mutation?

**Keywords:** `POST` · `PUT` · `DELETE` · `useMutation`

**Expectations:** Define a mutation as an operation that changes server data. Explain that `useMutation` handles execute, loading, error, and success callbacks, often invalidating related queries afterward.

---

## 23. What are query keys and why are they important?

**Keywords:** `Cache Key` · `Identity` · `Invalidation`

**Expectations:** Explain that query keys uniquely identify cached data (often arrays like `['users', id]`). Point out that they drive caching, deduplication, and targeted `invalidateQueries`.

---

## 24. How does React Query handle caching?

**Keywords:** `Stale-while-revalidate` · `Query Key` · `Background Refetch`

**Expectations:** Explain that data is stored by query key. Point out that fresh data can be shown immediately while stale queries refetch in the background according to `staleTime` and triggers like focus or reconnect.

---

## 25. What is `staleTime`?

**Keywords:** `Fresh` · `No Refetch` · `TTL`

**Expectations:** Define `staleTime` as the duration data is considered fresh. Point out that while data is fresh, mounts may not refetch automatically, depending on configuration.

---

## 26. What is `cacheTime` / `gcTime`?

**Keywords:** `Garbage Collection` · `Inactive` · `Memory`

**Expectations:** Explain that it is how long unused query data stays in memory after the last observer unmounts, before garbage collection. Mention that it is called `gcTime` in v5, formerly `cacheTime`.

---

## 27. When does React Query refetch automatically?

**Keywords:** `Window Focus` · `Reconnect` · `Interval`

**Expectations:** Name the common triggers: window refocus, network reconnect, `refetchInterval`, and invalidation after mutations. Point out that these are subject to `staleTime` and `enabled`.

---

## 28. What does `enabled` do?

**Keywords:** `Conditional Fetch` · `Dependencies` · `Lazy Query`

**Expectations:** Explain that with `enabled: false`, the query does not run automatically until toggled true. Mention that this is useful when an id or auth token must exist first.

---

## 29. What is the difference between `isLoading` and `isFetching`?

**Keywords:** `First Load` · `Any Request` · `Background`

**Expectations:** Contrast them: `isLoading` is true when there is no cached data yet and a fetch is in flight, while `isFetching` is true for any in-flight request, including background refetches.

---

## 30. How do you invalidate queries?

**Keywords:** `queryClient` · `invalidateQueries` · `Refetch`

**Expectations:** Explain calling `queryClient.invalidateQueries({ queryKey: [...] })` to mark matching queries stale and trigger refetch for active observers.

---

## 31. How do you perform optimistic updates?

**Keywords:** `onMutate` · `Rollback` · `setQueryData`

**Expectations:** Walk through updating the cache in `onMutate`, returning rollback context, and restoring on `onError` if the mutation fails. Point out that this makes the UI feel instant while staying consistent.

---

## 32. How do you handle pagination and infinite scrolling?

**Keywords:** `useInfiniteQuery` · `getNextPageParam` · `Flatten`

**Expectations:** Explain that `useInfiniteQuery` loads pages with `fetchNextPage`, using `getNextPageParam` from the last response. Mention flattening `data.pages` in the UI and virtualizing long feeds when needed.

---

## 33. How do you handle mutation errors?

**Keywords:** `onError` · `Toast` · `Retry`

**Expectations:** Explain using `onError` in `useMutation` to show messages, log, or revert optimistic updates. Mention pairing it with global error boundaries or toasts for consistent UX.

---
