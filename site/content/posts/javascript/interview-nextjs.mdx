## Next.js Fundamentals

### 1. What is Next.js?

Next.js is a React framework for building web applications. It adds file-system routing, server rendering, static generation, Server Components, data fetching conventions, metadata, Route Handlers, image and font optimization, and deployment patterns around React.

React gives you the component model. Next.js gives you the application structure.

### 2. What is the App Router?

The App Router is the modern routing system based on the `app/` directory. It uses route segments, `page.tsx`, `layout.tsx`, Server Components, Client Components, loading UI, error boundaries, Route Handlers, metadata APIs, and caching controls.

For new projects, answer App Router questions with `app/` concepts first. Mention the Pages Router only when comparing older APIs such as `getStaticProps` or `getServerSideProps`.

### 3. How does file-system routing work?

In the App Router, folders define route segments. A segment becomes publicly routable when it has a `page.tsx` file.

```text
app/
  page.tsx
  products/
    page.tsx
    [id]/
      page.tsx
```

This creates `/`, `/products`, and `/products/:id`.

### 4. What is the difference between `page.tsx` and `layout.tsx`?

`page.tsx` renders the UI for a route. `layout.tsx` wraps a route segment and its children. Layouts are useful for shared navigation, sidebars, shells, and providers that should persist across navigation.

Use a page for route-specific content. Use a layout for shared structure.

### 5. What types of routes does Next.js App Router support, and when would you use each type?

Next.js App Router supports several types of routing based on the file system.

- **Static routes** are used for fixed pages such as `/about` or `/contact`.
- **Nested routes** organize pages into hierarchical URL structures, such as `/blog/tutorials`.
- **Dynamic routes**, using folders like `[slug]`, are useful for pages with variable segments, such as `/products/[id]`.
- **Catch-all routes**, using `[...slug]`, match multiple URL segments. They are useful for documentation systems or nested categories.
- **Route groups**, using `(group)`, help organize routes and share layouts without affecting the URL.

```text
app/
  about/page.tsx                 # Static: /about
  blog/tutorials/page.tsx        # Nested: /blog/tutorials
  products/[id]/page.tsx        # Dynamic: /products/:id
  docs/[...slug]/page.tsx       # Catch-all: /docs/a/b
  (shop)/cart/page.tsx           # Route group: /cart
```

In a real-world application, I typically combine these routing patterns. For example, in an e-commerce application, I use static routes for informational pages, dynamic routes for product details, and nested routes for product categories.

I also use layouts to share UI across related pages and loading or error files to improve the user experience during navigation. For dynamic pages, `params` may be treated asynchronously in current App Router versions, and a missing resource should still call `notFound()`.

## Project Structure

### 1. Can you explain the Next.js project structure and the purpose of its main folders and files?

In Next.js, the project structure helps organize routes, UI components, and application logic.

The `app` folder is the core of the App Router. It contains files like `page.tsx` for rendering pages, `layout.tsx` for shared UI, `loading.tsx` for loading states, and `route.ts` for API endpoints.

The `components` folder contains reusable UI components, while the `lib` folder contains shared logic, such as API clients and data-fetching functions.

The `public` folder stores static assets like images and icons. `next.config.ts` is used to configure Next.js, and `tsconfig.json` defines TypeScript settings.

In a real project, I usually organize these folders based on their responsibilities to keep the code maintainable and scalable.

### 2. When would you use a feature-based structure in Next.js?

I would use a feature-based structure when an application grows and has multiple independent business features.

For example, in an e-commerce application, I would organize features such as products, cart, and checkout into separate folders, each containing its own components, hooks, API functions, and types.

This makes the code easier to maintain, test, and scale. However, for a small project, I would prefer a simpler structure to avoid unnecessary complexity.

## Server and Client Components

### 1. What are Server Components?

Server Components render on the server and do not ship their component code to the browser. They are useful for reading server-only data, calling databases, using secrets, rendering static content, and reducing client JavaScript.

They cannot use browser-only APIs, event handlers, or client hooks such as `useState`.

### 2. What are Client Components?

Client Components run in the browser. Add `"use client"` at the top of the file to create a client boundary.

Use Client Components for click handlers, local state, effects, browser APIs, focus behavior, and interactive widgets.

### 3. When should you use `"use client"`?

Use `"use client"` only for the component subtree that needs browser interactivity. A product page can be a Server Component while an `AddToCartButton` inside it is a Client Component.

The common mistake is marking the entire route as client-rendered because one button needs `onClick`.

### 4. Can Server Components render Client Components?

Yes. A Server Component can import and render a Client Component, passing serializable props. This is the normal pattern for mixing server-rendered content with small interactive islands.

A Client Component should not directly import a Server Component. Instead, pass server-rendered children from a server parent when needed.

### 5. What is hydration?

Hydration is the process where React attaches client-side behavior to server-rendered HTML. Hydration warnings happen when the initial client render does not match the HTML produced on the server.

Common causes include rendering `Date.now()`, `Math.random()`, locale-dependent text, or `localStorage`-dependent values during the first render.

## Routing, Metadata, and Error Handling

### 1. How do you handle a 404 in the App Router?

Use `notFound()` when route data does not exist, and define a `not-found.tsx` file when the route needs custom not-found UI.

Do not silently render an empty page for a missing product. A missing resource is a route-level state.

### 2. How do redirects work?

Use `redirect()` when server-side route logic determines the user should go elsewhere, such as after an auth check or missing required setup.

Client-side navigation is still useful for user-initiated interactions, but protected content should not flash before a redirect.

### 3. How do you handle metadata and SEO in Next.js App Router?

I use the Metadata API in Next.js to manage SEO metadata. For static pages, I define a `metadata` object, and for dynamic pages, such as blog posts or product pages, I use `generateMetadata()` to generate titles and descriptions based on the page data.

I also configure `metadataBase`, title templates, Open Graph images, and canonical URLs to improve SEO and social media previews. Additionally, I make sure pages that shouldn't appear in search results use the appropriate `robots` configuration.

For example:

```tsx
import type { Metadata } from "next";

export async function generateMetadata({
  params,
}: {
  params: Promise<{ slug: string }>;
}): Promise<Metadata> {
  const { slug } = await params;
  const post = await getPost(slug);

  if (!post) {
    return {
      title: "Post Not Found",
      robots: { index: false, follow: false },
    };
  }

  return {
    title: post.title,
    description: post.description,
    alternates: {
      canonical: `/blog/${slug}`,
    },
    openGraph: {
      title: post.title,
      description: post.description,
      images: [post.ogImage],
    },
  };
}
```

This approach keeps metadata consistent, supports dynamic content, and helps search engines and social platforms understand each page.

### 4. How do you implement a sitemap in Next.js, and why is it important for SEO?

I implement a sitemap in Next.js using `app/sitemap.ts`, which automatically generates a `sitemap.xml` file for search engines.

For a dynamic website, such as an e-commerce platform, I fetch product, category, and blog URLs from the database and return them using the `MetadataRoute.Sitemap` type. I also include accurate `lastModified` dates to help search engines understand when content was updated.

For multilingual websites, I use `alternates.languages` to define relationships between localized URLs.

```ts
import type { MetadataRoute } from "next";

export default async function sitemap(): Promise<MetadataRoute.Sitemap> {
  const products = await getProducts();

  return [
    {
      url: "https://example.com",
      lastModified: new Date(),
    },
    ...products.map((product) => ({
      url: `https://example.com/products/${product.slug}`,
      lastModified: product.updatedAt,
    })),
  ];
}
```

A sitemap helps search engines discover important pages more efficiently, but it doesn't guarantee that those pages will be indexed.

### 5. How do you implement JSON-LD structured data in Next.js, and how does it improve SEO?

I implement JSON-LD in Next.js using the `<script type="application/ld+json">` element to provide structured data based on the page content.

For example, on an e-commerce website, I use the Product schema to describe product information such as its name, description, image, price, and availability. I also use schemas like Organization, WebSite, and BreadcrumbList where appropriate.

In the Next.js App Router, I typically generate the JSON-LD dynamically from the same data used to render the page, ensuring that the structured data stays consistent with the actual content.

```tsx
export default async function ProductPage({
  params,
}: {
  params: Promise<{ slug: string }>;
}) {
  const { slug } = await params;
  const product = await getProduct(slug);

  const jsonLd = {
    "@context": "https://schema.org",
    "@type": "Product",
    name: product.name,
    description: product.description,
    image: product.image,
    offers: {
      "@type": "Offer",
      price: product.price,
      priceCurrency: "USD",
      availability: "https://schema.org/InStock",
    },
  };

  return (
    <>
      <script
        type="application/ld+json"
        dangerouslySetInnerHTML={{ __html: JSON.stringify(jsonLd) }}
      />
      <h1>{product.name}</h1>
    </>
  );
}
```

JSON-LD helps search engines understand page content and can make pages eligible for rich results in search results. However, it doesn't guarantee better rankings or rich result display.

I also validate the structured data using Google's Rich Results Test and ensure that the schema follows Google's guidelines.

### 6. What is `loading.tsx`?

`loading.tsx` defines route-level loading UI. It works with Suspense boundaries so the user can see an immediate loading state while route content is prepared.

A good answer mentions the user experience: a slow product page needs a stable loading layout, not a blank screen.

### 7. What is the difference between `error.tsx`, `global-error.tsx`, and `notFound()` in Next.js App Router, and when would you use each?

In the Next.js App Router, I use them for different types of errors.

- `error.tsx` is a route-level error boundary. It catches unexpected errors in a route segment and displays a fallback UI with an option to retry. It must be a Client Component.
- `global-error.tsx` handles errors in the root `app/layout.tsx` that the normal `app/error.tsx` boundary cannot catch. It replaces the root layout, so it must define its own `<html>` and `<body>` elements.
- `notFound()` handles missing resources, such as a product that doesn't exist. It renders the nearest `not-found.tsx` UI and signals a 404 response.

For example, in an e-commerce project, I would use `notFound()` when a plant doesn't exist, `error.tsx` when loading the dashboard fails unexpectedly, and `global-error.tsx` when the root layout crashes.

My general rule is to handle expected errors explicitly and use error boundaries to recover from unexpected errors.

### 8. What is `proxy.ts` in Next.js 16, and what are its common use cases?

In Next.js 16, `proxy.ts` runs code before a request is completed, allowing us to inspect requests and control how they are handled.

Common use cases include redirecting users, rewriting URLs, modifying request or response headers, checking cookies, and handling localization.

For example, we can redirect unauthenticated users from `/admin` to `/admin/login`. However, Proxy should not replace backend authentication and authorization, because checking for a cookie alone does not verify that the user is authorized.

### 9. How do you handle multiple languages in a Next.js application?

I use `next-intl` to handle multiple languages in a Next.js application. I configure supported locales, set a default language, and use locale-based routing with the App Router.

I organize translation files by feature or component, such as `home.json`, `plants.json`, and `checkout.json`, with separate files for each language.

For Server Components, I use `getTranslations()`, while Client Components use `useTranslations()`. I also use `proxy.ts` to handle locale routing and validate supported locales.

This approach keeps translations organized, makes the application easier to maintain, and allows me to add new languages without significantly changing the existing architecture.

## Rendering and Caching

### 1. Can you explain the differences between SSG, SSR, ISR, and CSR in Next.js, and how would you choose the right rendering strategy for a real-world application?

Next.js supports several rendering strategies, and I choose one based on how frequently the data changes, SEO requirements, and user interactions.

- **SSG (Static Site Generation):** Pages are generated ahead of time and served as static HTML. I use it for blog posts, documentation, and landing pages where content doesn't change frequently.

- **SSR (Server-Side Rendering):** Pages are rendered on the server for each request when fresh or request-specific data is needed. It's useful for personalized pages or content that must reflect the latest data.

- **ISR (Incremental Static Regeneration):** Pages are statically generated and can be revalidated in the background or on demand. I use it for product pages or blogs where content changes periodically but doesn't need to be regenerated on every request.

- **CSR (Client-Side Rendering):** Data fetching and UI updates happen in the browser. I use it for interactive dashboards, admin interfaces, and features that rely heavily on client-side state.

In a real-world e-commerce application, I might use static rendering with revalidation for product pages, server-side rendering when content depends on request-specific information, and client-side rendering for interactive cart components.

With the Next.js App Router, these approaches can coexist within the same application. I choose the strategy for each page or component based on its requirements rather than using one strategy everywhere. In newer projects, you may also hear about Cache Components; the product-level decision is still which parts may be reused, which parts are request-specific, and where Suspense should show a loading state while uncached data resolves.

### 2. What is `generateStaticParams()`?

`generateStaticParams()` returns params for dynamic routes that should be generated at build time.

Use it for known blog slugs, documentation pages, marketing pages, or product pages where the catalog is known and build-time generation is reasonable.

### 3. How does caching work with `fetch()`?

Next.js extends server-side `fetch()` with persistent caching and revalidation controls. Defaults have changed across recent versions and can also depend on project configuration, so avoid giving a memorized default as if it were universal. Interviewers usually care more about whether you make freshness explicit for important data.

For example, product copy can be cached longer than stock status. A dashboard for the signed-in user should not share cached private data across users.

Useful answer pattern:

- **Public and slow-changing:** opt into caching and revalidate on a schedule or event.
- **User-specific:** fetch per request or use private caching where the framework supports it.
- **Security-sensitive:** never share a cached response across users unless the cache key and privacy boundary are explicit.

### 4. What is revalidation?

Revalidation updates cached data after time passes or after an event. Time-based revalidation is useful for data that can be a little stale. On-demand revalidation is useful after a CMS publish, catalog update, or admin action.

Name the freshness requirement before choosing a revalidation strategy.

### 5. How do you avoid stale search results?

Search routes often depend on query params, user input, ranking, and freshness. Avoid treating every possible search query as a prebuilt static page.

Depending on SEO and interactivity needs, render results on the server, fetch them on the client, or combine a server-rendered shell with client-side refinements.

## Data, Mutations, and APIs

### 1. What are Route Handlers?

Route Handlers let you define server endpoints inside the App Router, commonly with `route.ts`. Use them for API endpoints, webhooks, server-side data access, and integrations that should not expose secrets to the browser.

### 2. Where should secrets live?

Secrets should stay on the server: Server Components, Server Functions, Route Handlers, or other server-only code. Do not expose private API keys through Client Components or public environment variables.

### 3. What are Server Functions?

Server Functions run on the server and can be called from application code for mutations or server-side work. In interviews, explain why the server boundary matters: validation, authorization, secret access, and trusted writes belong on the server.

### 4. How do you use Zod to validate form data at runtime, and what is the difference between `parse()` and `safeParse()`?

I use Zod to validate data at runtime because TypeScript only checks types during development and cannot guarantee that data from forms or APIs is valid.

First, I define a schema with validation rules, such as required fields, minimum lengths, and format checks. Then, I use `safeParse()` to validate the input. If validation fails, I display errors to the user. If it succeeds, I use the validated data to submit the request.

```ts
import { z } from "zod";

const checkoutSchema = z.object({
  name: z.string().trim().min(2),
  phone: z.string().regex(/^0\d{9}$/),
});

type CheckoutForm = z.infer<typeof checkoutSchema>;

const result = checkoutSchema.safeParse(formData);

if (!result.success) {
  console.error(result.error.issues);
} else {
  await createOrder(result.data);
}
```

The main difference is that `parse()` throws a `ZodError` when validation fails, while `safeParse()` returns a result object that lets me handle success and failure explicitly without using `try/catch`.

I also use `z.infer` to derive TypeScript types from schemas, avoiding duplicated type definitions. In production, I validate on both the frontend and backend: frontend validation improves UX, while backend validation ensures invalid data cannot bypass business rules.

### 5. How do you handle authentication?

Read auth state from trusted server-side signals such as cookies or headers. Redirect unauthenticated users before rendering protected UI when the server has enough information.

```tsx
// app/dashboard/page.tsx
import { cookies } from "next/headers";
import { redirect } from "next/navigation";

export default async function DashboardPage() {
  const cookieStore = await cookies();
  const token = cookieStore.get("session")?.value;

  if (!token) {
    redirect("/login");
  }

  const user = await getUser(token);
  return <h1>Welcome, {user.name}</h1>;
}
```

For broad route gates, Next.js docs now use the term Proxy for pre-route logic. Some teams may still say Middleware because older versions and codebases used that term.

Do not put all authorization logic only in Proxy. It is useful for early routing decisions, but data access and mutations still need server-side authorization at the point where protected data is read or changed.

### 6. How do you implement JWT authentication in a Next.js application with a FastAPI backend?

I implement JWT authentication using short-lived access tokens and longer-lived refresh tokens stored in HttpOnly, Secure, and SameSite cookies.

In Next.js, I use `proxy.ts` to check for authentication cookies and protect admin routes. However, checking whether a cookie exists does not guarantee that the token is valid, so I call `/auth/me` to verify the current admin with the FastAPI backend.

When an API request returns `401 Unauthorized`, the API client attempts to refresh the access token. If the refresh succeeds, it retries the original request. Otherwise, it clears the authentication state and redirects the user to the login page.

For security, I avoid storing JWTs in `localStorage`, validate tokens on the backend, and protect cookie-based authentication endpoints against CSRF where necessary.

Protect admin routes with `proxy.ts`:

```ts
import { NextRequest, NextResponse } from "next/server";

export function proxy(request: NextRequest) {
  const accessToken = request.cookies.get("gg_access_token");
  const refreshToken = request.cookies.get("gg_refresh_token");

  if (!accessToken && !refreshToken) {
    return NextResponse.redirect(
      new URL("/admin/login", request.url)
    );
  }

  return NextResponse.next();
}

export const config = {
  matcher: ["/admin/:path*"],
};
```

This provides a basic route guard. It checks cookie presence, not JWT validity. The FastAPI backend must still validate authentication and authorization.

Handle token refresh in the API client:

```ts
let refreshPromise: Promise<boolean> | null = null;

async function refreshAccessToken(): Promise<boolean> {
  const response = await fetch(
    `${process.env.NEXT_PUBLIC_API_URL}/auth/refresh`,
    {
      method: "POST",
      credentials: "include",
    }
  );

  return response.ok;
}

export async function apiFetch(
  url: string,
  options: RequestInit = {}
) {
  const request = () =>
    fetch(url, {
      ...options,
      credentials: "include",
    });

  let response = await request();

  if (response.status !== 401) {
    return response;
  }

  refreshPromise ??= refreshAccessToken().finally(() => {
    refreshPromise = null;
  });

  const refreshed = await refreshPromise;

  if (!refreshed) {
    window.location.assign("/admin/login");
    return response;
  }

  return request();
}
```

The shared promise prevents multiple simultaneous requests from unnecessarily triggering separate refresh calls within the same browser context.

Key points:

- **HttpOnly cookies:** Prevent JavaScript from directly reading authentication tokens, reducing token theft through XSS.
- **Proxy:** Provides early route protection but is not a substitute for backend authorization.
- **Refresh token:** Allows the user to continue working after the access token expires.
- **Concurrency:** Avoid duplicate refresh requests when several API calls fail simultaneously.
- **Security:** Use HTTPS, appropriate cookie settings, CSRF protection, token expiry, and refresh-token rotation or revocation where appropriate.

### 7. What are the differences between cookies, `localStorage`, and `sessionStorage`, and when would you use each one?

Cookies, `localStorage`, and `sessionStorage` store data in the browser, but they have different purposes.

- **Cookies:** I use HttpOnly cookies to store authentication tokens because JavaScript cannot access them directly, reducing the risk of token theft through XSS. Cookies are automatically sent with matching HTTP requests.
- **`localStorage`:** I use it to store persistent, non-sensitive client-side data, such as theme preferences. The data remains after the browser is closed.
- **`sessionStorage`:** I use it for temporary data, such as a checkout step or form progress. The data is scoped to a browser tab and generally cleared when that tab session ends.

```ts
// Persist a theme preference
localStorage.setItem("theme", "dark");

// Store temporary checkout progress
sessionStorage.setItem("checkoutStep", "2");

// Set a basic cookie
document.cookie = "language=en; path=/; SameSite=Lax";
```

### 8. How do fetching, mutating, caching, and revalidating data work together, and when would you use `updateTag()`, `revalidateTag()`, or `revalidatePath()`?

In the Next.js App Router, fetching retrieves data from an API or database, mutating changes the data, caching stores the result to avoid unnecessary requests, and revalidating updates stale cached data after a mutation.

For example, when an admin creates a new plant, we save it to the database and then revalidate the cache so the storefront can display the updated data.

```tsx
// Fetch and tag the cached result
const plants = await fetch("https://api.example.com/plants", {
  next: { tags: ["plants"] },
}).then((res) => res.json());
```

```tsx
// app/actions.ts
"use server";

import { updateTag, revalidateTag, revalidatePath } from "next/cache";

export async function createPlant(formData: FormData) {
  await db.plant.create({ data: { name: String(formData.get("name")) } });

  updateTag("plants");              // Immediate: read-your-own-writes
  // revalidateTag("plants", "max"); // Stale-while-revalidate for public content
  // revalidatePath("/plants");      // Revalidate a specific route
}
```

Next.js provides three main APIs for revalidation:

- `updateTag()` immediately expires tagged cache entries. It's useful in Server Actions when users need to see their own changes immediately.
- `revalidateTag()` revalidates cached data by tag. With the `"max"` profile, Next.js uses stale-while-revalidate, which is suitable for public content that doesn't need to update immediately.
- `revalidatePath()` revalidates a specific route, such as `/plants`, rather than targeting data through a tag.

I choose the approach based on the use case. For example, in an e-commerce application, I'd use `updateTag()` after an admin updates a product when immediate consistency is important, and `revalidateTag()` for public catalog data where serving stale content briefly is acceptable.

### 9. How does TanStack Query (React Query) manage server state, and how do you handle caching, loading and error states, and cache invalidation after a mutation?

TanStack Query, formerly known as React Query, is a library for managing server state in React applications. It simplifies data fetching, caching, synchronization, and error handling.

I typically use `useQuery` to fetch data and `useMutation` to create, update, or delete data. React Query automatically manages loading, success, and error states, so I don't need to implement them manually.

For caching, I use `queryKey` to identify each query. When the parameters change, React Query can fetch the corresponding data and reuse cached results when appropriate.

After a successful mutation, I use `invalidateQueries()` to mark related queries as stale and refetch active queries. For example, after creating a product, I invalidate the product list so the UI displays the latest data.

I also use features like `keepPreviousData` to prevent the UI from flickering during pagination and `AbortSignal` to cancel unnecessary requests.

Overall, TanStack Query helps me manage server state efficiently, reduce unnecessary API calls, and keep the UI synchronized with the backend.

### 10. Why would you choose Zustand over Redux for client-side state management?

I would choose Zustand when I need lightweight shared client-side state with minimal boilerplate. Zustand doesn't require actions, reducers, dispatchers, or a Provider. I can define state and actions directly in a store and use selectors to subscribe to only the data a component needs.

For example, I might use Zustand for a shopping cart, UI preferences, or authentication-related client state. However, I wouldn't use it for server state by default. For API data such as products or orders, I would typically use React Query because it provides caching, synchronization, refetching, and mutation management out of the box.

So my decision is usually: Zustand for shared client state, React Query for server state, and `useState` for local component state.

### 11. How do you handle global state in a Next.js application using Zustand?

I usually handle global client-side state in a Next.js application with Zustand.

I create a centralized store that contains the state and actions, then use selectors in Client Components to access only the data they need.

For example, for an e-commerce application, I might use Zustand to manage the shopping cart:

```ts
const useCartStore = create<CartStore>((set) => ({
  items: [],

  addItem: (item) =>
    set((state) => ({
      items: [...state.items, item],
    })),

  clearCart: () => set({ items: [] }),
}));
```

Then a Client Component can subscribe to the store:

```tsx
"use client";

const items = useCartStore((state) => state.items);
```

I also use Zustand middleware such as `persist` when the state needs to survive page refreshes.

In Next.js, I keep the responsibility clear: Zustand for shared client state, while server data is usually handled by Server Components or React Query. This keeps the application state predictable and avoids putting everything into one global store.

## Performance and Deployment

### 1. How do you reduce client JavaScript?

Keep non-interactive UI as Server Components, put `"use client"` at small boundaries, avoid importing large browser-only libraries into shared parents, and measure bundle output before optimizing blindly.

### 2. How do images work in Next.js?

I use the `next/image` component to optimize images, serve responsive image sizes, and enable lazy loading by default.

To prevent layout shifts, I specify `width` and `height`, or use `fill` inside a container with a predefined aspect ratio.

For important above-the-fold images, such as hero images, I may use `fetchPriority="high"` to improve LCP. I also configure `remotePatterns` for remote images and use Lighthouse to measure performance improvements.

### 3. How do fonts work?

I use `next/font` to optimize font loading and self-host Google Fonts, which reduces external network requests.

I usually define the primary font in the root layout to apply it consistently across the application. I also use variable fonts when appropriate and choose compatible fallback fonts to minimize layout shifts when the custom font loads.

Finally, I use Lighthouse and Chrome DevTools to identify and measure font-related layout shifts.

### 4. How do you debug a slow route?

Split the problem:

- Is the server slow to fetch data?
- Is the page waiting on unnecessary blocking data?
- Is too much JavaScript sent to the browser?
- Is hydration expensive?
- Is an image hurting LCP?
- Is caching disabled by accident?

Then measure with framework build output, browser DevTools, server logs, and Web Vitals.

### 5. What changes between local development and production?

Development mode optimizes feedback for engineers. Production builds optimize output for users. Caching, bundling, minification, image behavior, and deployment environment can differ.

If a bug appears only in production, check environment variables, build-time assumptions, server/runtime differences, and caching.

## Senior Next.js Questions

### 1. How would you design a product detail route?

Use a Server Component page for product data and SEO. Generate metadata from product data. Return `notFound()` for missing products. Keep interactive parts such as cart controls, variant selectors, and wishlist buttons in small Client Components. Make freshness explicit for price and inventory.

### 2. How would you design an authenticated dashboard?

Check auth before rendering protected UI. Fetch user-specific data on the server with request-aware credentials. Avoid sharing cached private responses. Split slow widgets with Suspense when possible. Keep URL state for filters that users expect to share or revisit.

### 3. How would you migrate from Pages Router to App Router?

Do not rewrite everything at once. Migrate route by route, learn the new data and rendering model, replace `getStaticProps` and `getServerSideProps` with App Router patterns, move shared shells into layouts, and identify Client Component boundaries.

The biggest migration risk is carrying old mental models into Server Components and caching.

Good migration answers also mention compatibility work: routes may coexist during migration, shared components may need `"use client"` boundaries, API routes may move to Route Handlers only when there is a reason, and tests should cover redirects, metadata, and not-found behavior before and after the move.

### 4. How do you prevent hydration mismatches?

Make the first client render match the server HTML. Avoid browser-only reads during render. Move browser-only logic into effects, use cookies when the server needs the value, or render a deliberate client boundary for values that cannot be known on the server.

### 5. How do you choose between server and client fetching?

Use server fetching when data improves SEO, uses secrets, depends on trusted auth, or should avoid extra client waterfalls. Use client fetching for highly interactive data, browser-only context, live updates, or user actions after initial render.

The answer should include the UI states either way.

### 6. How do you handle partial failures?

Do not let one optional widget break an entire page. Use route error boundaries for route-level failures, local error UI for widget-level failures, and server-side validation for expected missing data.

Name which failures are fatal and which can degrade.

### 7. How do you keep a route maintainable?

Separate route concerns: data loading, metadata, UI composition, interactive client widgets, mutation boundaries, and error states. Avoid making `page.tsx` a long file that owns every detail.

### 8. How do you test a Next.js app?

Test pure utilities with unit tests, components with user-focused component tests, and critical flows with E2E tests. For framework-specific behavior such as redirects, route handlers, and server boundaries, test at the route or integration level where possible.

### 9. How do you use Playwright to test a complete user flow in a Next.js application?

I use Playwright for end-to-end testing to verify that critical user flows work correctly from start to finish. For example, in a Next.js e-commerce application, I test the checkout flow, including browsing products, adding items to the cart, and placing an order.

I use locators to interact with elements and assertions to verify expected behavior. For example:

```ts
import { test, expect } from "@playwright/test";

test("completes a checkout flow", async ({ page }) => {
  await page.goto("/vi/plants");

  await page.getByTestId("add-to-cart").click();
  await page.getByTestId("cart-checkout").click();

  await expect(page).toHaveURL(/\/vi\/checkout\/?$/);

  await page.locator("#checkout-name").fill("Test Customer");
  await page.locator("#checkout-phone").fill("0901234567");
  await page.locator("#checkout-address").fill("123 Test Street");

  await page.getByTestId("place-order").click();

  await expect(page).toHaveURL(/\/vi\/order-success\/?$/);
  await expect(
    page.getByRole("heading", { name: "Đặt hàng thành công!" })
  ).toBeVisible();
});
```

Playwright automatically waits for elements and assertions, which helps reduce flaky tests. I also use `test.step()` to organize complex flows and traces or screenshots to debug failures.

Finally, I run E2E tests against a dedicated test environment and keep them independent to ensure reliable results in CI/CD pipelines.

### 10. How do you review a Next.js PR?

Check whether secrets stay on the server, client boundaries are small, route states are handled, metadata is correct, caching is explicit where freshness matters, and loading/error/not-found states match the product requirement.

### 11. What is a good final interview answer pattern?

Use this structure:

1. Name the route or component boundary.
2. State the rendering and freshness requirement.
3. Choose the server/client split.
4. Name the Next.js file or API.
5. Call out one failure mode.
