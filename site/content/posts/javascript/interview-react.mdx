## Components

### 1. What are React components, and what are the key concepts every React developer should understand?

**Expectations:** Props · State · JSX · Form state · Re-renders · Logic reuse

**Example answer:**

> React components are reusable building blocks of a UI. They accept props, manage state when needed, and return JSX to describe what should be rendered.
>
> Three important concepts are form state management, component re-rendering, and logic reuse.

---

### 2. What is the difference between controlled and uncontrolled components?

**Expectations:** Controlled · Uncontrolled · State · Refs · When to use each

**Example answer:**

> A controlled component has its value managed by React state, while an uncontrolled component stores its current value in the DOM.
>
> Use controlled components when you need validation or dynamic UI updates. Use uncontrolled components for simpler forms or when accessing DOM values directly is sufficient.

```jsx
// Controlled
const [name, setName] = useState("");

<input value={name} onChange={(e) => setName(e.target.value)} />

// Uncontrolled
const nameRef = useRef(null);

<input ref={nameRef} defaultValue="" />
```

---

### 3. When does a React component re-render?

**Expectations:** State · Parent re-render · Context · Render vs DOM update

**Example answer:**

> A component typically re-renders when its state changes, its parent re-renders, or a context value it consumes changes.
>
> A re-render does not necessarily mean the DOM will be updated. React compares the rendered output and applies necessary DOM changes.

---

### 4. How can you prevent unnecessary re-renders?

**Expectations:** `React.memo` · Shallow compare · Not a guarantee

**Example answer:**

> You can use `React.memo` to skip re-rendering a function component when its props have not changed according to the default shallow prop comparison.
>
> However, `React.memo` is a performance optimization, not a guarantee. State changes and context updates can still trigger a re-render.

```jsx
const User = React.memo(function User({ name }) {
  return <div>{name}</div>;
});
```

---

### 5. What is a Higher-Order Component (HOC)?

**Expectations:** Wrapper · Reuse behavior · Custom hooks preferred today

**Example answer:**

> A Higher-Order Component is a function that takes a component and returns an enhanced component, allowing developers to reuse behavior across multiple components.
>
> HOCs were commonly used for logging, authentication, and shared behavior. Today, custom hooks are often preferred when reusing stateful logic because they avoid adding another component layer.

```jsx
function withLogger(WrappedComponent) {
  return function EnhancedComponent(props) {
    console.log("Rendering component");

    return <WrappedComponent {...props} />;
  };
}
```

## Lifecycle

### 1. How does React manage a component's lifecycle and update the UI?

**Expectations:** Trigger · Render · Commit · Effects

**Example answer:**

> React updates the UI through three main phases: Trigger → Render → Commit.
>
> - **Trigger:** An initial render or a state update schedules rendering.
> - **Render:** React calls components to calculate the next UI.
> - **Commit:** React applies the necessary changes to the DOM.
>
> After the commit, Effects run according to their scheduling rules.

---

### 2. What are mount, update, and unmount in React?

**Expectations:** First render · Re-render triggers · Cleanup on remove

**Example answer:**

> - **Mount:** A component is added to the UI for the first time.
> - **Update:** A component renders again due to state, props, context, or its parent's render.
> - **Unmount:** A component is removed from the UI, and its Effect cleanup functions run.

---

### 3. When does `useEffect` run, and why is cleanup important?

**Expectations:** After commit · Dependencies · Event listeners · Strict Mode

**Example answer:**

> `useEffect` runs after a commit when its dependencies have changed. With an empty dependency array (`[]`), it runs on mount, with cleanup when the component unmounts.
>
> Cleanup is important for removing event listeners, clearing timers, and cancelling or disconnecting external resources.
>
> In development, React Strict Mode may run an extra setup-and-cleanup cycle to help detect bugs.

```jsx
useEffect(() => {
  const handleResize = () => console.log(window.innerWidth);

  window.addEventListener("resize", handleResize);

  return () => {
    window.removeEventListener("resize", handleResize);
  };
}, []);
```

---

### 4. What is the difference between `useEffect` and `useLayoutEffect`?

**Expectations:** Paint timing · External systems · Layout measurement

**Example answer:**

> - **`useEffect`:** Used for synchronizing with external systems, such as fetching data or subscribing to events. It generally doesn't block browser painting.
> - **`useLayoutEffect`:** Runs after DOM mutations but before the browser repaints. It's useful for measuring layout or making visual adjustments without flicker.
>
> Prefer `useEffect` by default. Use `useLayoutEffect` when an operation must happen before repainting.

## DOM & Virtual DOM

### 1. What is the Virtual DOM, and how does React update the UI efficiently?

**Expectations:** DOM · Virtual DOM · Render · Reconciliation · Commit

**Example answer:**

> The DOM represents the browser's document structure, while the Virtual DOM is a common term for React's in-memory representation of UI elements.
>
> When state changes, React renders the component, reconciles the new element tree with the previous one, and commits the necessary changes to the real DOM.

---

### 2. What is the difference between the DOM and the Virtual DOM?

**Expectations:** Browser document · In-memory UI · Declarative updates · Not always faster

**Example answer:**

> - **DOM:** The browser's representation of the HTML document, which JavaScript can access and modify.
> - **Virtual DOM:** A lightweight way to describe the UI in JavaScript that React uses to calculate updates.
>
> The Virtual DOM helps React manage UI updates declaratively, but it doesn't guarantee better performance than direct DOM manipulation in every situation.

---

### 3. What is reconciliation in React?

**Expectations:** Element tree diff · Types · Positions · Keys · State preservation

**Example answer:**

> Reconciliation is the process React uses to determine how the UI should change when a new render produces a different element tree.
>
> React compares element types, positions, and keys to determine whether to update existing elements, preserve component state, or replace parts of the tree.

---

### 4. Does React recreate the entire DOM when state changes?

**Expectations:** Minimal mutations · Commit phase · Re-render ≠ DOM change

**Example answer:**

> No. React calculates the necessary changes and applies the relevant DOM mutations during the commit phase.
>
> For example, when a counter changes from `0` to `1`, React can update the text content without recreating the surrounding elements.
>
> Important: A component re-render does not necessarily mean the DOM changes.

---

### 5. Is the Virtual DOM always faster than the real DOM?

**Expectations:** Reconciliation cost · Declarative model · Depends on workload

**Example answer:**

> No. Creating element descriptions and performing reconciliation also have costs.
>
> React's main advantage is its declarative programming model and its ability to coordinate UI updates efficiently. Actual performance depends on component complexity, rendering work, DOM mutations, and browser layout and painting.

## Keys

### 1. Why does React need a `key` when rendering lists?

**Expectations:** Identity across renders · Add/remove/reorder · Stable unique IDs

**Example answer:**

> The `key` prop helps React identify each element across renders. It allows React to determine which items have been added, removed, or reordered, preserving the correct component identity and state.
>
> A stable, unique ID is usually the best choice for a key.

```jsx
{fruits.map((fruit) => (
  <div key={fruit.id}>{fruit.name}</div>
))}
```

---

### 2. What happens if you use an array index as a key?

**Expectations:** Reorder/remove bugs · Wrong state association · Static lists OK

**Example answer:**

> When items are removed or reordered, indexes can change. React may associate existing component instances or DOM elements with different data, potentially causing incorrect UI state.
>
> For example, an uncontrolled input may retain the text entered for the previous item after the first item is removed.
>
> Index keys are not always wrong. They are acceptable for static lists that never change order, have items added or removed, or otherwise change their positions.

---

### 3. Can changing a component's `key` reset its state?

**Expectations:** Remount · Local state reset · Controlled inputs need value update

**Example answer:**

> Yes. Changing the key tells React to treat the component as a different instance. React unmounts the previous instance and mounts a new one, resetting its local state and DOM state.
>
> For controlled inputs, you must also update the state that supplies the input's `value`.

```jsx
<FruitInput key={selectedFruitId} />
```

When `selectedFruitId` changes, React creates a new `FruitInput` instance.

---

### 4. Does React pass `key` to the component as a prop?

**Expectations:** Special prop · Not in `props` · Pass `id` separately

**Example answer:**

> No. `key` is a special React prop and is not available inside the component through `props`.
>
> `key` is used by React for reconciliation, while values like `id` must be passed explicitly if the component needs them.

```jsx
function Fruit({ id, name }) {
  return <div>{id}: {name}</div>;
}

<Fruit key={fruit.id} id={fruit.id} name={fruit.name} />
```

## Error Boundaries

### 1. What are Error Boundaries in React, and why do we need them?

**Expectations:** Catch render errors · Fallback UI · Isolate failures · `react-error-boundary`

**Example answer:**

> Error Boundaries are components that catch errors during rendering in their descendant component tree and display a fallback UI instead of the failed content.
>
> They help isolate UI failures and prevent rendering errors from taking down larger parts of the application.
>
> In modern React applications, we can use the `react-error-boundary` library.

```jsx
import { ErrorBoundary } from "react-error-boundary";

<ErrorBoundary
  fallback={<p>Something went wrong.</p>}
>
  <UserList />
</ErrorBoundary>
```

If `UserList` throws an error during rendering, the fallback UI is displayed.

---

### 2. What errors can Error Boundaries catch?

**Expectations:** Rendering · Not event handlers · Not async/`useEffect` · `showBoundary()`

**Example answer:**

> They catch errors thrown during rendering and other React-managed operations covered by Error Boundary behavior.
>
> However, they do not automatically catch errors from event handlers, asynchronous callbacks, or `useEffect`.
>
> For asynchronous errors, we can forward the error using `showBoundary()` from `react-error-boundary`.

---

### 3. How do you reset an Error Boundary?

**Expectations:** `resetErrorBoundary()` · `resetKeys` · Underlying error still matters

**Example answer:**

> With `react-error-boundary`, we can call `resetErrorBoundary()` from the fallback component to retry rendering.
>
> We can also use `resetKeys` to reset the boundary when relevant values change. When those values change, the boundary resets and attempts to render the updated content. However, the underlying error must still be resolved.

```jsx
<ErrorBoundary
  FallbackComponent={Fallback}
  resetKeys={[userId]}
>
  <UserProfile userId={userId} />
</ErrorBoundary>
```

---

### 4. Should every API error be handled by an Error Boundary?

**Expectations:** Expected vs unexpected · Explicit error states · Retry UI

**Example answer:**

> No. Expected API failures, such as validation errors or failed requests, are usually better handled with explicit loading, error, and retry states.
>
> Error Boundaries are more appropriate for unexpected errors that prevent a component subtree from rendering correctly.

## TypeScript

### 1. How does TypeScript improve code quality, and which features do you use to make applications type-safe?

**Expectations:** Static checking · Unions · Narrowing · Generics · Utility types · `satisfies` · Runtime validation

**Example answer:**

> TypeScript improves code quality by detecting type errors during static checking, making data structures explicit, and enabling safer refactoring. I commonly use union types, type narrowing, generics, utility types, and `satisfies` to build maintainable applications.
>
> However, TypeScript cannot guarantee runtime safety, so external data still needs validation.

---

### 2. What is the difference between `type` and `interface`?

**Expectations:** Declaration merging · Unions · Object shapes · When to use each

**Example answer:**

> Both can describe object shapes. The main differences are that `interface` supports declaration merging, while `type` can represent unions, intersections, primitives, and other type expressions.
>
> I generally use `interface` for extensible object contracts and `type` for unions, utility types, and more complex type compositions. Both are suitable for many object shapes.

```ts
interface User {
  name: string;
}

interface User {
  age: number;
}

// Declaration merging: both properties exist.
const user: User = {
  name: "Viet",
  age: 30,
};

type Status = "loading" | "success" | "error";
```

---

### 3. What is type narrowing?

**Expectations:** Runtime checks · `typeof` · `unknown` vs `any`

**Example answer:**

> Type narrowing allows TypeScript to determine a more specific type from a broader type using runtime checks.
>
> `unknown` is safer than `any` because it requires validation before most operations, whereas `any` disables type checking for the value.

```ts
function printValue(value: string | number) {
  if (typeof value === "string") {
    console.log(value.toUpperCase());
  } else {
    console.log(value.toFixed(2));
  }
}

function handleError(error: unknown) {
  if (error instanceof Error) {
    console.log(error.message);
  }
}
```

---

### 4. What are `keyof` and `typeof` used for?

**Expectations:** Derive types · Avoid duplication · `as const`

**Example answer:**

> `typeof` derives a type from a value, while `keyof` extracts an object's property names as a union.
>
> To avoid duplicating types, I derive them from existing constants or objects instead of maintaining separate definitions.

```ts
const config = {
  apiUrl: "/api",
  timeout: 5000,
};

type Config = typeof config;
type ConfigKey = keyof Config;
// "apiUrl" | "timeout"

const roles = ["admin", "user", "guest"] as const;

type Role = (typeof roles)[number];
// "admin" | "user" | "guest"
```

---

### 5. What are generics, and why are they useful?

**Expectations:** Preserve type info · Reusable · `extends` constraints

**Example answer:**

> Generics allow functions, classes, and types to work with different data types while preserving type information.
>
> I constrain a generic with `extends` when it must satisfy a specific requirement, such as accepting only objects with a string `id`.

```ts
function getFirst<T>(items: T[]): T | undefined {
  return items[0];
}

const first = getFirst([1, 2, 3]);
// number | undefined

function getId<T extends { id: string }>(item: T): string {
  return item.id;
}
```

---

### 6. What are TypeScript utility types?

**Expectations:** `Omit` · `Partial` · `Pick` · `Record`

**Example answer:**

> Utility types transform existing types without requiring you to redefine them.
>
> `Partial<T>` makes every property optional, which is useful for update payloads. `Pick<T, K>` selects specific properties while preserving their original types, which is useful for a compact representation.

```ts
interface User {
  id: number;
  name: string;
  email: string;
}

type CreateUser = Omit<User, "id">;
type UpdateUser = Partial<User>;
type UserPreview = Pick<User, "id" | "name">;
type UserMap = Record<string, User>;
```

---

### 7. What is the difference between `satisfies` and a type annotation?

**Expectations:** Compile-time check · Preserve inference · Not runtime validation

**Example answer:**

> A type annotation checks compatibility but can widen the resulting expression's type. `satisfies` checks compatibility while retaining more of the expression's inferred type.
>
> `satisfies` is a compile-time check only. API responses and other external data still need runtime validation.

```ts
type Color = "red" | "green" | "blue";

const palette = {
  primary: "red",
  secondary: "blue",
} satisfies Record<string, Color>;

palette.primary;
// Inferred as "red"
```

---

### 8. How do you implement exhaustive checks?

**Expectations:** Discriminated unions · `never` · Missing cases

**Example answer:**

> I use discriminated unions and `never` to ensure every case is handled. If I add another union member without handling it, TypeScript reports an error at the exhaustive check, helping me identify the missing case.

```ts
type Result =
  | { status: "success"; data: string }
  | { status: "error"; message: string };

function handleResult(result: Result): string {
  switch (result.status) {
    case "success":
      return result.data;

    case "error":
      return result.message;

    default: {
      const exhaustiveCheck: never = result;
      return exhaustiveCheck;
    }
  }
}
```

---

### 9. Does TypeScript prevent all runtime errors?

**Expectations:** Types erased · External data · Zod · `unknown`

**Example answer:**

> No. TypeScript checks types statically, but types are erased at runtime. It cannot automatically guarantee that external data matches a declared type or that business logic is correct.
>
> To make this safer, I treat parsed data as `unknown` and validate it with runtime checks or a schema validation library such as Zod before using it.

```ts
type User = { name: string };

const user: User = JSON.parse('{"age": 30}');

console.log(user.name.toUpperCase());
// Runtime error: user.name is undefined
```
