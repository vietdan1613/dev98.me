## Components

### 1. What are React components, and what are the key concepts every React developer should understand?

**Expectations:** Props · State · JSX · Form state · Re-renders · Logic reuse

**Example answer:**

> React components are reusable building blocks of a UI. They accept props, manage state when needed, and return JSX to describe what should be rendered.
>
> Three important concepts are form state management, component re-rendering, and logic reuse.

---

### 2. What is the difference between controlled and uncontrolled components?

**Expectations:** Controlled · Uncontrolled · State · Refs · When to use each

**Example answer:**

> A controlled component has its value managed by React state, while an uncontrolled component stores its current value in the DOM.
>
> Use controlled components when you need validation or dynamic UI updates. Use uncontrolled components for simpler forms or when accessing DOM values directly is sufficient.

```jsx
// Controlled
const [name, setName] = useState("");

<input value={name} onChange={(e) => setName(e.target.value)} />

// Uncontrolled
const nameRef = useRef(null);

<input ref={nameRef} defaultValue="" />
```

---

### 3. When does a React component re-render?

**Expectations:** State · Parent re-render · Context · Render vs DOM update

**Example answer:**

> A component typically re-renders when its state changes, its parent re-renders, or a context value it consumes changes.
>
> A re-render does not necessarily mean the DOM will be updated. React compares the rendered output and applies necessary DOM changes.

---

### 4. How can you prevent unnecessary re-renders?

**Expectations:** `React.memo` · Shallow compare · Not a guarantee

**Example answer:**

> You can use `React.memo` to skip re-rendering a function component when its props have not changed according to the default shallow prop comparison.
>
> However, `React.memo` is a performance optimization, not a guarantee. State changes and context updates can still trigger a re-render.

```jsx
const User = React.memo(function User({ name }) {
  return <div>{name}</div>;
});
```

---

### 5. What is a Higher-Order Component (HOC)?

**Expectations:** Wrapper · Reuse behavior · Custom hooks preferred today

**Example answer:**

> A Higher-Order Component is a function that takes a component and returns an enhanced component, allowing developers to reuse behavior across multiple components.
>
> HOCs were commonly used for logging, authentication, and shared behavior. Today, custom hooks are often preferred when reusing stateful logic because they avoid adding another component layer.

```jsx
function withLogger(WrappedComponent) {
  return function EnhancedComponent(props) {
    console.log("Rendering component");

    return <WrappedComponent {...props} />;
  };
}
```

## Lifecycle

### 1. How does React manage a component's lifecycle and update the UI?

**Expectations:** Trigger · Render · Commit · Effects

**Example answer:**

> React updates the UI through three main phases: Trigger → Render → Commit.
>
> - **Trigger:** An initial render or a state update schedules rendering.
> - **Render:** React calls components to calculate the next UI.
> - **Commit:** React applies the necessary changes to the DOM.
>
> After the commit, Effects run according to their scheduling rules.

---

### 2. What are mount, update, and unmount in React?

**Expectations:** First render · Re-render triggers · Cleanup on remove

**Example answer:**

> - **Mount:** A component is added to the UI for the first time.
> - **Update:** A component renders again due to state, props, context, or its parent's render.
> - **Unmount:** A component is removed from the UI, and its Effect cleanup functions run.

---

### 3. When does `useEffect` run, and why is cleanup important?

**Expectations:** After commit · Dependencies · Event listeners · Strict Mode

**Example answer:**

> `useEffect` runs after a commit when its dependencies have changed. With an empty dependency array (`[]`), it runs on mount, with cleanup when the component unmounts.
>
> Cleanup is important for removing event listeners, clearing timers, and cancelling or disconnecting external resources.
>
> In development, React Strict Mode may run an extra setup-and-cleanup cycle to help detect bugs.

```jsx
useEffect(() => {
  const handleResize = () => console.log(window.innerWidth);

  window.addEventListener("resize", handleResize);

  return () => {
    window.removeEventListener("resize", handleResize);
  };
}, []);
```

---

### 4. What is the difference between `useEffect` and `useLayoutEffect`?

**Expectations:** Paint timing · External systems · Layout measurement

**Example answer:**

> - **`useEffect`:** Used for synchronizing with external systems, such as fetching data or subscribing to events. It generally doesn't block browser painting.
> - **`useLayoutEffect`:** Runs after DOM mutations but before the browser repaints. It's useful for measuring layout or making visual adjustments without flicker.
>
> Prefer `useEffect` by default. Use `useLayoutEffect` when an operation must happen before repainting.

## DOM & Virtual DOM

### 1. What is the Virtual DOM, and how does React update the UI efficiently?

**Expectations:** DOM · Virtual DOM · Render · Reconciliation · Commit

**Example answer:**

> The DOM represents the browser's document structure, while the Virtual DOM is a common term for React's in-memory representation of UI elements.
>
> When state changes, React renders the component, reconciles the new element tree with the previous one, and commits the necessary changes to the real DOM.

---

### 2. What is the difference between the DOM and the Virtual DOM?

**Expectations:** Browser document · In-memory UI · Declarative updates · Not always faster

**Example answer:**

> - **DOM:** The browser's representation of the HTML document, which JavaScript can access and modify.
> - **Virtual DOM:** A lightweight way to describe the UI in JavaScript that React uses to calculate updates.
>
> The Virtual DOM helps React manage UI updates declaratively, but it doesn't guarantee better performance than direct DOM manipulation in every situation.

---

### 3. What is reconciliation in React?

**Expectations:** Element tree diff · Types · Positions · Keys · State preservation

**Example answer:**

> Reconciliation is the process React uses to determine how the UI should change when a new render produces a different element tree.
>
> React compares element types, positions, and keys to determine whether to update existing elements, preserve component state, or replace parts of the tree.

---

### 4. Does React recreate the entire DOM when state changes?

**Expectations:** Minimal mutations · Commit phase · Re-render ≠ DOM change

**Example answer:**

> No. React calculates the necessary changes and applies the relevant DOM mutations during the commit phase.
>
> For example, when a counter changes from `0` to `1`, React can update the text content without recreating the surrounding elements.
>
> Important: A component re-render does not necessarily mean the DOM changes.

---

### 5. Is the Virtual DOM always faster than the real DOM?

**Expectations:** Reconciliation cost · Declarative model · Depends on workload

**Example answer:**

> No. Creating element descriptions and performing reconciliation also have costs.
>
> React's main advantage is its declarative programming model and its ability to coordinate UI updates efficiently. Actual performance depends on component complexity, rendering work, DOM mutations, and browser layout and painting.

## Keys

### 1. Why does React need a `key` when rendering lists?

**Expectations:** Identity across renders · Add/remove/reorder · Stable unique IDs

**Example answer:**

> The `key` prop helps React identify each element across renders. It allows React to determine which items have been added, removed, or reordered, preserving the correct component identity and state.
>
> A stable, unique ID is usually the best choice for a key.

```jsx
{fruits.map((fruit) => (
  <div key={fruit.id}>{fruit.name}</div>
))}
```

---

### 2. What happens if you use an array index as a key?

**Expectations:** Reorder/remove bugs · Wrong state association · Static lists OK

**Example answer:**

> When items are removed or reordered, indexes can change. React may associate existing component instances or DOM elements with different data, potentially causing incorrect UI state.
>
> For example, an uncontrolled input may retain the text entered for the previous item after the first item is removed.
>
> Index keys are not always wrong. They are acceptable for static lists that never change order, have items added or removed, or otherwise change their positions.

---

### 3. Can changing a component's `key` reset its state?

**Expectations:** Remount · Local state reset · Controlled inputs need value update

**Example answer:**

> Yes. Changing the key tells React to treat the component as a different instance. React unmounts the previous instance and mounts a new one, resetting its local state and DOM state.
>
> For controlled inputs, you must also update the state that supplies the input's `value`.

```jsx
<FruitInput key={selectedFruitId} />
```

When `selectedFruitId` changes, React creates a new `FruitInput` instance.

---

### 4. Does React pass `key` to the component as a prop?

**Expectations:** Special prop · Not in `props` · Pass `id` separately

**Example answer:**

> No. `key` is a special React prop and is not available inside the component through `props`.
>
> `key` is used by React for reconciliation, while values like `id` must be passed explicitly if the component needs them.

```jsx
function Fruit({ id, name }) {
  return <div>{id}: {name}</div>;
}

<Fruit key={fruit.id} id={fruit.id} name={fruit.name} />
```

## Error Boundaries

### 1. What are Error Boundaries in React, and why do we need them?

**Expectations:** Catch render errors · Fallback UI · Isolate failures · `react-error-boundary`

**Example answer:**

> Error Boundaries are components that catch errors during rendering in their descendant component tree and display a fallback UI instead of the failed content.
>
> They help isolate UI failures and prevent rendering errors from taking down larger parts of the application.
>
> In modern React applications, we can use the `react-error-boundary` library.

```jsx
import { ErrorBoundary } from "react-error-boundary";

<ErrorBoundary
  fallback={<p>Something went wrong.</p>}
>
  <UserList />
</ErrorBoundary>
```

If `UserList` throws an error during rendering, the fallback UI is displayed.

---

### 2. What errors can Error Boundaries catch?

**Expectations:** Rendering · Not event handlers · Not async/`useEffect` · `showBoundary()`

**Example answer:**

> They catch errors thrown during rendering and other React-managed operations covered by Error Boundary behavior.
>
> However, they do not automatically catch errors from event handlers, asynchronous callbacks, or `useEffect`.
>
> For asynchronous errors, we can forward the error using `showBoundary()` from `react-error-boundary`.

---

### 3. How do you reset an Error Boundary?

**Expectations:** `resetErrorBoundary()` · `resetKeys` · Underlying error still matters

**Example answer:**

> With `react-error-boundary`, we can call `resetErrorBoundary()` from the fallback component to retry rendering.
>
> We can also use `resetKeys` to reset the boundary when relevant values change. When those values change, the boundary resets and attempts to render the updated content. However, the underlying error must still be resolved.

```jsx
<ErrorBoundary
  FallbackComponent={Fallback}
  resetKeys={[userId]}
>
  <UserProfile userId={userId} />
</ErrorBoundary>
```

---

### 4. Should every API error be handled by an Error Boundary?

**Expectations:** Expected vs unexpected · Explicit error states · Retry UI

**Example answer:**

> No. Expected API failures, such as validation errors or failed requests, are usually better handled with explicit loading, error, and retry states.
>
> Error Boundaries are more appropriate for unexpected errors that prevent a component subtree from rendering correctly.

## useState

### 1. What is `useState`, and how does it work in React?

**Expectations:** Store state · Setter · Re-render on change

**Example answer:**

> `useState` is a React Hook that lets function components store state between renders. It returns the current state value and a setter function that schedules an update and triggers a re-render when the state changes.

```jsx
const [count, setCount] = useState(0);

setCount(count + 1);
```

---

### 2. Why use a functional state update?

**Expectations:** Next depends on previous · Sequential updaters · Batching

**Example answer:**

> Use a functional update when the next state depends on the previous state. React processes updater functions in sequence, so multiple updates work correctly.
>
> These updates increase the count by three.

```jsx
setCount((prev) => prev + 1);
setCount((prev) => prev + 1);
setCount((prev) => prev + 1);
```

---

### 3. Why should we not mutate objects or arrays in state directly?

**Expectations:** Immutability · New references · Detect changes

**Example answer:**

> React state should be treated as immutable. Create a new object or array when updating state so React can detect the change correctly.
>
> Mutating an existing object and passing the same reference back may cause React to skip the update.

```jsx
setUser((prev) => ({
  ...prev,
  name: "Alex",
}));
```

---

### 4. What is lazy initialization in `useState`?

**Expectations:** Expensive initial value · Run once · Pure · Strict Mode

**Example answer:**

> Lazy initialization lets you avoid recalculating an expensive initial value on every render. Pass a function instead of calling it directly.
>
> React uses the function's return value for the initial state. The initializer should be pure because Strict Mode may call it twice in development.

```jsx
const [value, setValue] = useState(() => computeInitial());
```

---

### 5. What is the difference between colocating state and lifting state up?

**Expectations:** Local ownership · Shared parent · Closest common ancestor

**Example answer:**

> - **Colocating state:** Keep state close to the component that uses it to simplify ownership and reduce unnecessary sharing.
> - **Lifting state up:** Move state to the closest common parent when multiple components need to read or update the same value.
>
> For example, a search input and its results component can share a `query` state owned by their parent.

---

## useEffect

### 1. What is `useEffect`, and when should you use it?

**Expectations:** External systems · After commit · Dependency array · Cleanup

**Example answer:**

> `useEffect` is a React Hook used to synchronize a component with external systems, such as APIs, timers, event listeners, and subscriptions.
>
> It runs after React commits a render. Its dependency array determines when the Effect needs to run again.

```jsx
useEffect(() => {
  // Synchronize with an external system

  return () => {
    // Cleanup
  };
}, [dependencies]);
```

---

### 2. What is the difference between `useEffect` with and without a dependency array?

**Expectations:** Every commit · Mount/`[]` · Specific deps · `Object.is` · Strict Mode

**Example answer:**

> - **No dependency array:** Runs after every commit.
> - **Empty array `[]`:** Runs after the initial commit, with an extra setup-and-cleanup cycle in development Strict Mode.
> - **With dependencies `[count]`:** Runs after the initial commit and again when `count` changes.
>
> React compares dependencies using `Object.is`.

---

### 3. Why is cleanup important in `useEffect`?

**Expectations:** Timers · Listeners · Subscriptions · Before re-run · Unmount

**Example answer:**

> Cleanup stops ongoing work created by an Effect, such as timers, event listeners, or subscriptions.
>
> React runs cleanup before re-running the Effect with changed dependencies and when the component unmounts.
>
> Without cleanup, timers or subscriptions can continue running unnecessarily.

```jsx
useEffect(() => {
  const id = setInterval(() => {
    console.log("tick");
  }, 1000);

  return () => clearInterval(id);
}, []);
```

---

### 4. What happens if you forget to include a dependency?

**Expectations:** Stale closures · Include all reactive values · Don't suppress warnings

**Example answer:**

> The Effect may use a stale value from an earlier render because React doesn't know that the Effect needs to re-run when that value changes.
>
> Include all reactive values used by the Effect in its dependency array. If an Effect runs too often, review its dependencies and restructure the logic rather than suppressing the dependency warning.

---

## useId

### 1. What is `useId`, and when should you use it?

**Expectations:** Unique IDs · Labels · Accessibility · Avoid duplicates

**Example answer:**

> `useId` is a React Hook that generates a unique ID for a component instance. It's primarily used to connect form elements with labels, hints, and accessibility attributes.
>
> When multiple `EmailInput` instances render, each receives its own ID, avoiding duplicate IDs in the document.

```jsx
import { useId } from "react";

function EmailInput() {
  const id = useId();

  return (
    <>
      <label htmlFor={id}>Email</label>
      <input id={id} />
    </>
  );
}
```

---

### 2. Why is `useId` useful for accessibility?

**Expectations:** `htmlFor` · `aria-describedby` · Screen readers

**Example answer:**

> It helps connect related elements using attributes such as `htmlFor` and `aria-describedby`.
>
> Screen readers can use this relationship to associate the input with its description.

```jsx
const id = useId();

<input id={id} aria-describedby={`${id}-hint`} />
<p id={`${id}-hint`}>Enter your email address.</p>
```

---

### 3. Can you use `useId` to generate list keys?

**Expectations:** No · Stable data IDs · Top-level Hooks only

**Example answer:**

> No. `useId` is not designed for list keys. Use stable IDs from your data instead.
>
> Also, Hooks must be called at the top level of a component or custom Hook, not inside loops or callbacks.

```jsx
items.map((item) => (
  <Row key={item.id} item={item} />
))
```

---

### 4. Is the ID generated by `useId` stable across re-renders and server rendering?

**Expectations:** Stable across re-renders · SSR hydration · Matching trees

**Example answer:**

> Yes. The ID remains stable across re-renders and supports consistent server-rendered and client-rendered IDs during hydration, provided the component trees match.

---

## useRef

### 1. What is `useRef`, and how is it different from `useState`?

**Expectations:** Mutable `.current` · No re-render · DOM access · Persist values

**Example answer:**

> `useRef` is a React Hook that stores a mutable value in a persistent object across renders. Updating its `.current` property does not trigger a re-render.
>
> It's commonly used to access DOM elements, manage timers, and store values that don't directly affect the UI.

```jsx
const inputRef = useRef(null);

<input ref={inputRef} />
```

---

### 2. What are the common use cases for `useRef`?

**Expectations:** Focus inputs · Timer IDs · Third-party libraries

**Example answer:**

> Three common use cases are accessing DOM elements, such as focusing an input; storing timer IDs or other mutable values between renders; and integrating third-party libraries that need direct access to DOM elements.

```jsx
const handleFocus = () => {
  inputRef.current?.focus();
};
```

---

### 3. Why doesn't changing `ref.current` trigger a re-render?

**Expectations:** Not tracked as state · Persist without scheduling render

**Example answer:**

> React doesn't track changes to `ref.current` as state updates. The ref object persists across renders, but modifying its value doesn't schedule a render.
>
> Use `useState` instead when a value must update the UI.

---

### 4. When should you use `useRef` instead of `useState`?

**Expectations:** UI-affecting data → state · Persist without render → ref

**Example answer:**

> Use `useState` for data that affects rendering, such as a counter or form value. Use `useRef` for values that must persist between renders but don't need to trigger UI updates, such as a timer ID.
>
> Rule of thumb: If changing a value should update the UI, use state. If you need to remember a value without triggering a render, use a ref.

## Suspense & `use()`

### 1. How does React handle asynchronous rendering with `Suspense`, Error Boundaries, and `use()`?

**Expectations:** Suspense fallback · Error Boundary · `use()` reads Promises · Declarative async UI

**Example answer:**

> React provides a declarative way to handle pending resources and rendering errors.
>
> - **Suspense:** Displays fallback UI while a child suspends.
> - **Error Boundaries:** Display fallback UI when a descendant throws a rendering error.
> - **`use()`:** Reads a resource such as a Promise during rendering. If the Promise is pending, React suspends; if it rejects, the error can propagate to an Error Boundary.

```jsx
<ErrorBoundary fallback={<div>Something went wrong.</div>}>
  <Suspense fallback={<div>Loading...</div>}>
    <PhoneDetails phonePromise={phonePromise} />
  </Suspense>
</ErrorBoundary>
```

---

### 2. Does Suspense automatically handle every `fetch()` call?

**Expectations:** Suspense-enabled resources only · Not ordinary `useEffect` fetch · Framework/library integration

**Example answer:**

> No. Suspense only responds to supported Suspense-enabled resources. Ordinary `fetch()` calls inside `useEffect` do not automatically activate Suspense.
>
> For example, React frameworks and supported data-fetching libraries can integrate their data loading with Suspense.

---

### 3. What does the React `use()` API do?

**Expectations:** Read Promise during render · Suspend when pending · Error Boundary on reject · Conditions/loops allowed

**Example answer:**

> The `use()` API reads a resource, such as a Promise, during rendering.
>
> If the Promise is pending, React can show the nearest Suspense fallback. If it rejects, the error can reach the nearest Error Boundary.
>
> Unlike ordinary Hooks, `use()` can be called inside conditions and loops, subject to its API rules.

```jsx
function PhoneDetails({ phonePromise }) {
  const phone = use(phonePromise);

  return <div>{phone.name}</div>;
}
```

---

### 4. Why should Promise identity remain stable?

**Expectations:** Avoid repeated suspension · Pass from parent/data layer · Reuse across re-renders

**Example answer:**

> Creating a new Promise during every render can cause repeated suspension and unnecessary requests.
>
> Instead, create the Promise in a parent or supported data-fetching layer and pass it to the component. Reuse the same Promise across re-renders until the resource needs to change.

---

### 5. How can you avoid async waterfalls?

**Expectations:** Start requests before `use()` · Concurrent fetching · Preserve identity

**Example answer:**

> Start independent requests before reading their results, so they can run concurrently rather than one after another.
>
> The important detail is that both requests start before the child reads either Promise. In production, the data-fetching layer must also preserve Promise identity across re-renders.

```jsx
const favoritesPromise = getFavorites(username);
const friendsPromise = getFriends(username);

return (
  <Suspense fallback={<div>Loading...</div>}>
    <ProfileDetails
      favoritesPromise={favoritesPromise}
      friendsPromise={friendsPromise}
    />
  </Suspense>
);
```

## Custom Hooks & Memoization

### 1. What is a Custom Hook, and how can you optimize it with `useCallback` and `useMemo`?

**Expectations:** Reuse logic · Independent state · `useCallback` · `useMemo`

**Example answer:**

> A Custom Hook is a JavaScript function whose name starts with `use` and that reuses stateful logic across components.
>
> Each call has its own independent state unless the Hook connects to a shared store or Context.

```jsx
function useCount() {
  const [count, setCount] = useState(0);

  const increment = () => setCount(c => c + 1);

  return { count, increment };
}
```

---

### 2. Do Custom Hooks share state between components?

**Expectations:** Share logic · Not state · Parent · Context · Store

**Example answer:**

> No. Custom Hooks share logic, not state. Each component calling `useCount()` gets its own `count` state.
>
> To share state, use a common parent, Context, or a shared state store.

---

### 3. Why can a function inside a Custom Hook cause unnecessary Effect executions?

**Expectations:** New reference each render · Effect deps · `useCallback` · Functional updates

**Example answer:**

> A function declared inside a Hook is recreated on every render. If an Effect depends on that function, React detects a changed dependency and re-runs the Effect.
>
> For example, an interval might be repeatedly cleared and restarted.
>
> Here, `useCallback` preserves the function reference between renders while its dependencies remain unchanged. The functional state update means `count` does not need to be a dependency.

```jsx
const increment = useCallback(() => {
  setCount(c => c + 1);
}, []);
```

---

### 4. What is the difference between `useCallback` and `useMemo`?

**Expectations:** Function identity · Calculated value · `Object.is`

**Example answer:**

> - **`useCallback`** caches a function reference.
> - **`useMemo`** caches the result of a calculation.
>
> Both compare dependencies using `Object.is`.

```jsx
const total = useMemo(() => calculateTotal(items), [items]);

const handleClick = useCallback(() => {
  submitForm(formData);
}, [formData]);
```

---

### 5. When should you use memoization?

**Expectations:** Expensive work · Stable identity · Not everywhere · Optimization only

**Example answer:**

> Use `useMemo` for expensive calculations and `useCallback` when stable function identity matters, such as passing callbacks to memoized child components or using functions as Effect dependencies.
>
> Avoid memoizing everything because memoization adds complexity and overhead. It should be a performance optimization, not a requirement for correctness.

---

## useImperativeHandle

### 1. What is `useImperativeHandle`, and when should you use it?

**Expectations:** Custom ref API · Limited methods · Focus/scroll · Not full DOM access

**Example answer:**

> `useImperativeHandle` is a React Hook that lets a child component expose a custom API through a ref. Instead of giving the parent direct access to the child's DOM element, you can expose only specific methods, such as `focusInput()` or `scrollToTop()`.

---

### 2. How does `useImperativeHandle` work?

**Expectations:** Child exposes methods · Parent calls via ref · React 19 `ref` prop · `forwardRef` earlier

**Example answer:**

> The child defines the methods it wants to expose, and the parent calls them through a ref.
>
> In React 19, `ref` can be received as a prop. In earlier React versions, function components typically use `forwardRef`.

```jsx
import { useImperativeHandle, useRef } from "react";

function MyInput({ ref }) {
  const inputRef = useRef(null);

  useImperativeHandle(ref, () => ({
    focusInput() {
      inputRef.current?.focus();
    },
  }), []);

  return <input ref={inputRef} />;
}
```

---

### 3. Why not expose the DOM element directly?

**Expectations:** Controlled API · Encapsulation · Limit parent access

**Example answer:**

> Exposing a custom API gives the parent controlled access to specific actions without revealing the child's internal implementation.
>
> For example, a reusable input can expose `focusInput()` without allowing the parent to manipulate every property of the underlying DOM element.

---

### 4. When should you use `useImperativeHandle` instead of props?

**Expectations:** Imperative actions · Prefer declarative props · Dialog `isOpen` vs `open()`

**Example answer:**

> Use it when a parent needs to trigger an imperative action, such as focusing an input, scrolling a container, or controlling media playback.
>
> Prefer props for declarative behavior, such as showing or hiding a dialog. For example, an `isOpen` prop is usually better than an imperative `open()` method when the parent owns the dialog's state.

## flushSync

### 1. What is `flushSync()`, and when should you use it?

**Expectations:** Synchronous flush · Immediate DOM commit · Sparingly · Performance cost

**Example answer:**

> `flushSync()` is an API from `react-dom` that forces React to synchronously flush updates inside its callback, ensuring the relevant DOM updates are committed before the next line executes.
>
> It's useful when an external integration or imperative operation requires the DOM to be updated immediately. However, it can hurt performance and should be used sparingly.

---

### 2. Why doesn't calling `setState()` immediately update the DOM?

**Expectations:** Schedules update · Batching · Ref may still be `null`

**Example answer:**

> Calling a state setter schedules an update. React may batch updates and commit them later, so the DOM may not reflect the new state immediately.
>
> For example, if an input is conditionally rendered, its ref may still be `null` immediately after calling `setShow(true)`.

---

### 3. How can you focus a conditionally rendered input without `flushSync()`?

**Expectations:** `useEffect` after commit · Preferred approach

**Example answer:**

> Use `useEffect` to focus the input after React commits the update.
>
> This is usually the preferred solution because focus management generally doesn't require forcing a synchronous update.

```jsx
useEffect(() => {
  if (show) {
    inputRef.current?.focus();
  }
}, [show]);
```

---

### 4. When would you actually use `flushSync()`?

**Expectations:** Third-party/browser APIs · Immediate DOM access · Performance warning

**Example answer:**

> Use it when a third-party library or browser API requires the DOM to reflect a React update before the next statement executes.
>
> After `flushSync` returns, the relevant DOM update has been committed, so the input ref can be accessed.
>
> Important: `flushSync()` can flush other pending work and Effects, and it may hurt performance. Prefer normal state updates and Effects unless synchronous DOM access is genuinely necessary.

```jsx
flushSync(() => {
  setShow(true);
});

inputRef.current?.focus();
```

## Portals

### 1. What are React Portals, and why do we use them?

**Expectations:** Different DOM node · Same React tree · Modals · Tooltips · Escape CSS clipping

**Example answer:**

> React Portals let you render JSX into a different DOM node while keeping the component inside the same React tree.
>
> They're commonly used for modals, tooltips, and dropdowns that need to escape CSS constraints such as `overflow: hidden`.

```jsx
import { createPortal } from "react-dom";

function Modal({ children }) {
  return createPortal(children, document.body);
}
```

---

### 2. Why use a Portal instead of rendering a modal normally?

**Expectations:** `overflow: hidden` · `transform` · Render into `document.body`

**Example answer:**

> A modal rendered inside a parent with `overflow: hidden` may be clipped. CSS properties such as `transform` can also affect the positioning of fixed elements.
>
> Rendering the modal into `document.body` can avoid these ancestor-related layout constraints.

---

### 3. Do events and Context still work inside a Portal?

**Expectations:** DOM placement vs React tree · Context from ancestors · Event bubbling in React tree

**Example answer:**

> Yes. A Portal changes the DOM placement, not the component's position in the React tree.
>
> - **Context:** The portal can access Context from its React ancestors.
> - **Events:** React events can bubble through the React tree, even when the DOM elements aren't direct ancestors.

---

### 4. What should you consider when using Portals in production?

**Expectations:** Focus · Escape · Accessibility · SSR · Tooltip positioning

**Example answer:**

> For modals, consider managing keyboard focus and restoring it when the modal closes, supporting Escape to close when appropriate, providing accessible dialog labels, and ensuring the portal target exists, especially in server-rendered applications.
>
> For tooltips, also consider positioning, scrolling, viewport boundaries, and keyboard accessibility.

## useLayoutEffect

### 1. What is `useLayoutEffect`, and how is it different from `useEffect`?

**Expectations:** After commit · Before paint · Measure layout · Prefer `useEffect` by default

**Example answer:**

> `useLayoutEffect` is a React Hook that runs after React commits DOM changes but before the browser repaints. It's useful when you need to measure layout or make visual adjustments before the user sees the result.
>
> By contrast, `useEffect` is generally preferred for synchronization that doesn't need to block painting.

---

### 2. When should you use `useLayoutEffect`?

**Expectations:** Measure dimensions · Position before paint · Avoid flicker

**Example answer:**

> Use it when you need to measure an element's dimensions or adjust its position before the browser paints, such as positioning a tooltip without visible flicker.

```jsx
useLayoutEffect(() => {
  const height = ref.current?.getBoundingClientRect().height;
  if (height !== undefined) {
    setHeight(height);
  }
}, []);
```

---

### 3. What is the main difference between `useLayoutEffect` and `useEffect`?

**Expectations:** Before vs after paint · Blocking · Cleanup · Dependencies

**Example answer:**

> - **`useLayoutEffect`:** Runs before repaint and can block painting while its code and synchronous state updates are processed.
> - **`useEffect`:** Generally allows the browser to paint first for updates not caused by an interaction, making it suitable for most effects.
>
> Both support cleanup functions and dependency arrays.

---

### 4. Why shouldn't you use `useLayoutEffect` everywhere?

**Expectations:** Blocks paint · Performance · Prefer `useEffect` for most work

**Example answer:**

> Because it can block browser painting and hurt performance. Use it only when the timing of a visual update matters.
>
> For fetching data, subscriptions, and most other external synchronization, prefer `useEffect`.

## useReducer

### 1. What is `useReducer`, and when should you use it instead of `useState`?

**Expectations:** Reducer · Actions · Complex transitions · Related values

**Example answer:**

> `useReducer` is a React Hook that manages state through a reducer function and dispatched actions.
>
> It's useful for complex state logic, especially when multiple related values need predictable state transitions.
>
> - **state:** The current state.
> - **dispatch:** Sends an action to update state.
> - **reducer:** A pure function that calculates the next state.

```tsx
const [state, dispatch] = useReducer(reducer, initialState);
```

---

### 2. What is the difference between `useState` and `useReducer`?

**Expectations:** Simple vs complex · Centralized transitions · Local state

**Example answer:**

> - **`useState`:** Best for simple, independent state values.
> - **`useReducer`:** Better for complex state logic involving multiple related values or actions.
>
> Both manage local component state, but `useReducer` centralizes state transitions in a reducer function.

---

### 3. Why must a reducer be a pure function?

**Expectations:** No mutation · No side effects · Predictable · Testable

**Example answer:**

> A reducer must produce the next state based only on the current state and action, without mutating existing state or performing side effects.
>
> Pure reducers make state transitions predictable, easier to test, and compatible with React's rendering behavior.

```tsx
function reducer(state, action) {
  switch (action.type) {
    case "increment":
      return { ...state, count: state.count + 1 };

    default:
      return state;
  }
}
```

---

### 4. Can you perform API calls inside a reducer?

**Expectations:** No · Keep pure · Dispatch from handlers/effects

**Example answer:**

> No. Reducers should remain pure and synchronous.
>
> Perform API requests in event handlers, Effects, or a dedicated data-fetching layer, then dispatch actions to update state.

```tsx
async function loadUsers() {
  dispatch({ type: "fetch" });

  try {
    const response = await fetch("/api/users");

    if (!response.ok) {
      throw new Error("Failed to fetch users");
    }

    const users = await response.json();
    dispatch({ type: "success", data: users });
  } catch (error) {
    dispatch({ type: "error" });
  }
}
```

---

### 5. What is the difference between `useReducer` and Redux?

**Expectations:** Local vs global · Middleware · DevTools · App-wide store

**Example answer:**

> - **`useReducer`:** Manages state locally within a component or a shared subtree when combined with Context.
> - **Redux:** Provides a centralized state store with features such as middleware, DevTools, and application-wide state management.
>
> Both use reducers and actions, but Redux is designed for more extensive state management needs.

## useSyncExternalStore

### 1. What is `useSyncExternalStore`, and why was it introduced?

**Expectations:** External stores · Concurrent-safe · Subscribe · Snapshot · SSR

**Example answer:**

> `useSyncExternalStore` is a React Hook introduced in React 18 that lets components subscribe to external stores and read their state safely during concurrent rendering.
>
> It's useful when the source of truth lives outside React, such as a Redux store, a browser API, or a custom store.
>
> - **`subscribe`:** Registers a change listener and returns an unsubscribe function.
> - **`getSnapshot`:** Reads the current store state.
> - **`getServerSnapshot`:** Provides the snapshot for server rendering and hydration.

```jsx
const snapshot = useSyncExternalStore(
  subscribe,
  getSnapshot,
  getServerSnapshot
);
```

---

### 2. Why not use `useEffect` and `useState` instead?

**Expectations:** Timing issues · Tearing · Standard subscription API

**Example answer:**

> You can use `useEffect` and `useState` for simple subscriptions, but manually synchronizing them can introduce timing issues between rendering and subscription setup.
>
> `useSyncExternalStore` provides a standard subscription mechanism that helps React avoid inconsistent snapshots, also known as tearing, during concurrent rendering.

---

### 3. What are the requirements for `getSnapshot`?

**Expectations:** Stable reference · No new object every call · New snapshot on change

**Example answer:**

> `getSnapshot` must return a cached, stable value while the store hasn't changed.
>
> For example, returning a newly created object on every call can cause unnecessary re-renders or an infinite-loop warning.
>
> The store should provide a new snapshot reference when its state changes.

```jsx
// ❌ Returns a new object every time
const getSnapshot = () => ({ ...store.state });

// ✅ Returns the existing immutable snapshot
const getSnapshot = () => store.getSnapshot();
```

---

### 4. What is `getServerSnapshot` used for?

**Expectations:** SSR · Hydration · Matching initial snapshots · Browser fallbacks

**Example answer:**

> It provides the initial snapshot during server rendering and client hydration.
>
> The server and client must produce matching initial snapshots for hydration to work correctly. If the store is browser-specific, the server snapshot should use a suitable fallback value.

---

### 5. When should you use `useSyncExternalStore` instead of `useState`?

**Expectations:** React-owned vs external · CSS for visual media queries

**Example answer:**

> Use `useState` when React owns the state. Use `useSyncExternalStore` when the source of truth exists outside React and components need to subscribe to its changes.
>
> For purely visual responsiveness, CSS media queries are often simpler than subscribing to `window.matchMedia`.

## Context

### 1. What is React Context, and when should you use it?

**Expectations:** Share values · Avoid prop drilling · Provider · `useContext` · Theme/auth

**Example answer:**

> React Context lets components share values without passing props through every intermediate component. It's useful for data such as themes, authentication information, and shared application state.
>
> A Provider supplies the value, and descendant components access it using `useContext`.

```jsx
const ThemeContext = createContext("light");

function App() {
  return (
    <ThemeContext.Provider value="dark">
      <Profile />
    </ThemeContext.Provider>
  );
}

function Profile() {
  const theme = useContext(ThemeContext);
  return <div>Theme: {theme}</div>;
}
```

---

### 2. Do Custom Hooks share state between components?

**Expectations:** Share logic · Not state · Lift state · Context Provider

**Example answer:**

> No. Custom Hooks share logic, not state. Each call creates its own independent state unless the Hook connects to a shared state source, such as Context.
>
> To share state, you can lift it to a common parent or use Context with a Provider that owns the state.

---

### 3. What happens when a Context value changes?

**Expectations:** Consumers re-render · `Object.is` · New object identity · `useMemo` / split Contexts

**Example answer:**

> Components that consume that Context receive the updated value and re-render when the Provider's value changes according to `Object.is`.
>
> For example, if a Provider supplies a new object on every render, its consumers may re-render even if the object's properties are unchanged.
>
> You can use `useMemo`, split Contexts, or restructure components when profiling identifies unnecessary work.

---

### 4. Is Context a replacement for Redux?

**Expectations:** Value sharing vs store · Middleware · DevTools · Complexity tradeoff

**Example answer:**

> Not necessarily.
>
> - **Context:** Shares values across a component tree.
> - **Redux:** Provides centralized state management and additional capabilities such as middleware, DevTools, and structured update patterns.
>
> Context works well for relatively simple shared state. Redux or another state-management library may be more suitable for complex application-wide state.

## Component Patterns

### 1. How do you design reusable React components without making their APIs difficult to maintain?

**Expectations:** Composition · Shared state · Reusable behavior · Pattern choice

**Example answer:**

> React provides several patterns for improving component composition, sharing state, and reusing interaction logic. The right choice depends on whether components need shared state, flexible composition, or reusable behavior.

---

### 2. What is the Compound Components pattern?

**Expectations:** Shared parent state · Context · Flexible declarative API

**Example answer:**

> Compound Components let related components share state through a common parent, usually using Context.
>
> This provides a flexible, declarative API without requiring consumers to pass state and callbacks to every child.

```jsx
<Toggle>
  <Toggle.On>ON</Toggle.On>
  <Toggle.Off>OFF</Toggle.Off>
  <Toggle.Button />
</Toggle>
```

---

### 3. How can component composition prevent prop drilling?

**Expectations:** Pass `children` · Layout wrappers · Context when many need the value

**Example answer:**

> Instead of passing props through intermediate components, pass elements using `children`.
>
> The container doesn't need to know what its children render or which props they need.
>
> Composition is especially useful for layout components, wrappers, and modals. Context is more suitable when many descendants genuinely need the same shared value.

```jsx
function Container({ children }) {
  return <div className="container">{children}</div>;
}
```

---

### 4. What is the Latest Ref pattern, and when is it useful?

**Expectations:** Stable callback · Latest values in refs · Debounce/timers · Not for UI state

**Example answer:**

> The Latest Ref pattern stores the latest callback or value in a ref so a long-lived function can access current data without changing its identity.
>
> It's useful for debounced callbacks, timers, and event subscriptions that need the latest callback without repeatedly restarting.
>
> However, update refs carefully. If the value must trigger rendering, use state instead.

---

### 5. What are Prop Collections and Prop Getters?

**Expectations:** Ready-made props · Getter merges custom props · Accessibility · Flexibility

**Example answer:**

> Both patterns let a custom Hook expose props needed to operate a component.
>
> - **Prop collection:** Returns a ready-made props object.
> - **Prop getter:** Returns a function that generates props and can incorporate consumer customization.
>
> For example, a toggle Hook can provide `aria-pressed` and `onClick` so consumers don't have to implement the interaction logic themselves.
>
> Prop getters are more flexible when consumers need to add custom handlers, classes, or accessibility attributes.

## Performance

### 1. How do you optimize React applications to reduce unnecessary rendering and improve performance?

**Expectations:** Profile first · Memoization · Code splitting · Concurrent APIs · Context · Virtualization

**Example answer:**

> I start by identifying the bottleneck using React DevTools Profiler and browser performance tools. Then I apply targeted optimizations, such as memoization, code splitting, concurrent rendering features, Context optimization, and list virtualization.

---

### 2. How can you prevent unnecessary re-renders?

**Expectations:** `React.memo` · `useMemo` · `useCallback` · Reuse JSX · Measure first

**Example answer:**

> Use `React.memo` to skip parent-driven renders when props remain unchanged, `useMemo` to cache expensive calculations, and `useCallback` when stable function identity matters.
>
> You can also reuse static JSX elements across renders. However, memoization should be applied when it provides a meaningful performance benefit.

---

### 3. What is the difference between `useTransition` and `useDeferredValue`?

**Expectations:** Non-urgent updates · Deferred values · Not debounce · Not faster compute

**Example answer:**

> Both help keep the UI responsive by allowing non-urgent rendering work to be deprioritized.
>
> - **`useTransition`:** Marks a state update as non-urgent.
> - **`useDeferredValue`:** Lets a value used by part of the UI lag behind its latest value.
>
> For example, a search input can update immediately while an expensive results list renders using a deferred query.
>
> Neither Hook automatically makes expensive calculations faster or debounces network requests.

---

### 4. How do you optimize React Context?

**Expectations:** `Object.is` · Memoize values · Split state/actions · Memo doesn't block context

**Example answer:**

> Context consumers re-render when the provided value changes according to `Object.is`.
>
> To reduce unnecessary updates, memoize object or array values when appropriate, split state and actions into separate Contexts when consumers need different update patterns, and keep Providers close to the components that need them.
>
> Remember that a component consuming a Context still re-renders when that Context value changes, even if it is wrapped in `React.memo`.

---

### 5. What is code splitting, and how does it improve performance?

**Expectations:** Smaller initial JS · `React.lazy` · `Suspense` · On-demand features

**Example answer:**

> Code splitting divides JavaScript into smaller bundles that can load when needed, reducing the amount of JavaScript required for the initial page.
>
> The Globe module is loaded when the component is first rendered. This is particularly useful for heavy features that users may not need immediately.

```jsx
const Globe = lazy(() => import("./Globe"));

<Suspense fallback={<div>Loading...</div>}>
  {showGlobe && <Globe />}
</Suspense>
```

---

### 6. How do you optimize a list containing thousands of items?

**Expectations:** Virtualization · Visible rows only · `react-window` · Smaller DOM

**Example answer:**

> Use list virtualization to render only the visible items and a small buffer rather than mounting the entire list.
>
> Libraries such as `react-window` can reduce DOM size, memory usage, and layout work, improving scrolling performance.
>
> For example, a list of 10,000 items may only need around a dozen visible rows at a time, depending on viewport and row height.

## Concurrent UI Hooks

### 1. How do you keep React interfaces responsive during expensive updates and form submissions?

**Expectations:** `useDeferredValue` · `useTransition` · `useFormStatus` · `useOptimistic`

**Example answer:**

> React provides specialized hooks for different UI responsiveness problems:
>
> - **`useDeferredValue`** — defer updating a value used by expensive UI.
> - **`useTransition`** — mark state updates as non-urgent.
> - **`useFormStatus`** — access the pending status of a parent form.
> - **`useOptimistic`** — display temporary UI state before an Action finishes.

---

### 2. What is the difference between `useDeferredValue` and `useTransition`?

**Expectations:** Defer a value · Mark updates non-urgent · Not faster compute · Not debounce

**Example answer:**

> Both help React prioritize urgent interactions, but they work differently.
>
> - **`useDeferredValue`** lets a value used by expensive UI lag behind the latest value.
> - **`useTransition`** lets you mark specific state updates as non-urgent.
>
> Use `useDeferredValue` when you don't control the state update, or want to defer a value passed to an expensive component. Use `useTransition` when you control the state update and want to mark it as a transition.
>
> Important: Neither hook makes expensive JavaScript execute faster or debounces network requests.

---

### 3. How does `useFormStatus` work?

**Expectations:** Nearest parent form · `pending` · Must be inside the form

**Example answer:**

> `useFormStatus` from `react-dom` exposes the submission status of the nearest parent form.
>
> The component calling `useFormStatus` must be rendered inside the form it tracks. Calling it in the component that creates the form won't track that form's submission.

```jsx
function SubmitButton() {
  const { pending } = useFormStatus();

  return (
    <button type="submit" disabled={pending}>
      {pending ? "Submitting..." : "Submit"}
    </button>
  );
}
```

---

### 4. What is optimistic UI, and how does `useOptimistic` help?

**Expectations:** Update UI immediately · Temporary state · Revert on failure · Sync confirmed state

**Example answer:**

> Optimistic UI updates the interface immediately while an asynchronous Action is running, rather than waiting for server confirmation.
>
> Here, `liked` is the underlying state, and `optimisticLiked` is the temporary UI state. The example assumes `startTransition` is available in scope and the parent updates `liked` after the server confirms the change.
>
> If the Action fails, handle the error and ensure the underlying state remains consistent. The optimistic state reverts when the Action ends unless the confirmed state has also been updated.

```jsx
const [optimisticLiked, setOptimisticLiked] =
  useOptimistic(liked);

async function handleLike() {
  startTransition(async () => {
    setOptimisticLiked(!optimisticLiked);
    await updateLikeOnServer(!optimisticLiked);
  });
}
```

---

### 5. When should you use `useState` instead of `useOptimistic`?

**Expectations:** Persistent client state · Temporary Action anticipation

**Example answer:**

> Use `useState` for persistent client-side state, such as form values, validation errors, or multi-step workflow progress.
>
> Use `useOptimistic` for temporary UI state that anticipates the result of an asynchronous Action, such as liking a post or adding a todo.

---

### 6. Do these hooks replace each other?

**Expectations:** Different problems · Choose by bottleneck

**Example answer:**

> No. Each addresses a different problem.
>
> | Hook | Main purpose |
> | --- | --- |
> | `useDeferredValue` | Defer value-driven rendering |
> | `useTransition` | Mark updates as non-urgent |
> | `useFormStatus` | Track parent form submission status |
> | `useOptimistic` | Show temporary optimistic state |
> | `useState` | Store regular component state |
>
> Start by identifying the problem—expensive rendering, form submission feedback, or perceived network latency—then choose the hook that addresses it.

## Testing

### 1. How do you test React components effectively?

**Expectations:** RTL · Observable behavior · `user-event` · MSW · Accessibility

**Example answer:**

> React Testing Library (RTL) encourages testing components through observable user behavior rather than implementation details. Combined with `user-event`, `jest-dom`, and MSW, it helps test interactions, accessibility, asynchronous updates, and API behavior.

```jsx
const user = userEvent.setup();

render(<LoginForm />);

await user.type(
  screen.getByRole("textbox", { name: /email/i }),

await user.click(

expect(await screen.findByText(/welcome/i))

```

### 2. What is the difference between `getBy`, `queryBy`, and `findBy`?

**Expectations:** Immediate · Absence · Async wait · Prefer `getByRole`

**Example answer:**

> - **`getBy...`:** Finds an element immediately or throws an error.
> - **`queryBy...`:** Returns `null` if no element matches; useful for checking absence.
> - **`findBy...`:** Returns a Promise and waits for an element to appear.
>
> Prefer `getByRole` when possible because it encourages accessible markup.

```jsx
expect(screen.getByRole("button")).toBeInTheDocument();

expect(screen.queryByText(/error/i)).not.toBeInTheDocument();

expect(await screen.findByText(/loaded/i)).toBeInTheDocument();
```

### 3. Why use `user-event` instead of `fireEvent`?

**Expectations:** Realistic interactions · Event sequences · Prefer for most tests

**Example answer:**

> `user-event` simulates user interactions more realistically, including the sequence of events involved in typing and clicking. `fireEvent` dispatches individual DOM events directly.
>
> Use `user-event` for most interaction tests and `fireEvent` when you specifically need to dispatch a particular event.

---

### 4. What is jsdom, and what are its limitations?

**Expectations:** Node DOM · No real layout · Mock browser APIs · Playwright for E2E

**Example answer:**

> `jsdom` provides a browser-like DOM environment in Node.js, allowing component tests without launching a real browser.
>
> However, it doesn't fully implement browser behavior such as actual layout, scrolling, media playback, or geolocation.
>
> - **RTL + jsdom:** Test component behavior and DOM interactions.
> - **Playwright or Cypress:** Test real-browser rendering, responsive layouts, and end-to-end workflows.
>
> Browser APIs such as `matchMedia` or `IntersectionObserver` may need mocks in jsdom tests.

---

### 5. How do you test API requests without calling a real server?

**Expectations:** MSW · Network boundary · Success/error · Loading states

**Example answer:**

> Use Mock Service Worker (MSW) to intercept network requests and return controlled responses while the application uses its normal API client.
>
> You can test successful responses, HTTP errors and network failures, loading and empty states, and retry behavior.
>
> Unlike mocking `fetch` directly, MSW intercepts requests at the network boundary, making tests more representative of real application behavior.

---

### 6. How do you test components that require Context or other providers?

**Expectations:** Custom render · Shared providers · Less boilerplate

**Example answer:**

> Create a custom `render` helper that wraps components with shared providers, such as `ThemeProvider`, `QueryClientProvider`, or a router.
>
> This avoids repeating provider setup in every test and keeps tests focused on component behavior.

```jsx
function renderWithProviders(ui: React.ReactElement) {
  return render(ui, {
    wrapper: AppProviders,
  });
}
```

## TypeScript

### 1. How does TypeScript improve code quality, and which features do you use to make applications type-safe?

**Expectations:** Static checking · Unions · Narrowing · Generics · Utility types · `satisfies` · Runtime validation

**Example answer:**

> TypeScript improves code quality by detecting type errors during static checking, making data structures explicit, and enabling safer refactoring. I commonly use union types, type narrowing, generics, utility types, and `satisfies` to build maintainable applications.
>
> However, TypeScript cannot guarantee runtime safety, so external data still needs validation.

---

### 2. What is the difference between `type` and `interface`?

**Expectations:** Declaration merging · Unions · Object shapes · When to use each

**Example answer:**

> Both can describe object shapes. The main differences are that `interface` supports declaration merging, while `type` can represent unions, intersections, primitives, and other type expressions.
>
> I generally use `interface` for extensible object contracts and `type` for unions, utility types, and more complex type compositions. Both are suitable for many object shapes.

```ts
interface User {
  name: string;
}

interface User {
  age: number;
}

// Declaration merging: both properties exist.
const user: User = {
  name: "Viet",
  age: 30,
};

type Status = "loading" | "success" | "error";
```

---

### 3. What is type narrowing?

**Expectations:** Runtime checks · `typeof` · `unknown` vs `any`

**Example answer:**

> Type narrowing allows TypeScript to determine a more specific type from a broader type using runtime checks.
>
> `unknown` is safer than `any` because it requires validation before most operations, whereas `any` disables type checking for the value.

```ts
function printValue(value: string | number) {
  if (typeof value === "string") {
    console.log(value.toUpperCase());
  } else {
    console.log(value.toFixed(2));
  }
}

function handleError(error: unknown) {
  if (error instanceof Error) {
    console.log(error.message);
  }
}
```

---

### 4. What are `keyof` and `typeof` used for?

**Expectations:** Derive types · Avoid duplication · `as const`

**Example answer:**

> `typeof` derives a type from a value, while `keyof` extracts an object's property names as a union.
>
> To avoid duplicating types, I derive them from existing constants or objects instead of maintaining separate definitions.

```ts
const config = {
  apiUrl: "/api",
  timeout: 5000,
};

type Config = typeof config;
type ConfigKey = keyof Config;
// "apiUrl" | "timeout"

const roles = ["admin", "user", "guest"] as const;

type Role = (typeof roles)[number];
// "admin" | "user" | "guest"
```

---

### 5. What are generics, and why are they useful?

**Expectations:** Preserve type info · Reusable · `extends` constraints

**Example answer:**

> Generics allow functions, classes, and types to work with different data types while preserving type information.
>
> I constrain a generic with `extends` when it must satisfy a specific requirement, such as accepting only objects with a string `id`.

```ts
function getFirst<T>(items: T[]): T | undefined {
  return items[0];
}

const first = getFirst([1, 2, 3]);
// number | undefined

function getId<T extends { id: string }>(item: T): string {
  return item.id;
}
```

---

### 6. What are TypeScript utility types?

**Expectations:** `Omit` · `Partial` · `Pick` · `Record`

**Example answer:**

> Utility types transform existing types without requiring you to redefine them.
>
> `Partial<T>` makes every property optional, which is useful for update payloads. `Pick<T, K>` selects specific properties while preserving their original types, which is useful for a compact representation.

```ts
interface User {
  id: number;
  name: string;
  email: string;
}

type CreateUser = Omit<User, "id">;
type UpdateUser = Partial<User>;
type UserPreview = Pick<User, "id" | "name">;
type UserMap = Record<string, User>;
```

---

### 7. What is the difference between `satisfies` and a type annotation?

**Expectations:** Compile-time check · Preserve inference · Not runtime validation

**Example answer:**

> A type annotation checks compatibility but can widen the resulting expression's type. `satisfies` checks compatibility while retaining more of the expression's inferred type.
>
> `satisfies` is a compile-time check only. API responses and other external data still need runtime validation.

```ts
type Color = "red" | "green" | "blue";
```

### 8. How do you implement exhaustive checks?

**Expectations:** Discriminated unions · `never` · Missing cases

**Example answer:**

> I use discriminated unions and `never` to ensure every case is handled. If I add another union member without handling it, TypeScript reports an error at the exhaustive check, helping me identify the missing case.

```ts
type Result =
  | { status: "success"; data: string }
  | { status: "error"; message: string };

function handleResult(result: Result): string {
  switch (result.status) {
    case "success":
      return result.data;

    case "error":
      return result.message;

    default: {
      const exhaustiveCheck: never = result;
      return exhaustiveCheck;
    }
  }
}
```

### 9. Does TypeScript prevent all runtime errors?

**Expectations:** Types erased · External data · Zod · `unknown`

**Example answer:**

> No. TypeScript checks types statically, but types are erased at runtime. It cannot automatically guarantee that external data matches a declared type or that business logic is correct.
>
> To make this safer, I treat parsed data as `unknown` and validate it with runtime checks or a schema validation library such as Zod before using it.

```ts
type User = { name: string };

const user: User = JSON.parse('{"age": 30}');

console.log(user.name.toUpperCase());
// Runtime error: user.name is undefined
```
