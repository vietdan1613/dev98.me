## FastAPI Basics

### 1. What is FastAPI?

FastAPI is a modern Python web framework for building APIs. It uses standard Python type hints to handle request validation, response serialization, and automatic documentation. It's built on Starlette for the web parts and Pydantic for the data parts.

The short answer for an interview: FastAPI lets you build production-ready REST APIs with less code than Flask and better performance than Django.

### 2. Why is FastAPI popular?

Three reasons come up in every interview answer:

- **Speed:** FastAPI is one of the fastest Python frameworks, comparable to Node.js and Go.
- **Type hints:** You write regular Python type annotations and FastAPI turns them into validation, docs, and IDE autocomplete.
- **Async support:** Async is built into the library.

With FastAPI, you end up with less boilerplate and fewer bugs from mismatched request formats.

### 3. What is the difference between FastAPI and Flask?

Flask is minimal and unopinionated. You get routing and templating, and you add everything else yourself, including validation and serialization.

FastAPI includes those things by default. You get automatic request validation from type hints, automatic OpenAPI docs, and native async support without extra libraries.

The downside is that FastAPI is more opinionated. If you want full control over every layer, Flask gives you more room. But if you want to have something usable fast, FastAPI wins.

### 4. What is the difference between FastAPI and Django?

Django is a full-stack framework with an ORM, admin panel, templating, and authentication. It's designed for building web applications end to end.

FastAPI is API-first. It doesn't include an ORM or admin panel, and it doesn't try to. You bring your own database layer (usually SQLAlchemy or SQLModel) and focus on building the API.

For a monolithic web app with server-rendered HTML, Django is the better option. For microservices, ML model APIs, or backend services talking to a separate frontend, FastAPI is a better fit.

### 5. What is automatic API documentation?

FastAPI generates interactive API docs from your code. You get two endpoints:

- `/docs` serves a Swagger UI interface
- `/redoc` serves a ReDoc interface

Both are generated from the OpenAPI schema FastAPI builds from your type hints, Pydantic models, and route decorators. You don't write the docs. You write the code, and the docs stay in sync.

### 6. How does FastAPI generate OpenAPI schemas?

FastAPI generates the OpenAPI schema from your code. It inspects your routes, path parameters, Pydantic models, response models, and dependency signatures, and produces a JSON document that describes the whole API.

You get the schema at `/openapi.json`, plus the Swagger UI at `/docs` and ReDoc at `/redoc`. OpenAPI generation rewards clean type hints, so always use Pydantic models with clear field names.

You can customize the schema by passing metadata to `FastAPI()` and to each route:

```python
app = FastAPI(title="Orders API", version="1.2.0")

@app.get("/orders", summary="List orders", tags=["orders"])
def read_orders():
    ...
```

## Routing and API Design

How requests reach your code, and how to shape URLs, status codes, and list endpoints so the API is easy to use.

### 1. How do you define a route?

You use a decorator on a function. The decorator specifies the HTTP method and the path:

```python
from fastapi import FastAPI

app = FastAPI()

@app.get("/items")
def read_items():
    return {"items": []}
```

The function name doesn't matter for routing. What matters is the decorator (`@app.get`, `@app.post`, `@app.put`, `@app.delete`) and the path string.

### 2. What are path parameters?

Path parameters are values embedded in the URL path itself. You declare them with curly braces in the route and as function arguments:

```python
@app.get("/items/{item_id}")
def read_item(item_id: int):
    return {"item_id": item_id}
```

The type hint `int` tells FastAPI to validate and convert the value. If someone hits `/items/abc`, FastAPI returns a 422 error.

### 3. What are query parameters?

Query parameters are the key-value pairs after the `?` in a URL. In FastAPI, any function argument that isn't a path parameter is treated as a query parameter:

```python
@app.get("/items")
def read_items(skip: int = 0, limit: int = 10):
    return {"skip": skip, "limit": limit}
```

A request to `/items?skip=20&limit=5` gets `skip=20` and `limit=5`. Default values make the parameters optional.

### 4. What REST principles does FastAPI encourage?

FastAPI doesn't enforce REST, but its design makes REST easy to follow.

The principles that come up in interviews:

- **Resource-based URLs:** `/users/{id}/orders` instead of `/getUserOrders?id=5`.
- **HTTP methods for actions:** GET reads, POST creates, PUT and PATCH update, DELETE removes. FastAPI's decorators map one to one.
- **Statelessness:** each request contains everything the server needs. FastAPI dependencies make it easy to attach auth and context per request without hidden state.
- **Consistent status codes:** 2xx for success, 4xx for client errors, 5xx for server errors.

FastAPI won't stop you from breaking these principles. It just makes the correct pattern the easy one.

### 5. Which HTTP status codes should you use?

The codes that come up most in FastAPI interviews:

| Code | Meaning |
| --- | --- |
| 200 OK | Successful GET, PUT, PATCH |
| 201 Created | Successful POST that creates a resource |
| 204 No Content | Successful DELETE or PUT with no response body |
| 400 Bad Request | Malformed request the client should fix |
| 401 Unauthorized | Missing or invalid authentication |
| 403 Forbidden | Authenticated but not allowed |
| 404 Not Found | Resource doesn't exist |
| 409 Conflict | Request conflicts with current state, like a duplicate email on signup |
| 422 Unprocessable Entity | Validation failed. FastAPI returns this automatically for Pydantic errors |
| 500 Internal Server Error | Something broke on your side |

You set the code with the `status_code` parameter on the decorator:

```python
@app.post("/users", status_code=201)
def create_user(user: UserCreate):
    return db.create(user)
```

### 6. How do you handle pagination?

The two patterns are offset-based and cursor-based.

Offset-based pagination uses `skip` and `limit`:

```python
@app.get("/items")
def read_items(skip: int = 0, limit: int = 20):
    return db.query(Item).offset(skip).limit(limit).all()
```

It's simple, and clients can jump to arbitrary pages. The downside is that deep pages get slow, because the database still has to skip every earlier row. It also breaks when items are inserted or deleted during pagination.

Cursor-based pagination uses an opaque cursor pointing to the last item seen:

```python
@app.get("/items")
def read_items(cursor: str | None = None, limit: int = 20):
    return db.query_after(cursor, limit)
```

It's fast at any depth and stable under inserts, because you're always paging forward from a known position. The downside is that clients can't jump to page 47.

Use offset pagination for admin dashboards and small datasets. Use cursor pagination for infinite scroll and large datasets.

### 7. How do you handle filtering?

Filtering usually happens through query parameters. Simple cases use plain parameters:

```python
@app.get("/orders")
def read_orders(
    status: str | None = None,
    min_total: float | None = None,
    customer_id: int | None = None,
):
    return db.filter_orders(status=status, min_total=min_total, customer_id=customer_id)
```

For anything with more than four or five filters, move them into a Pydantic model as a dependency:

```python
class OrderFilters(BaseModel):
    status: str | None = None
    min_total: float | None = None
    customer_id: int | None = None

@app.get("/orders")
def read_orders(filters: OrderFilters = Depends()):
    return db.filter_orders(**filters.model_dump(exclude_none=True))
```

Here you're balancing flexibility and safety. You can build a generic filter system that accepts any field and operator, but you also open the door to slow queries and injection risks.

### 8. How do you handle API versioning?

There are three patterns you should know:

- **URL versioning:** `/v1/users` and `/v2/users`. Easiest to route, easiest to explain, and works with every client.
- **Header versioning:** clients send an `Accept-Version` header. Cleaner URLs but harder to debug and cache.
- **Query parameter versioning:** `/users?version=2`. Works, but rarely used in practice.

URL versioning is the best choice most of the time. You mount separate routers under different prefixes:

```python
from fastapi import APIRouter

v1_router = APIRouter(prefix="/v1")
v2_router = APIRouter(prefix="/v2")

app.include_router(v1_router)
app.include_router(v2_router)
```

The downside of URL versioning is that clients tend to hardcode the version into their code, so that's something to be aware of.

## Pydantic

### 1. What is Pydantic, and how does it work with FastAPI?

**Expectations:** Validation · Type coercion · Serialization · Request/response schemas · `422`

**Example answer:**

> Pydantic validates incoming data, converts compatible values into expected Python types, and serializes data for API responses. FastAPI uses Pydantic models to validate request bodies and define response schemas.
>
> - **`BaseModel`:** Defines the data structure and types.
> - **`Field()`:** Adds constraints, such as a non-empty name and a positive price.
> - Invalid data raises a validation error, which FastAPI typically returns as a `422` response for invalid request data.

```python
from pydantic import BaseModel, Field

class Product(BaseModel):
    name: str = Field(min_length=1)
    price: float = Field(gt=0)
```

---

### 2. What is the difference between `field_validator` and `model_validator`?

**Expectations:** Single-field rules · Cross-field rules · `mode="after"` · Custom `ValueError`

**Example answer:**

> - **`field_validator`:** Validates an individual field using custom logic.
> - **`model_validator`:** Validates relationships between multiple fields.
>
> For example, `field_validator` can check an SKU format, while `model_validator` ensures the end date is not earlier than the start date.

```python
from datetime import date
from pydantic import BaseModel, field_validator, model_validator

class Promotion(BaseModel):
    sku: str
    start_date: date
    end_date: date

    @field_validator("sku")
    @classmethod
    def validate_sku(cls, value: str) -> str:
        if not value.startswith("MON-"):
            raise ValueError("Invalid SKU")
        return value

    @model_validator(mode="after")
    def validate_dates(self):
        if self.end_date < self.start_date:
            raise ValueError("Invalid dates")
        return self
```

---

### 3. What are `model_validate()` and `model_dump()` used for?

**Expectations:** Validate input · Create instance · Serialize to dict · Type coercion · `from_attributes`

**Example answer:**

> - **`model_validate()`:** Validates input data and creates a Pydantic model instance.
> - **`model_dump()`:** Converts the model into a Python dictionary.
>
> Pydantic converts compatible input values, such as date strings, into their declared Python types. If you need to validate an ORM object's attributes, configure the model with `ConfigDict(from_attributes=True)`.
>
> Core distinctions: `BaseModel` defines the schema, `Field()` adds constraints, validators implement custom rules, `model_validate()` creates validated instances, and `model_dump()` serializes them into dictionaries.

```python
data = {
    "sku": "MON-001",
    "start_date": "2026-10-22",
    "end_date": "2026-10-30",
}

promotion = Promotion.model_validate(data)
result = promotion.model_dump()
```

## Dependency Injection

### 1. What is Dependency Injection (DI), and why is it useful in FastAPI?

**Expectations:** `Depends()` · Declare vs provide · Loose coupling · Reusability · Testability

**Example answer:**

> Dependency Injection allows a function to declare what it needs while another component provides it. FastAPI uses `Depends()` to inject dependencies such as database sessions and authenticated users.
>
> Instead of creating and closing database sessions inside routes, the route declares its requirements and FastAPI resolves the dependencies. The session's cleanup depends on how `get_db` is implemented.
>
> Benefits include:
>
> - **Loose coupling:** Separates business logic from dependency creation.
> - **Reusability:** Shares authentication, database, and pagination logic across routes.
> - **Testability:** Replaces dependencies without changing route implementations.

```python
from fastapi import Depends
from sqlalchemy.ext.asyncio import AsyncSession


@app.get("/api/plants")
async def get_plants(
    db: AsyncSession = Depends(get_db),
):
    ...
```

---

### 2. How does dependency composition work, and how do you override dependencies in tests?

**Expectations:** Nested `Depends` · Request-scoped reuse · `dependency_overrides` · Test DB

**Example answer:**

> Dependencies can depend on other dependencies. For example, `get_current_admin` can use `get_db` to retrieve an administrator from the database.
>
> FastAPI resolves the dependency chain automatically. By default, repeated dependencies using the same callable and cache settings are reused within a request.
>
> For testing, replace the production database dependency with a test implementation using `app.dependency_overrides`. This allows routes to use a test database without modifying the application code.
>
> Key ideas: `Depends()` declares dependencies, composition lets dependencies reuse one another, and `app.dependency_overrides` makes testing easier.

```python
async def get_current_admin(
    db: AsyncSession = Depends(get_db),
) -> Admin:
    ...


@app.get("/api/admin/plants")
async def get_admin_plants(
    admin: Admin = Depends(get_current_admin),
    db: AsyncSession = Depends(get_db),
):
    ...


app.dependency_overrides[get_db] = get_test_db
# Run tests...
app.dependency_overrides.pop(get_db, None)
```

## Middleware

### 1. What is middleware in FastAPI, and how does it work?

**Expectations:** Request/response pipeline · `call_next` · Cross-cutting concerns · Timing/logging/CORS

**Example answer:**

> Middleware sits between the client and the application. It processes requests before they reach the endpoint and can inspect or modify responses before returning them.
>
> Common use cases include request logging, request IDs, request timing, CORS, security headers, rate limiting, and GZip compression.
>
> The request flow has three steps:
>
> 1. **Before `call_next()`:** Process the incoming request.
> 2. **At `call_next()`:** Pass the request to the next layer and await the response.
> 3. **After `call_next()`:** Inspect or modify the response.

```python
import time

from fastapi import FastAPI, Request

app = FastAPI()


@app.middleware("http")
async def timing_middleware(request: Request, call_next):
    start = time.perf_counter()
    response = await call_next(request)
    elapsed = time.perf_counter() - start
    response.headers["X-Process-Time"] = f"{elapsed:.4f}"
    return response
```

---

### 2. How do you use `request.state`, and what is the difference between HTTP middleware and ASGI middleware?

**Expectations:** Request-scoped state · HTTP `call_next` · ASGI `scope`/`receive`/`send` · Business logic elsewhere

**Example answer:**

> `request.state` stores data scoped to an individual request, such as a request ID. It is not global application state. An endpoint or dependency can access values like `request.state.request_id`.
>
> - **HTTP middleware:** Uses `@app.middleware("http")` with `request` and `call_next`. Convenient for logging, timing, and headers.
> - **ASGI middleware:** Wraps the application directly with `scope`, `receive`, and `send`, providing lower-level control over ASGI messages.
>
> Use HTTP middleware for common request/response processing. Use ASGI middleware when you need lower-level control. Keep business logic in endpoints, dependencies, or services rather than putting it in middleware.

```python
import uuid

from fastapi import Request


@app.middleware("http")
async def request_id_middleware(request: Request, call_next):
    request_id = (
        request.headers.get("X-Request-ID") or str(uuid.uuid4())
    )
    request.state.request_id = request_id

    response = await call_next(request)

    response.headers["X-Request-ID"] = request_id
    return response
```

## Exception Handling

### 1. How do you implement centralized exception handling in FastAPI?

**Expectations:** `AppException` · Global handlers · Consistent responses · Validation · Unexpected errors

**Example answer:**

> A production API should return consistent error responses instead of handling errors separately in every endpoint.
>
> A common approach is to define a custom `AppException` and register global exception handlers. The exception carries the HTTP status, application error code, message, and optional details.
>
> Common handlers include:
>
> - **`AppException`:** Application-specific errors.
> - **`HTTPException`:** Standard HTTP errors.
> - **`RequestValidationError`:** Invalid request data.
> - **`Exception`:** Unexpected errors.
>
> This centralizes error formatting and keeps route handlers focused on their main responsibilities.

```python
class AppException(Exception):
    def __init__(
        self,
        error_code: int,
        error_message: str,
        error=None,
        status_code: int = 500,
    ):
        self.error_code = error_code
        self.error_message = error_message
        self.error = error
        self.status_code = status_code
        super().__init__(error_message)


app.add_exception_handler(
    AppException, app_exception_handler
)
app.add_exception_handler(
    RequestValidationError, validation_exception_handler
)
app.add_exception_handler(
    Exception, generic_exception_handler
)
```

---

### 2. How do you organize custom exceptions and handle database errors in the service layer?

**Expectations:** Domain exceptions · Service raises errors · Rollback · `raise ... from` · Handlers format HTTP

**Example answer:**

> Create specific exceptions for different application modules while inheriting from `AppException`, such as `DBException`, `AuthException`, `PaymentException`, and `ExternalAPIException`.
>
> The service layer raises meaningful exceptions instead of constructing HTTP responses. Use `rollback()` when appropriate, preserve the original cause with `raise ... from exc`, and let the global handler convert the custom exception into a standardized HTTP response.
>
> Keep responsibilities separate: services detect and raise errors; global handlers translate them into HTTP responses. Log unexpected failures for debugging, but do not expose internal stack traces or sensitive database details to clients.

```python
try:
    result = await session.execute(query)
except SQLAlchemyError as exc:
    await session.rollback()
    raise DBException(
        error_code=1001,
        error_message="Failed to retrieve client.",
    ) from exc
```

## Errors and App Lifecycle

### 1. What are lifespan events and when do you use them?

Lifespan events run code at application startup and shutdown. You use them for anything that needs to happen once per process, like connecting to a database or loading an ML model.

The modern pattern uses an async context manager:

```python
from contextlib import asynccontextmanager

@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.model = load_model()
    yield
    app.state.model = None

app = FastAPI(lifespan=lifespan)
```

Code before `yield` runs on startup. Code after `yield` runs on shutdown. Both are async, so you can await connections and gracefully close resources.

The tradeoff is that lifespan events run per worker process, not per app. If you run four Gunicorn workers, your ML model loads four times. For large models, that's a memory problem you solve with shared memory or a separate model server.

### 2. What are background tasks?

Background tasks let you run code after the response has already been sent to the client. You inject a `BackgroundTasks` object into your endpoint and add functions to it:

```python
from fastapi import BackgroundTasks

@app.post("/signup")
def signup(email: str, background_tasks: BackgroundTasks):
    user = create_user(email)
    background_tasks.add_task(send_welcome_email, email)
    return {"status": "created"}
```

The client gets the response immediately. The email sends in the background.

This works for short tasks that don't need retries or persistence. For anything that must not be lost, like payment processing or file conversion, use a real task queue like Celery or RQ. Background tasks run in the same process, so if the process crashes, the task won't complete.

### 3. How do you handle file uploads?

File uploads use the `File` and `UploadFile` types:

```python
from fastapi import File, UploadFile

@app.post("/upload")
async def upload_file(file: UploadFile = File(...)):
    contents = await file.read()
    return {"filename": file.filename, "size": len(contents)}
```

`UploadFile` is the recommended type because it spools the file to a temporary location on disk instead of keeping the whole thing in memory. For a 10 MB file, that's fine either way. For a 2 GB file, it's the only way not to crash your service.

Read the file in chunks if it's large. `UploadFile` does the cleanup for you when the request ends.

## Async Programming

Async questions come up in every FastAPI interview. They're where most candidates lose points, because you have to explain what the event loop actually does.

### 1. What's the difference between async and sync endpoints?

A sync endpoint runs in a threadpool. FastAPI takes your regular `def` function and runs it in a worker thread so it doesn't block the event loop.

An async endpoint runs directly on the event loop. FastAPI awaits the coroutine you defined with `async def`.

```python
@app.get("/sync")
def sync_endpoint():
    return {"type": "sync"}

@app.get("/async")
async def async_endpoint():
    return {"type": "async"}
```

The rule most candidates get wrong is that async isn't automatically faster. If your endpoint does CPU work, async is slower because the event loop can't do anything else while you compute. If your endpoint does I/O, async is much faster because the event loop can handle other requests during the wait.

### 2. What is asyncio?

`asyncio` is Python's built-in library for writing concurrent code with coroutines. It provides the event loop, primitives like `Task` and `Future`, and utility functions like `asyncio.gather` and `asyncio.sleep`.

FastAPI is built on top of asyncio through Starlette. When you write `async def`, the coroutine gets scheduled on the asyncio event loop that Uvicorn runs.

For the interview, you should know:

- `asyncio.gather(*coroutines)` runs multiple coroutines concurrently and waits for all of them.
- `asyncio.create_task(coroutine)` schedules a coroutine to run in the background.
- `asyncio.sleep(seconds)` is the async version of `time.sleep`, and it doesn't block the event loop.

### 3. What does `await` actually do?

`await` pauses the current coroutine until the awaited object is ready, and gives control back to the event loop.

```python
async def fetch_user(user_id: int):
    user = await db.get(user_id)
    return user
```

When the code gets to `await db.get(user_id)`, three things happen:

1. The coroutine pauses.
2. The event loop moves on to run other coroutines.
3. When the database returns, the coroutine resumes from where it paused.

`await` only helps if the thing you're awaiting is also async. Calling a function that internally runs `time.sleep(5)` blocks the event loop for five seconds, even inside an async endpoint. Nothing else runs during that time.

If you take one thing from this section, take that.

### 4. What is the event loop?

The event loop is a single thread that runs coroutines one at a time. It picks up whichever coroutine is ready to run, executes it until the next `await`, and then moves on.

You can think of it as a task scheduler with one worker. It's not doing things in parallel. It's doing things very fast, one at a time, and switching between them whenever one is waiting on I/O.

This is why FastAPI can handle thousands of concurrent connections with a single process. Most requests spend their time waiting on a database or an external API. While one request waits, the event loop serves another.

But if any coroutine doesn't yield control, the whole loop stops.

### 5. What's the difference between concurrency and parallelism?

Concurrency is dealing with many things at once. Parallelism is doing many things at once.

An async FastAPI process is concurrent. It works on thousands of connections on one thread by switching between them whenever one is waiting.

Parallelism needs multiple CPU cores running code at the same time. In Python, that usually means multiple processes, because the GIL prevents threads from running Python code in parallel.

For a FastAPI app, concurrency handles I/O-bound tasks. Parallelism (multiple Uvicorn workers) handles CPU load and lets you use multiple cores.

### 6. When does async improve performance?

Async improves performance when your endpoint spends most of its time waiting.

Good fits for async:

- Database queries with an async driver like asyncpg or async SQLAlchemy
- HTTP calls to external APIs with `httpx.AsyncClient`
- File I/O with aiofiles
- Message queue operations

Situations where you shouldn't use async:

- CPU-heavy work like image processing or ML inference
- Any code path that calls a sync library with no async equivalent

The pattern to look for is I/O wait time. If an endpoint takes 200 ms and 190 ms of that is waiting on a database, async lets that time overlap across requests. If it takes 200 ms because it's doing CPU work, async does nothing for you.

### 7. What happens when you use blocking operations in async code?

Blocking operations in an async endpoint freeze the event loop. Every other request waits until the blocking call finishes.

```python
@app.get("/bad")
async def bad_endpoint():
    time.sleep(5)  # blocks the event loop for 5 seconds
    return {"status": "done"}
```

While this endpoint sleeps, no other async endpoint can run.

Common sources of accidental blocking:

- `time.sleep` instead of `asyncio.sleep`
- `requests.get` instead of `httpx.AsyncClient`
- Sync database drivers like psycopg2 without an async layer
- CPU-heavy work embedded in an async endpoint

The fixes are to switch to an async library, run the blocking call in a threadpool with `asyncio.to_thread`, or move the whole endpoint back to sync `def`. FastAPI will run sync endpoints in a threadpool for you, which is often the simplest fix.

## SQLAlchemy

### 1. How do you integrate SQLAlchemy asynchronously with FastAPI and PostgreSQL?

**Expectations:** `asyncpg` · `AsyncSession` · `async_sessionmaker` · `Depends(get_db)` · No auto-commit

**Example answer:**

> SQLAlchemy manages database operations, FastAPI handles HTTP requests, and `asyncpg` provides the asynchronous PostgreSQL driver. `AsyncSession` handles database interactions, while dependency injection provides a session to each request.
>
> Inject the session into an endpoint using `Depends(get_db)`. The context manager closes the session when the dependency finishes, but does not automatically commit transactions.

```python
from sqlalchemy.ext.asyncio import (
    create_async_engine,
    async_sessionmaker,
    AsyncSession,
)

engine = create_async_engine(DATABASE_URL)
AsyncSessionLocal = async_sessionmaker(
    engine,
    expire_on_commit=False,
)


async def get_db():
    async with AsyncSessionLocal() as session:
        yield session
```

### 2. How do you define models, query and modify records, and manage database migrations?

**Expectations:** `DeclarativeBase` · `Mapped` · `Decimal`/`Numeric` · `select` · `add`/`commit`/`refresh` · Alembic · Separate Pydantic schemas

**Example answer:**

> SQLAlchemy models map Python classes to database tables using `DeclarativeBase`, `Mapped`, and `mapped_column()`. Use `Decimal` with `Numeric` for monetary values to avoid floating-point precision issues.
>
> Query with `await db.execute(select(...))`, then `scalars().all()`. Insert with `db.add()`, `await db.commit()`, and `await db.refresh()`. Remember that `add()` is synchronous because it stages the object, while database I/O uses `await`.
>
> Manage migrations with Alembic (`init -t async`, `revision --autogenerate`, `upgrade head`). Configure `target_metadata` to use `Base.metadata`, and review autogenerated migrations before applying them.
>
> Keep SQLAlchemy models separate from Pydantic schemas: ORM models represent database tables, while Pydantic schemas validate input and define API response structures.

```python
from decimal import Decimal

from sqlalchemy import Numeric, String, select
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column


class Base(DeclarativeBase):
    pass


class Plant(Base):
    __tablename__ = "plants"

    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(100))
    price: Mapped[Decimal] = mapped_column(Numeric(10, 2))


result = await db.execute(select(Plant))
plants = result.scalars().all()

plant = Plant(name="Monstera", price=Decimal("250000.00"))
db.add(plant)
await db.commit()
await db.refresh(plant)
```

## Security

### 1. What are the essential security practices for a production FastAPI application?

**Expectations:** AuthN/AuthZ · CORS · Rate limiting · Headers · Validation · HTTPS · Secrets

**Example answer:**

> A production API needs multiple layers of security to protect user accounts, data, and application resources.
>
> - **Authentication:** Verifies who the user is, for example by validating credentials and JWTs.
> - **Authorization:** Determines what the user can do, including role permissions and resource ownership.
> - **CORS:** Restricts which browser origins can access the API.
> - **Rate limiting:** Limits request frequency to reduce brute-force attacks and abuse. Return `429 Too Many Requests` when limits are exceeded.
> - **Security headers:** Headers such as `X-Content-Type-Options` and `X-Frame-Options` add browser-level protections.
> - **Input validation:** Use Pydantic to validate request data and reject invalid input.
> - **HTTPS:** Encrypts data transmitted between clients and servers.
> - **Secrets management:** Keep database credentials, API keys, and JWT signing secrets out of source code.

### 2. How do you protect authentication, user input, and sensitive data in production?

**Expectations:** JWT validation · Ownership checks · XSS · Argon2id · Env secrets · HTTPS proxies

**Example answer:**

> For authentication and authorization, validate JWT signatures, expiration, and relevant claims. Restrict permissions and check resource ownership where applicable.
>
> For input and XSS protection, validate incoming data with Pydantic, use safe database queries, and render untrusted content as text. If accepting HTML, sanitize it with a library such as `nh3`.
>
> For passwords and secrets: hash passwords with Argon2id, never log passwords or tokens, load secrets from environment variables or a secrets manager, and use HTTPS while trusting only known reverse proxies for forwarded headers.
>
> Security is not a single middleware or library. Authentication identifies users, authorization enforces permissions, validation checks input, and infrastructure controls such as HTTPS, rate limiting, and secrets management provide complementary protection.

## WebSockets

### 1. What are WebSockets, and how do you implement real-time communication with FastAPI and React?

**Expectations:** Bidirectional · Persistent connection · `accept`/`receive`/`send` · JSON · React hook lifecycle

**Example answer:**

> WebSockets provide a persistent, bidirectional connection between a client and a server. Unlike traditional HTTP request-response communication, either side can send messages without establishing a new connection for each message.
>
> Common use cases include chat applications, real-time notifications, live dashboards, and delivery tracking.
>
> The main FastAPI operations are `accept()`, `receive_text()`, `send_text()`, and `close()`. For structured data, use `receive_json()` and `send_json()`.
>
> In React, the browser's `WebSocket` API manages the client connection. A custom hook using `useEffect` can create the connection, update state when messages arrive, and close the connection during cleanup.

```python
from fastapi import FastAPI, WebSocket, WebSocketDisconnect

app = FastAPI()


@app.websocket("/ws")
async def websocket_endpoint(websocket: WebSocket):
    await websocket.accept()

    try:
        while True:
            message = await websocket.receive_text()
            await websocket.send_text(
                f"Server received: {message}"
            )
    except WebSocketDisconnect:
        pass
```

---

### 2. How do you manage multiple connections and build reliable WebSocket applications?

**Expectations:** Connection manager · Broadcast · Auth · Reconnect/backoff · Redis Pub/Sub · `wss://`

**Example answer:**

> A connection manager tracks active connections, broadcasts messages, and removes disconnected clients.
>
> For production applications, also consider authentication and authorization, disconnect handling with `WebSocketDisconnect`, reconnection with exponential backoff and jitter, Redis Pub/Sub for multi-worker communication, message IDs or acknowledgements when delivery must be guaranteed, and `wss://` over HTTPS.
>
> An in-memory connection list only tracks connections within its own process. WebSockets are useful when updates are frequent and low latency matters; for simpler infrequent updates, HTTP polling or Server-Sent Events (SSE) may be easier to maintain.

```python
class ConnectionManager:
    def __init__(self):
        self.active_connections: list[WebSocket] = []

    async def connect(self, websocket: WebSocket):
        await websocket.accept()
        self.active_connections.append(websocket)

    def disconnect(self, websocket: WebSocket):
        if websocket in self.active_connections:
            self.active_connections.remove(websocket)

    async def broadcast(self, message: str):
        for connection in self.active_connections.copy():
            await connection.send_text(message)
```

## Streaming Responses

### 1. What is streaming in FastAPI, and how do you implement real-time AI responses?

**Expectations:** Progressive chunks · `StreamingResponse` · `yield` · SSE · Forward AI tokens immediately

**Example answer:**

> Streaming sends response data progressively instead of waiting for the entire response to finish. It improves perceived responsiveness, especially for AI chat, logs, and live progress updates.
>
> FastAPI provides `StreamingResponse`, which can consume a generator that produces data using `yield`. For structured events, Server-Sent Events (SSE) uses `text/event-stream`, and each event ends with a blank line.
>
> For AI streaming, use an asynchronous model SDK with streaming enabled, iterate over the generated chunks, and forward each chunk immediately rather than collecting the complete response first.

```python
from fastapi import FastAPI
from fastapi.responses import StreamingResponse

app = FastAPI()


async def generate():
    for chunk in ["Hello", " from", " FastAPI"]:
        yield chunk


@app.get("/stream")
async def stream():
    return StreamingResponse(
        generate(),
        media_type="text/plain",
    )
```

```python
import json


def format_sse(data: dict) -> str:
    return f"data: {json.dumps(data)}\n\n"


async def generate_events():
    yield format_sse({
        "type": "chunk",
        "content": "Hello",
    })
    yield format_sse({"type": "done"})
```

### 2. How do you consume SSE streams in React, and what production issues should you consider?

**Expectations:** `fetch` · `ReadableStream` · Buffering · Proxy buffering · Cancellation · Keep-alive

**Example answer:**

> For a `POST` streaming endpoint, the browser's `fetch()` API and `ReadableStream` allow React to read chunks incrementally.
>
> Network reads do not necessarily align with SSE events. A read may contain a partial event or multiple events, so the client must buffer incomplete data.
>
> For production, consider proxy buffering, timeouts for long-running streams, cancellation of upstream AI generation when the client disconnects, structured error events, concurrent stream limits, and keep-alive comment frames.
>
> Remember the roles: `StreamingResponse` streams content, SSE structures server-to-client events, and `ReadableStream` lets the browser consume data incrementally.

```javascript
const response = await fetch("/api/chat/stream", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ message: "Explain FastAPI" }),
});

if (!response.ok || !response.body) {
  throw new Error("Unable to start stream");
}

const reader = response.body.getReader();
const decoder = new TextDecoder();
let buffer = "";

while (true) {
  const { value, done } = await reader.read();

  buffer += decoder.decode(value, { stream: !done });

  const events = buffer.split("\n\n");
  buffer = events.pop() ?? "";

  for (const event of events) {
    const line = event
      .split("\n")
      .find((item) => item.startsWith("data: "));

    if (!line) continue;

    const data = JSON.parse(line.slice(6));

    if (data.type === "chunk") {
      console.log(data.content);
    } else if (data.type === "done") {
      console.log("Streaming complete");
    } else if (data.type === "error") {
      console.error(data.message);
    }
  }

  if (done) break;
}
```

## Redis

### 1. What is Redis, and how do you integrate it with FastAPI?

**Expectations:** In-memory store · `redis.asyncio` · Lifespan · `ping`/`aclose` · Per-worker client

**Example answer:**

> Redis is an in-memory data store commonly used for caching, rate limiting, session storage, and temporary data. It can reduce repeated database queries and share data across multiple application workers.
>
> FastAPI can use the asynchronous `redis.asyncio` client to communicate with Redis without blocking the event loop during I/O operations. Use FastAPI's lifespan handler to manage the connection lifecycle: `ping()` checks connectivity, `app.state.redis` exposes the client to endpoints, and `aclose()` closes it during shutdown. Each application worker should manage its own client and connection pool.

```python
import os

import redis.asyncio as redis

redis_client = redis.from_url(
    os.getenv("REDIS_URL", "redis://localhost:6379/0"),
    decode_responses=True,
)
```

```python
from contextlib import asynccontextmanager

from fastapi import FastAPI


@asynccontextmanager
async def lifespan(app: FastAPI):
    await redis_client.ping()
    app.state.redis = redis_client

    try:
        yield
    finally:
        await redis_client.aclose()


app = FastAPI(lifespan=lifespan)
```

### 2. How do you store and retrieve cached data, and what are Redis's common production use cases?

**Expectations:** TTL · Cache get/set · Rate limiting · Sessions · Pub/Sub · Not a DB replacement

**Example answer:**

> Redis supports key-value operations with an optional time-to-live (TTL). For example, `ex=300` sets a five-minute TTL, and Redis automatically expires the key after that period.
>
> Common production use cases include caching, rate limiting across workers, session storage, Pub/Sub event distribution, and background job queues with suitable libraries.
>
> For production, configure Redis through environment variables, protect access with authentication and network controls, validate cache keys, and define expiration and invalidation policies.
>
> Redis is often used for fast, temporary or shared application state, while PostgreSQL remains the primary persistent database. Redis is usually an optimization and coordination layer, not a replacement for your main database.

```python
@app.put("/cache/{key}")
async def set_cache(key: str, value: str, request: Request):
    client = request.app.state.redis
    await client.set(key, value, ex=300)
    return {"message": "Value stored successfully"}


@app.get("/cache/{key}")
async def get_cache(key: str, request: Request):
    value = await request.app.state.redis.get(key)

    if value is None:
        raise HTTPException(
            status_code=404,
            detail="Cache key not found",
        )

    return {"key": key, "value": value}
```

## Rate Limiting

### 1. What is rate limiting, and how do you implement it in FastAPI?

**Expectations:** Request caps · SlowAPI · `key_func` · `429` · `Request`/`Response` params

**Example answer:**

> Rate limiting controls how many requests a client can make within a specific period. It helps protect APIs against brute-force attacks, automated abuse, and excessive resource consumption.
>
> SlowAPI is a rate-limiting library for FastAPI and Starlette. It uses a key function to identify clients, tracks their requests, and returns `429 Too Many Requests` when a limit is exceeded.
>
> SlowAPI requires `request: Request` on decorated endpoints; `response: Response` allows rate-limit headers to be attached.

```python
from fastapi import FastAPI, Request, Response
from slowapi import Limiter, _rate_limit_exceeded_handler
from slowapi.errors import RateLimitExceeded
from slowapi.util import get_remote_address

app = FastAPI()

limiter = Limiter(
    key_func=get_remote_address,
    storage_uri="memory://",
    headers_enabled=True,
)

app.state.limiter = limiter
app.add_exception_handler(
    RateLimitExceeded,
    _rate_limit_exceeded_handler,
)


@app.post("/login")
@limiter.limit("5/minute")
async def login(request: Request, response: Response):
    return {"message": "Login endpoint"}
```

---

### 2. How do you configure Redis and apply rate limiting in production?

**Expectations:** `memory://` vs Redis · Shared counters · Proxy IPs · Strict sensitive routes · `@limiter.exempt`

**Example answer:**

> SlowAPI supports different storage backends. `memory://` stores counters in the current process and is suitable for local development. `redis://` shares counters across workers and servers, making it more suitable for production deployments.
>
> Apply stricter limits to login, password-reset, and expensive AI endpoints. In production, configure Redis authentication and network access securely, trust forwarded client IP headers only from known reverse proxies, monitor rejected requests, return `429` consistently, and exempt health checks when appropriate using `@limiter.exempt`.
>
> Key concepts: `key_func` identifies the client, `storage_uri` determines where counters are stored, and `@limiter.limit()` defines endpoint-specific limits. Redis is important when multiple workers must share rate-limit state.

```python
limiter = Limiter(
```

## Feature-Based Architecture

### 1. What is feature-based architecture in FastAPI, and how do you organize an application using it?

**Expectations:** Business domains · Feature ownership · `core/`/`db/`/`shared/` · API aggregation · Request flow

**Example answer:**

> Feature-based architecture organizes code by business domain rather than technical responsibility. Instead of placing all routers, schemas, services, and models into global folders, each feature owns its related code.
>
> Each directory has a specific responsibility:
>
> - `main.py`: Initializes FastAPI, middleware, exception handlers, and application lifecycle.
> - `api/`: Aggregates routers from individual features.
> - `core/`: Provides shared infrastructure, such as configuration, database sessions, and security utilities.
> - `db/`: Defines the SQLAlchemy declarative base and registers ORM models for database tooling such as Alembic.
> - `shared/`: Contains reusable functionality genuinely needed by multiple features.
> - `features/`: Contains business-specific routers, services, Pydantic schemas, ORM models, and dependencies.
>
> The typical request flow is `HTTP Request → Router → Service → Database Session / ORM Models → Database`.

```text
app/
├── main.py
├── api/
│   └── router.py
├── core/          # Shared configuration and infrastructure
├── db/            # SQLAlchemy base and model registry
├── shared/        # Reusable cross-feature utilities
└── features/
    ├── plants/
    │   ├── router.py
    │   ├── service.py
    │   ├── schemas.py
    │   └── models.py
    └── orders/
        ├── router.py
        ├── service.py
        ├── schemas.py
        └── models.py
```

```python
from fastapi import APIRouter

from app.features.plants.router import router as plants_router
from app.features.orders.router import router as orders_router

api_router = APIRouter()

api_router.include_router(
    plants_router,
    prefix="/plants",
    tags=["Plants"],
)
api_router.include_router(
    orders_router,
    prefix="/orders",
    tags=["Orders"],
)
```

> This lets `main.py` register one application-level router while each feature maintains its own endpoints.

### 2. How do you manage dependencies between features and avoid circular imports?

**Expectations:** One-directional deps · Service interfaces · No circular imports · `shared/` · Minimal modules

**Example answer:**

> Features sometimes need to use each other's functionality. For example, the orders feature may need to check whether a plant is available before creating an order.
>
> A maintainable approach is to expose a clear service function or interface, rather than accessing another feature's internal implementation. The orders feature can call the plants service instead of duplicating plant-related business logic.
>
> Follow these principles:
>
> - Keep dependencies one-directional: Features may use `core/` infrastructure, but `core/` should not import business features.
> - Avoid circular imports: For example, `plants` importing `orders` while `orders` also imports `plants`.
> - Use shared abstractions or orchestration: For complex workflows involving multiple features, a coordinating service can manage the interactions.
> - Move genuinely shared code into `shared/`: Avoid turning it into a miscellaneous folder.
> - Keep modules minimal: A feature does not need every possible file if it does not require that functionality.
>
> Feature-based architecture is most useful when an application has multiple business domains, grows beyond a small set of endpoints, or needs clearer boundaries for testing and team development. For a small API, a simpler structure may be sufficient.
>
> The goal is not merely to organize folders. It is to create clear business boundaries that reduce coupling, prevent circular dependencies, and make features easier to test and change independently.

```python
    plant_id: int,

    # Check plant availability
    ...
```

## Performance and Scaling

Senior interviews focus on tradeoffs: what makes a FastAPI service slow, and what you change when traffic grows.

### 1. How do you optimize FastAPI performance?

Performance optimization in FastAPI usually falls into four buckets:

- **Use async for I/O-bound endpoints and sync for CPU-bound work.** Mixing them wrong is the top cause of slow FastAPI services.
- **Reduce Pydantic validation overhead** by keeping response models lean. Extra fields cost serialization time.
- **Cache expensive computations at the right layer.** In-memory for hot data, Redis for shared data.
- **Profile before optimizing.** Use py-spy or austin to find the actual bottleneck.

The biggest single win is usually switching from sync to async for endpoints that connect to the database or external APIs.

### 2. What caching strategies work with FastAPI?

Caching in FastAPI happens at three layers:

- **In-process caching:** functions and computed values cached with `functools.lru_cache` or `cachetools`. Fast, but per-worker, so cache hits vary across workers.
- **Distributed caching:** Redis or Memcached. Slower than in-process but shared across all workers and machines. This is what you use for session data, rate limits, and any state that must be consistent.
- **HTTP caching:** setting `Cache-Control` headers so clients and CDNs cache responses. It adds zero cost to your service, so it's usually the best option.

The tradeoff is cache invalidation. Every layer of caching makes stale data more likely. Cache read-heavy data that doesn't change often. Don't cache user-specific data unless the cache key includes the user ID.

### 3. How do you scale with multiple workers?

Scaling FastAPI is mostly about processes and workers.

A single Uvicorn process runs one event loop. That handles thousands of concurrent connections for I/O-bound work, but only uses one CPU core. For real-world traffic, you run multiple worker processes behind a process manager.

The standard setup is Gunicorn with Uvicorn workers:

```bash
gunicorn app.main:app -w 4 -k uvicorn.workers.UvicornWorker
```

`-w 4` runs four worker processes. Each worker has its own event loop and can use one CPU core. A common starting point is `2 * cpu_cores + 1` workers.

Beyond process scaling, you scale horizontally by running the same container on multiple machines behind a load balancer. Shared state (sessions, caches, rate limits) moves out of the process into Redis or a database.

The tradeoff is memory. More workers means more memory, especially if you load large objects at startup.

### 4. How do you scale vertically and horizontally?

You can scale FastAPI vertically and horizontally.

**Vertical scaling** means bigger machines with more CPU and RAM per instance. You handle it by increasing the worker count until you saturate the CPU or reach memory limits.

**Horizontal scaling** means more instances behind the load balancer. You handle it by moving all state out of the process:

- Sessions and rate limits move to Redis
- Uploads go to object storage, not local disk
- Background jobs go to a shared queue like Celery or RQ
- Database connections respect the total pool size across all instances

Autoscaling is triggered by CPU, memory, or request rate. In Kubernetes, the Horizontal Pod Autoscaler does it for you.

The trap in this question: autoscaling on CPU works for compute-heavy services. For I/O-bound APIs, request queue depth or response latency is a better signal, because CPU stays low even when the service is slow.

## Deployment

Deployment questions separate candidates who've shipped from the ones who've only read about it. Interviewers ask them because the mistakes here take down services in production.

### 1. What is Uvicorn and how do you use it?

Uvicorn is an ASGI server. It runs your FastAPI application and handles the HTTP protocol, WebSocket connections, and the event loop.

In development, you run it directly:

```bash
uvicorn app.main:app --reload
```

The `--reload` flag restarts the server when files change. Don't use it in production.

For production, run Uvicorn without reload, bind to all interfaces, and pick a worker count that matches your CPU:

```bash
uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 4
```

Uvicorn alone works, but many teams run it behind Gunicorn for more process management features.

### 2. What does Gunicorn add on top of Uvicorn?

Gunicorn is a process manager. It handles starting workers, restarting crashed workers, graceful shutdowns, and signal handling. It also gives you more control over how workers run.

The standard command:

```bash
gunicorn app.main:app -w 4 -k uvicorn.workers.UvicornWorker --bind 0.0.0.0:8000
```

`-k uvicorn.workers.UvicornWorker` tells Gunicorn to use Uvicorn for each worker. You get Uvicorn's async handling with Gunicorn's process management:

- Graceful reloads with zero dropped connections
- Automatic restart of crashed workers
- Cleaner logging and signal handling

For a single-worker setup, or a container orchestrator that already restarts processes, Uvicorn alone is fine.

### 3. How do you Dockerize a FastAPI application?

A basic FastAPI Dockerfile:

```dockerfile
FROM python:3.13-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

CMD ["gunicorn", "app.main:app", "-w", "4", "-k", "uvicorn.workers.UvicornWorker", "--bind", "0.0.0.0:8000"]
```

Rules that come up in interviews:

- Use a specific Python version, not `python:latest`.
- Use `-slim` variants for smaller images. Alpine can break some Python packages, so slim is safer.
- Use multi-stage builds when you have build dependencies you don't need at runtime.
- Don't bake secrets into the image. Pass them at runtime through environment variables or a secrets manager.
- Copy `requirements.txt` before the rest of the code, so Docker caches the `pip install` layer.

For serious deployments, let your orchestrator (like Kubernetes) handle scaling and restarts.

### 4. How do you use a reverse proxy with FastAPI?

The typical production stack puts a reverse proxy in front of the app server. Nginx and Traefik are the common options, and cloud load balancers like AWS ALB or Google Cloud Load Balancing fill the same role.

What you get with a reverse proxy:

- TLS termination, so the app only speaks HTTP internally
- Static file serving
- Request buffering, so slow clients don't hold up your workers
- Rate limiting at the edge
- Header manipulation, like adding `X-Forwarded-For`

A minimal Nginx config for FastAPI:

```nginx
server {
    listen 443 ssl;
    server_name api.example.com;

    location / {
        proxy_pass http://localhost:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

Run Uvicorn with `--proxy-headers` (and `--forwarded-allow-ips` set to the proxy's address) so the app trusts the forwarded headers and reports the real client IP and scheme.

### 5. What does a production FastAPI deployment look like?

A typical stack you should be able to explain:

1. DNS pointing to a load balancer
2. Load balancer or reverse proxy handling TLS
3. Container orchestrator (Kubernetes, ECS) running FastAPI containers
4. Each container running Uvicorn workers (optionally under Gunicorn)
5. FastAPI talking to a managed database, cache, and any external services
6. Logs and metrics sent to a central place

Other things that show up in interviews:

- Health check endpoints (`/health` and `/ready`) that the orchestrator polls
- Graceful shutdown handling, so in-flight requests finish during a deploy
- Configuration through environment variables, not hardcoded values
- Secrets from a secrets manager

If you skip any of these, the interviewer usually follows up with "what happens when...".

### 6. How do you monitor a FastAPI application in production?

There are three types of monitoring you should know:

- **Logs:** structured JSON logs with request ID, user ID, endpoint, status code, and latency, sent to a central log store.
- **Metrics:** request rate, error rate, latency percentiles (p50, p95, p99), and worker health. Prometheus is the common choice.
- **Traces:** distributed tracing across services with OpenTelemetry. Essential when a request touches multiple services.

The three metrics that matter most for FastAPI:

- Requests per second, so you know the load
- p95 latency, so you know the slow tail of requests
- Error rate, split by 4xx and 5xx

Log the request ID on every line, propagate it through async code, and include it in error responses. When a customer reports a bug, you'll find the exact request in seconds.

## Testing

### 1. How do you test FastAPI applications using Pytest and HTTPX?

**Expectations:** `pytest` · HTTPX · `ASGITransport` · Fixtures · `dependency_overrides` · Test DB

**Example answer:**

> `pytest` runs automated tests, while HTTPX sends requests to the FastAPI application. Using `ASGITransport`, you can test endpoints without starting a live Uvicorn server.
>
> Key concepts include:
>
> - **Fixtures:** Share reusable setup, such as HTTP clients and database sessions.
> - **Dependency overrides:** Replace production dependencies with test implementations using `app.dependency_overrides`.
> - **Test database:** Keep tests isolated from production data and clean up test changes.

```python
import pytest
from httpx import ASGITransport, AsyncClient

from app.main import app


@pytest.mark.asyncio
async def test_health():
    transport = ASGITransport(app=app)

    async with AsyncClient(
        transport=transport,

    ) as client:

    assert response.status_code == 200
    assert response.json() == {"status": "ok"}
```

## Scenario-Based Questions

Scenario questions are the hardest part of a senior interview because there's no textbook answer. The interviewer wants to see how you think through a problem and what tradeoffs you'd weigh before making a change.

### 1. Your API becomes slow under load. How do you debug it?

Start by figuring out what "slow" means. Slow can mean several different things, and the fix depends on which one.

A standard debugging path:

1. **Check metrics first.** Look at request rate, latency percentiles, error rate, CPU, memory, and event loop lag.
2. **If CPU is maxed out**, you're compute-bound. Add workers or find the responsible function with py-spy.
3. **If CPU is low but latency is high**, you're I/O-bound. Check database query times, external API calls, and connection pool wait times.
4. **If the event loop is stuck**, something is blocking async code. Look for sync calls inside async endpoints.

The usual suspects are N+1 queries from lazy-loaded ORM relationships, missing database indexes on filtered columns, and sync libraries called from async endpoints. All three cause slowness that only shows up under load.

Don't guess and change things. Measure first, form a hypothesis, then test.

### 2. Your Pydantic validation isn't catching invalid input. What's happening?

Three things could be going on:

1. **Is the endpoint actually using the model?** A parameter typed as `dict` or `Any` bypasses validation, so check the function signature.
2. **Is the field optional when it shouldn't be?** A field typed as `str | None = None` accepts null and missing values. Make it required by removing the default value.
3. **Is a custom validator swallowing errors?** For example, a `try/except` inside a validator that returns instead of raising will hide problems.

Beyond that, open the OpenAPI schema at `/openapi.json` and look at what FastAPI thinks the endpoint expects. If the schema shows a field as optional and you thought it was required, the model is wrong.

### 3. Authentication fails intermittently for some users. How do you diagnose it?

Intermittent auth failures usually mean one of four things:

- **Token expiry:** users near the boundary get random 401s as their token expires mid-session.
- **Clock skew between servers:** if one server's clock is off, JWT `exp` and `iat` checks fail on that server.
- **Per-worker in-memory state:** if you cache decoded tokens per worker, users hitting different workers get different results.
- **Load balancer routing:** if one server's Redis connection is broken, requests routed to that server fail auth.

Steps to debug:

1. Log the token expiry, the current server time, and the outcome on every auth check.
2. Correlate failures with specific servers or workers. If they cluster, the issue is one server.
3. Test with a fresh token to rule out expiry as the cause.
4. Check that your JWT verification uses the current signing key.

Once you find the pattern, the fix is usually short. Finding the pattern is the hard part, which is why your reasoning matters more than the code change.

### 4. Your database connections are exhausted. What went wrong?

Connection exhaustion means requests are holding connections longer than expected, or you have more concurrent requests than your pool can serve.

A debugging process that usually works:

1. **Check pool size and max overflow.** If total capacity across all workers exceeds the database's limit, the database rejects new connections.
2. **Look for sessions that don't close.** A missing `finally` block or an exception path without cleanup leaks connections.
3. **Check for long-running queries.** A slow query holds a connection for its full duration.
4. **Look for connections held across `await` points.** If a request opens a connection, calls an external API for two seconds, then uses the connection, that's two seconds of held capacity per request.

The common root cause is that someone opened a session outside the dependency system and forgot to close it.

The fix is to always use the dependency-with-`yield` pattern. It closes the session in the `finally` block, so exceptions don't leak connections. Then set pool size based on peak concurrency across all workers.

### 5. An async endpoint blocks unexpectedly. How do you find the cause?

Something inside the endpoint is sync and holding the event loop.

The suspects, in order of likelihood:

1. Sync database calls with a sync driver. `db.query(User).all()` blocks even in an async endpoint.
2. Sync HTTP calls with `requests` instead of `httpx.AsyncClient`.
3. CPU-bound work like image processing or ML inference.
4. `time.sleep` instead of `asyncio.sleep`.
5. Sync file I/O without aiofiles.

Add timing around each block of the endpoint and look for the section that takes most of the latency. Then check whether that section actually yields to the loop. asyncio's debug mode (`PYTHONASYNCIODEBUG=1`) logs callbacks that take too long, and tools like aiomonitor help inspect a running loop.

The fix depends on what's blocking. For CPU work, run it in a thread or process pool or move it to a background worker. For sync I/O, switch to an async library or use `asyncio.to_thread`. If none of those work, change the endpoint to sync `def`. FastAPI runs it in a threadpool and the event loop stays free.

### 6. Large file uploads slow down your service. What do you do?

Large uploads slow things down for a few different reasons, and the fix depends on which one applies.

The first check is whether you're loading the whole file into memory. `await file.read()` on a 2 GB upload reads all 2 GB into RAM.

The fix is chunked reads:

```python
@app.post("/upload")
async def upload(file: UploadFile = File(...)):
    with open(f"/tmp/{file.filename}", "wb") as f:
        while chunk := await file.read(1024 * 1024):
            f.write(chunk)
    return {"filename": file.filename}
```

In real code, never trust `file.filename` for the path. Generate your own name to avoid path traversal.

The second cause is holding a worker for the full upload duration. A 500 MB upload over a slow connection ties up a worker for minutes.

Fixes you can mention in an interview:

- Put a reverse proxy in front that buffers the upload before it hits your app.
- Use a presigned URL pattern: your API returns a signed upload URL, and the client uploads directly to object storage (S3, GCS).
- Restrict the max upload size at the proxy level and reject oversized requests before they use resources.

For anything above a few hundred megabytes, direct-to-storage uploads are the right answer. The service that handles metadata and the service that handles bytes shouldn't be the same service.

## Common FastAPI Interview Mistakes

These mistakes show up in almost every FastAPI interview. None of them are hard to fix once you know they exist, but most candidates don't know until an interviewer points it out.

### Confusing async and sync

The most common mistake is treating `async def` as a performance switch. Candidates make endpoints async because it sounds faster, then call sync libraries inside them and wonder why the service is slow.

Async only helps when you're waiting on I/O with an async library. Sync database drivers and CPU-bound work block the event loop. If you can't await it, don't put it in an async endpoint.

If you declare a function as async, use async all the way down. Otherwise, use sync `def` and let FastAPI run it in a threadpool.

### Misunderstanding dependency injection

Many candidates treat `Depends()` as a fancy way to call a function. They inject dependencies but bypass them in tests, or reimplement the same logic in multiple endpoints.

Dependencies are the boundary. Auth, database sessions, permission checks, and configuration all belong there. Endpoints should receive them as parameters and not care where they came from.

Red flags for the interviewer:

- Opening a session inside the endpoint instead of using a dependency
- Calling `get_current_user()` directly instead of injecting it
- Writing the same three-line auth check at the top of every endpoint

If you find yourself repeating code across endpoints, that code probably belongs in a dependency.

### Ignoring validation

Candidates who skip response models, use `dict` as a request type, or reach for manual `request.json()` parsing are unlikely to get a senior role. FastAPI does validation for you, and not using it means writing more code that does less.

Interviewers look for a few things: every endpoint has a request model or typed parameters, every endpoint has a response model, and validators live inside Pydantic classes.

This matters because validation catches bad input before it reaches the business logic, which is where most security bugs and many crashes come from.

### Weak REST API design

Bad API design is easy to spot in an interview: `/getUser?id=5` instead of `/users/5`, POST used for everything including reads, status codes that don't match the outcome, and endpoint names that describe implementation instead of resources.

General rules that apply everywhere, not just in FastAPI:

- URLs describe resources, not actions.
- HTTP methods describe the action: GET reads, POST creates, PUT and PATCH update, DELETE removes.
- Status codes match the outcome: 201 for created, 204 for no content, 404 for missing, 409 for conflict.
- Naming is consistent: plural nouns for collections, singular resources under them.

Candidates who ignore these in design questions usually ignore them in code, too.

### Forgetting production considerations

Production is where FastAPI gets interesting, and interviewers ask about it because that's where things break.

Your answers on this topic should account for:

- Multiple worker processes, not a single Uvicorn process
- A reverse proxy in front, handling TLS and buffering
- Health check endpoints for the orchestrator
- Structured logging with request IDs
- Environment-based config
- Secrets from a secrets manager
- Migrations run separately from app startup
- Metrics on request rate, latency, and error rate

## How to Prepare for a FastAPI Interview

The best FastAPI prep is building something and breaking it. Reading docs works for the beginner questions, but beyond that you need code you've actually written, deployed, debugged, and thought about.

### Build a real REST API

Pick a project idea and build it end to end. Not a to-do list: something with at least three related resources, real relationships between them, and a few endpoints per resource.

A rough idea that covers most interview topics:

- Users with signup, login, and profile endpoints
- A second resource users can create, read, update, and delete
- A third resource that belongs to the second one, so you get nested routes
- Filtering, pagination, and sorting on the list endpoints

Build it with Pydantic models, a database, and proper response models. When you're done, you'll have working code to reference in every answer.

### Deploy a FastAPI application

Deploy the API somewhere, like a cheap VPS. The point is going through the full path from code to running service.

This teaches you more than you'd expect:

- Writing a Dockerfile that works
- Running Uvicorn workers, optionally under Gunicorn
- Putting Nginx or a cloud load balancer in front
- Getting HTTPS working with a real certificate
- Handling environment variables and secrets
- Setting up basic monitoring, or at least log aggregation

### Practice async programming

Async is where most candidates lose points.

A useful exercise: build a small script that fetches data from three APIs concurrently with `httpx.AsyncClient` and `asyncio.gather`. Then rewrite the same script with sync `requests` and compare the times. Then break the async version by putting a `time.sleep` in the middle.

Do the same with async SQLAlchemy. Feel where async helps and where it doesn't.

### Learn Pydantic properly

Pydantic isn't just types. It's validators, model config, computed fields, discriminated unions, and serialization control. Interviewers ask about it because it's at the core of every FastAPI service.

Areas you should know:

- Field types, defaults, and constraints (`Field(gt=0, max_length=100)`)
- Custom validators with `@field_validator` and `@model_validator`
- Model config for controlling serialization and validation behavior
- The difference between `model_dump()` and `model_dump_json()`
- How Pydantic handles optional fields, unions, and enums

Build a few complex models with nested structures, custom validators, and computed fields. That covers most of the intermediate interview questions.

### Understand dependency injection

Read FastAPI's dependency injection docs, then use dependencies for everything: auth, database sessions, config, permission checks, request context.

A good exercise is refactoring your practice API to move every reusable piece of logic into dependencies. When you're done, endpoints should be five to ten lines each and read like business logic without infrastructure noise.

### Review authentication workflows

Auth questions come up in every interview, and most candidates give surface-level answers. Go deeper than "we use JWT."

Build both patterns in your practice API:

- OAuth2 password flow with JWT access tokens
- API key authentication for a service-to-service endpoint

Then add authorization on top: role-based checks with dependencies, ownership checks that verify the user owns the resource, and a rate limiter for login attempts. Write tests that call both the allowed and denied paths.

Auth is one of those topics where hands-on experience shows immediately. You either know how tokens flow through a system or you don't, and interviewers can tell within two follow-up questions.

## Conclusion

FastAPI interviews aren't about syntax. They're about API design, deployment, async programming, and production engineering, and the interviewer can tell within two questions which of those you've actually done.

The fastest path there is building a real application with moderate complexity, like a REST API with users, resources, auth, and a database. Deploy it. Load-test it. When something breaks, fix it. That puts you in a much stronger position than candidates who've only read about it.
