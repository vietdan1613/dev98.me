Error handling and resource management are essential for building reliable Python applications. Exceptions help you respond to unexpected situations, while context managers and cleanup mechanisms ensure resources such as files, database connections, and network sessions are released correctly.

### 1. Exception Handling

An exception is an event that interrupts the normal execution of a program. Python uses `try`, `except`, `else`, and `finally` to handle exceptions and control execution flow.

```python
try:
    number = int("abc")
except ValueError:
    print("Invalid number")
else:
    print(f"Converted: {number}")
finally:
    print("Operation completed")
```

Execution flow:

- `try`: Executes the code that might raise an exception.
- `except`: Handles a matching exception.
- `else`: Executes if the `try` block completes without an exception.
- `finally`: Executes when control leaves the construct, including when an exception occurs or is handled.

You can handle multiple exception types:

```python
def divide(a: float, b: float) -> float:
    try:
        return a / b
    except ZeroDivisionError:
        raise ValueError("Divisor must not be zero")
```

Catch specific exceptions whenever possible. Avoid using a bare `except:` because it can catch exceptions such as `KeyboardInterrupt` and `SystemExit`, which usually should not be handled as ordinary application errors.

**Key takeaway:** Use exceptions for exceptional situations, handle errors at the appropriate level, and avoid silently ignoring failures.

### 2. Custom Exceptions

Custom exceptions let you represent application-specific errors with meaningful names. Define them by inheriting from `Exception` or one of its subclasses.

```python
class AppException(Exception):
    """Base exception for application errors."""


class PlantNotFoundError(AppException):
    """Raised when a requested plant does not exist."""


def get_plant(plant_id: int) -> dict:
    if plant_id <= 0:
        raise ValueError("Plant ID must be positive")

    plant = None  # Simulate a missing plant

    if plant is None:
        raise PlantNotFoundError(
            f"Plant {plant_id} was not found"
        )

    return plant
```

Callers can handle the specific error:

```python
try:
    get_plant(10)
except PlantNotFoundError as error:
    print(error)
```

For larger applications, a custom exception hierarchy helps separate domain errors from implementation details.

For example, a FastAPI application might define `PlantNotFoundError`, `InvalidOrderError`, and `PaymentFailedError`, then translate them into appropriate HTTP responses at the API boundary.

### 3. Exception Chaining

Exception chaining preserves the relationship between an original exception and a higher-level exception.

Use `raise ... from error` when translating a low-level exception into a more meaningful application error.

```python
class ConfigurationError(Exception):
    pass


def load_port(value: str) -> int:
    try:
        return int(value)
    except ValueError as error:
        raise ConfigurationError(
            "The configured port must be an integer"
        ) from error
```

The original `ValueError` remains available through the exception chain, making debugging easier.

Python also supports implicit exception chaining when a new exception is raised while another exception is being handled.

To suppress the displayed exception context intentionally, use `raise ... from None`, but do so only when hiding that context is appropriate.

### 4. File Handling with Context Managers

File handling involves opening, reading, writing, and closing files. The built-in `open()` function returns a file object that should be closed when it is no longer needed.

A context manager handles this lifecycle automatically.

```python
with open("data.txt", "r", encoding="utf-8") as file:
    content = file.read()

print(content)
```

When execution exits the `with` block, Python closes the file, even if an exception occurs inside the block.

Common file modes include:

| Mode | Purpose |
|---|---|
| `"r"` | Read an existing file |
| `"w"` | Write, replacing existing content |
| `"a"` | Append to a file |
| `"x"` | Create a new file, failing if it exists |
| `"b"` | Binary mode modifier |
| `"+"` | Enable reading and writing |

For example, writing a file:

```python
with open("output.txt", "w", encoding="utf-8") as file:
    file.write("Hello, Python!")
```

Use `pathlib.Path` when you want a convenient object-oriented interface for working with filesystem paths.

```python
from pathlib import Path

path = Path("data.txt")
content = path.read_text(encoding="utf-8")
```

### 5. Context Managers: `with` and `async with`

A context manager defines setup and cleanup behavior around a block of code.

The `with` statement uses the synchronous context management protocol:

- `__enter__()` runs when entering the block.
- `__exit__()` runs when leaving the block.

The asynchronous equivalent uses `async with`:

- `__aenter__()` performs asynchronous setup.
- `__aexit__()` performs asynchronous cleanup.

#### Example: Synchronous context manager

```python
with open("data.txt", "r", encoding="utf-8") as file:
    content = file.read()
```

Python obtains the context manager, invokes its entry method, executes the block, and invokes its exit method when leaving the block.

#### Example: Asynchronous context manager

```python
async with session_factory() as session:
    result = await session.execute(query)
```

Here, assume `session_factory()` returns an asynchronous context manager, and `query` is a valid database statement. The context manager manages the session lifecycle, while `await` allows asynchronous database execution.

In practice, asynchronous database sessions often use `async with` to acquire and release resources, and `await` to perform I/O operations.

You can also define context managers using `contextlib`:

```python
from contextlib import contextmanager

@contextmanager
def managed_resource():
    print("Acquire resource")
    try:
        yield "resource"
    finally:
        print("Release resource")


with managed_resource() as resource:
    print(resource)
```

The `yield` separates setup from the managed block. The `finally` section performs cleanup when the block exits.

### 6. `try`, `finally`, and Resource Cleanup

Resource cleanup ensures that resources are released even when operations fail. Examples include closing files, releasing locks, and closing network connections.

A `finally` block is useful when cleanup must occur regardless of whether an exception is raised.

```python
resource = acquire_resource()

try:
    process(resource)
finally:
    release_resource(resource)
```

This assumes `acquire_resource()`, `process()`, and `release_resource()` are application-defined functions.

If acquisition succeeds, the `finally` block ensures that the resource is released after processing. However, if acquisition itself fails before the `try` block begins, there is no resource to release through this `finally` block.

For resources that support context management, prefer:

```python
with acquire_managed_resource() as resource:
    process(resource)
```

This makes the resource lifecycle explicit and reduces the risk of forgetting cleanup.

For asynchronous resources:

```python
async with acquire_async_resource() as resource:
    await process_async(resource)
```

Cleanup can still fail, so resource-management APIs should define how cleanup errors are handled. Avoid returning from a `finally` block because it can suppress an exception or override an earlier return value.

### 7. Logging Fundamentals

Logging records application events, warnings, and errors. Unlike `print()`, Python's `logging` module supports severity levels, timestamps, configurable handlers, and consistent formatting.

The main logging levels are:

- `DEBUG`: Detailed diagnostic information.
- `INFO`: Normal application events.
- `WARNING`: Unexpected conditions that do not necessarily stop execution.
- `ERROR`: A failure that prevents an operation from completing.
- `CRITICAL`: A serious failure that may affect the application as a whole.

Configure logging once near the application's entry point:

```python
import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s %(name)s: %(message)s",
)

logger = logging.getLogger(__name__)

logger.info("Application started")
logger.warning("Configuration value is missing")
```

Use `logger.exception()` inside an exception handler when you want to include the traceback:

```python
try:
    result = 10 / 0
except ZeroDivisionError:
    logger.exception("Failed to calculate the result")
```

`logger.exception()` automatically includes exception information and should generally be called from an exception handler.

For expected failures, avoid logging the same exception at every layer. Record it at the level that has enough context to make the log useful, and let higher layers decide whether the error should be handled, translated, or propagated.

Never log passwords, access tokens, database credentials, or other sensitive data.
