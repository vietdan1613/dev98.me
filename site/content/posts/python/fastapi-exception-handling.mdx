Building a production-ready API is not only about handling successful requests. A good API should also handle failures consistently, safely, and predictably.

We want to:

- Return consistent error responses.
- Keep business logic clean.
- Log unexpected failures properly.
- Handle different types of errors in one centralized place.

> **Services should raise meaningful exceptions. Global handlers should decide how those exceptions become HTTP responses.**

## Create a Custom `AppException` 🛠️

First, create a base exception for errors that belong to your application.

```python
class AppException(Exception):
    """
    Custom application exception for standardized error handling.

    Attributes:
        error_code (int): Custom application-specific error code.
        error_message (str): Description of the error.
        error (Any, optional): Additional error details (e.g., stack trace, validation issues).
        status_code (int): HTTP status code associated with this error (default is 500).
    """

    def __init__(
        self,
        error_code: int,
        error_message: str,
        error: Union[Any, None] = None,
        status_code: int = 500
    ):
        """
        Initialize an AppException instance.

        Args:
            error_code (int): A unique application-defined error code.
            error_message (str): A human-readable message describing the error.
            error (Any, optional): Additional context or data about the error.
            status_code (int, optional): HTTP status code to return (default is 500).
        """
        self.status_code = status_code
        self.error_code = error_code
        self.error_message = error_message
        self.error = error
        super().__init__(self.error_message)
```

The exception can contain a few important pieces of information:

- `status_code` — the HTTP status returned to the client.
- `error_code` — an application-specific error code.
- `error_message` — a human-readable message.
- `error` — optional additional information.

This gives the application a standardized way to represent errors.

## Create Global Exception Handlers 🌐

Instead of handling errors inside every route, define exception handlers centrally.

For example, we can have handlers for:

- `HTTPException` — standard HTTP errors.
- `RequestValidationError` — invalid request data.
- `AppException` — application-specific errors.
- `Exception` — unexpected errors.

```python
logger = logging.getLogger(__name__)

def generate_error_response(status_code: int, error_code: int, message: str, error: Any = None):
    return JSONResponse(
        status_code=status_code,
        content={
            "status_code": error_code,
            "message": message,
            "error": error
        }
    )

# 1. Handle standard HTTPExceptions
async def http_exception_handler(request: Request, exc: HTTPException):
    logger.warning(f"HTTPException: {exc.detail}")
    return generate_error_response(
        status_code=exc.status_code,
        error_code=exc.status_code,
        message="HTTP Exception",
        error=exc.detail
    )
```

## Register the Handlers in `main.py` 🚀

Once the handlers are created, register them with FastAPI:

```python
app.add_exception_handler(AppException, app_exception_handler)
app.add_exception_handler(RequestValidationError, validation_exception_handler)
app.add_exception_handler(Exception, generic_exception_handler)
```

From this point on, FastAPI knows which handler should process each type of exception.

So when a service raises:

```python
raise AppException(...)
```

FastAPI automatically sends it to the corresponding handler.

## Create Specific Exceptions for Different Modules 📦

As the application grows, you may want different exception types for different areas.

For example:

```text
AppException
├── DBException
├── AuthException
├── PaymentException
└── ExternalAPIException
```

A database operation can raise `DBException`, while authentication logic can raise `AuthException`.

This makes errors easier to identify and organize without changing the global handling mechanism.

All of them can still inherit from `AppException`, so they can be handled centrally.

## Use Exceptions in Your Services 💬

The service layer should focus on business logic instead of creating HTTP responses.

For example, if a database operation fails:

```python
try:
    result = await session.execute(...)
except SQLAlchemyError as e:
    await session.rollback()
    raise DBException(
        error_code=1001,
        error_message="Failed to retrieve client."
    )
```

The service simply detects the problem and raises an appropriate exception.
